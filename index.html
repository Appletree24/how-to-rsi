    Chapter 01
    
认识 DeepSeek Harness

    
先回答三个问题：什么是 Agent Harness？为什么“一切皆插件”？以及——它在你机器上长什么样。


    
什么是 Agent Harness

    
大模型只会“说话”；让它真正干活需要一套运行时：组装提示词、把工具暴露给模型、执行工具调用、把每一步记录成可重放的会话、处理取消/重试/恢复。这套运行时就是 Agent Harness。

    

      
🧠
模型负责思考
DeepSeek 等 LLM 提供推理与工具调用意图；对 harness 而言模型只是一个可替换的适配器。

      
⚙️
Harness 负责落地
文件、终端、浏览器、网络、子智能体……能力以插件形式注册，经统一流水线安全执行。

      
💾
会话是真相源
每一步都写入追加式会话日志：可重放、可 fork、可导出，重启后不丢上下文。

    


    
DSH 是什么

    
DeepSeek Harness(dsh)是 DeepSeek AI 开源的 agent harness，采用 everything-is-a-plugin 架构，底层是插件框架 Cordis(以 vendored 方式内置，其设计见论文《A Programming Paradigm for Spatiotemporal Composability》)。它以 MIT 协议发布。

    
核心世界观：没有特权核心模型适配器、工具注册表、会话日志、甚至 agent 循环本身都是插件，均可从配置替换。扩展 dsh 不是“patch 核心”，而是在旁边挂载一个新插件；注册都是可逆效果，插件卸载时自动回收。

    Chapter 02
    
Cordis 核心：插件、服务与事件

    
Cordis 是 DSH 脚下的插件框架：插件向共享上下文贡献服务、类型化事件与可逆效果。掌握本章五个理念，后面所有章节都会变得顺理成章。


    
五个理念看懂 Cordis

    


    
插件长什么样

    
仓库约定了两种导出形态，不得混用：服务包 default 导出其 Service 类；函数插件具名导出 name / inject / Config / apply 且绝不能有 default 导出——混用会让 Loader 丢弃函数插件的命名空间(这是一次真实事故，见 postmortem 0001)。

    

      
 函数插件骨架(教学示意，非仓库原文)

      
// 函数插件：具名导出 name / inject / Config / apply，禁止 default 导出
export const name = 'my-plugin'
export const inject = ['tools']            // 声明依赖：服务就绪前不加载
export interface Config { greeting: string }

export function apply(ctx: Context, config: Config) {
  // 注册即效果：ctx.effect() 返回 disposer，插件卸载/重载时自动回收
  ctx.effect(() => registerMyTool(ctx, config))
}

    

    
可选服务怎么读？已声明在 inject 里的服务用 ctx.键 读；可选服务必须用 ctx.get(name)——属性代理对插件拓扑敏感，而 ctx.get 读全局服务存储。这也来自 postmortem 0001 的教训。

Waterfall：环绕式中间件

    
ctx.waterfall 是 around-middleware：监听器收到 (...args, next)。调用 next() 把(可能被包装的)结果委托给下一个监听器；不调用就是短路。值通过 next() 的返回值逐层回传。

    
    
      
  • 合作型监听器通常修改共享的请求/决策对象后委托；也可以整体替换结果，下游只能看到替换后的值。
    • 
      
  • 单决策事件的短路是设计本意：拥有决定权的策略监听器可以不调 next() 直接返回；只做注释/观察的监听器必须委托。
    • 
      
  • prepend: true 仅在监听器必须先于常规注册运行时使用。
    • 
    

    

      
 waterfall 监听器(教学示意)

      
ctx.on('tools/pre-execute', async (call, next) => {
  if (violatesPolicy(call)) return deny(call)  // 短路：本监听器拥有决定权
  annotate(call)                               // 合作：注释后必须委托
  return next()
})

    


    
Loader 与 cordis.yml

    
插件树由 cordis.yml 配置行描述。!!js 表达式(注意：永远不是 !js)只允许出现在两处：插件的 config 与条目的 disabled；其它元数据保持字面量，环境选择插件时用 overlay。config 在声明注入就绪后、针对插件上下文插值；disabled 在每次挂载决策时、针对 loader 上下文求值。

    

      
 cordis.patch.yml(教学示意)

      
# patch 按 id 定位一行，整体替换其 config，或插入新行
- id: my-llm-row
  plugin: dsh-llm-deepseek
  config:
    baseURL: !!js process.env.DEEPSEEK_BASE_URL   # !!js 仅限 config / disabled

    


    
实践守则

    

      
行为封装进插件
工具流水线事件属于 ctx.tools，模型流属于 ctx.llm，存活 agent 协调属于 ctx.agents。拦截与策略用事件；直接能力调用用服务方法。

      
每个注册都有 disposer
要么从 ctx.effect() 返回，要么用帮你处理的 Cordis helper。teardown 顺序重要时，把相关工作放进同一个 effect，让回收按预期顺序展开。

    

    
本章要点插件实现 Service；Context 是服务仓库；inject 表达依赖；五种 dispatch 模式各司其职(waterfall 必须 next())；一切注册都是可逆效果。

  


  
  

    Chapter 03
    
架构总览：从引导到事件域

    
一个运行中的 dsh，是在启动时由有序分层组合出的插件树。理解“分层组合 + 核心服务 + 三大事件域”，就拿到了阅读整个仓库的地图。


    
Profile × Bundle × Patch：分层引导

    
Profile 是存在 Harness home 的具名组合：列出要堆叠的 bundle、存放仓外插件、保存用户自己的 cordis.patch.yml。Bundle 是“Cordis 配置行 + 它们挂载的代码”的分发格式，它插入的一切对上层保持可 patch。两者都在自己的 package.json 的 dsh 字段里自报身份。

    
层按以下顺序应用到一个空条目列表上(悬停感受层叠关系)：

    

      
1
Bundles(按 profile 声明的顺序)
如 dsh-base → dsh-web-app；base 提供模型适配器、工具、持久化、沙箱与审批策略、设置、凭据、遥测
↓

      
2
Profile 的 cordis.patch.yml
这个命名组合自己的补丁
↓

      
3
Home 层 cordis.patch.yml
用户在 Harness home 的全局补丁
↓

      
4
--patch 覆盖层
命令行临时叠加；patch 按 id 定位行、整体替换 config 或插入新行

    

    
发货的 profile：web(支持 patch 热重载)、headless、sdk、sdk-minimal、acp(启动时一次性应用所有层——一次性/stdio 应用拥有工作后替换依赖会破坏其生命周期)。其中 sdk-minimal 是刻意的例外：单 bundle 拥有完整显式插件树，不叠 dsh-base。

    Chapter 04
    
Agent Loop 剖析：一个回合的一生

    
这是全站最重要的一章。先记住两个定义，再用播放器逐帧看完一个回合 —— 右侧磁带会同步展示会话日志里真正留下的事件。


    

      
step 步骤
一次模型请求 + 它引发的工具调用。

      
turn 回合
零到多个 step：在领取第一份输入前开启，直到不再“欠”任何工作才关闭。

      
round 轮次
包含一个 turn 的外层策略迭代(goal round、Ralph 尝试)；计数器属于那个策略。

    


    
回合播放器

    
示例任务：用户说“把 README 里的错别字改掉”。点击自动播放，或用 ←/→ 逐帧推进：

    


    
这张图背后的硬规则

    
    
      
  • 持久事件：turn/*、step/*、system/message、user/message、assistant/message、assistant/attempt、tool/* 写入会话日志；其余是三大域的存活扩展点。
    • 
      
  • waterfall 家族：agent/pre-step、agent/request、llm/stream 与三个 tools/* 事件都是 waterfall，监听器必须 next() 委托；agent/turn-stopping 是 serial，没有 next()。
    • 
      
  • 重试语义：每次尝试同步对账同一份已渲染组装，只在首次尝试追加 user 消息；重试不重新组装、不重跑 pre-step。失败/重试/取消/流错误的尝试沉淀为 assistant/attempt，不进入模型历史。
    • 
      
  • 历史不可变：循环发送不可变请求同时保持取消能力；消息冻结证据只在完整冻结的身份上复用。
    • 
      
  • 收件箱规则：输入经唯一 inbox 抵达驱动器；有些消息立即唤醒，注入的上下文(agent.inject())则等到另一条消息唤醒才随行。
    • 
      
  • 系统提示词也是历史：提示词只以 system/message 历史的形式旅行；空渲染会清空所有活跃 system 节点，不留旧提示词可见。
    • 
    


    
延伸阅读时序图 docs/agent-lifecycle.md、工具流水线 docs/tool-execution-pipeline.md、取消与错误恢复 docs/subsystems/core.md。驱动器本体在 packages/core/agent-loop，它只是“默认”实现 —— 接口在 core/agent，整个驱动器都可替换。

    
本章要点turn ⊇ step；每一帧要么是持久事件、要么是活体扩展点；模型历史从日志派生并冻结；拦截点 = agent/pre-step、agent/request、llm/stream、tools/*。

  


  
  

    Chapter 05
    
会话与持久化：日志即真相

    
DSH 最具区分度的设计：模型看到的上下文不是内存里的聊天数组，而是从追加式会话日志投影出来的。拿住这一点，fork、resume、导出、遥测就都顺理成章。


    
法则：模型可见 ⟺ 已记录

    
Model-visible means logged任何进入模型请求的内容必须能从会话日志重建，并有运行时不变量断言它。新的模型可见输入 ⇒ 必须先设计新的 session event。修改现有消息内容的插件则注册“纯消息投影”，离线读取方显式提供同一套定义。

    
deriveMessages() 从日志投影模型历史。每条 assistant/message 内嵌产生它的精确紧凑计时流；assistant/attempt 保留失败/重试/取消/流错误的尝试而不增加模型历史。Fork、resume、成稿、遥测、持久化全部源于这些持久结算；实时 UI 的增量渲染则来自进程内的 agent/assistant-stream 帧。


    
格式版本与代际：永不重写历史

    
磁盘上的会话是 JSONL(可选 zstd 压缩)。写入器版本由代码常量 SESSION_FORMAT_VERSION 唯一持有；当前已发布的最新格式是 v3(发布证据标签 dsh-v0.1.5-alpha.1)。升级不是“把旧文件改写”，而是在旁边发布新代：

    

      
session.jsonlv0 代际 · 永不动

      ── v0→v1 ─▶
      
session.v1.jsonl代际 · 永不动

      ── v1→v2 ─▶
      
session.v2.jsonl代际 · 永不动

      ── v2→v3 ─▶
      
session.v3.jsonl当前写入器格式

    

    
    
      
  • 每个迁移包只拥有一步 vN → vN+1：session-format-v0-to-v1、session-format-v1-to-v2、session-format-v2-to-v3。
    • 
      
  • 读式 open：选最高代际，内存中组合迁移链，不发布后继。写式 open：先编码、验证、独占式地在源文件旁发布版本命名的后继。
    • 
      
  • 已提交代际永不改名、替换、删除；前代不隐含回退或降级支持；拒绝打开未来版本。
    • 
      
  • 只有结构性格式变更才 bump SESSION_FORMAT_VERSION；读日志时遇到不认识的事件类型默认拒绝，除非事件声明 ignorable: true。
    • 
      
  • SQLite 后端(如会话检索索引)使用单调递增的 SCHEMA_VERSION。
    • 
    


    
投影 seam：读日志的正确姿势

    
dsh-session-projection 拥有 ctx.sessionProjections：注册的单元增量折叠已提交事件；宿主消费者用 stateOf() 读一个类型化状态，载体用 snapshot() 批量裁剪客户端视图。读取方要么在激活时就依赖该服务，要么在注册表/键缺失时显式失败——绝不默默兜底。agent-loop 自己就注册了共享的 turnBoundary 状态。


    
换存储后端？一个接口的事

    

      
 SessionPersistence — 存储 seam

      
create / open / stat / list / export
# 在共享的 handle 脚手架上实现这五个操作,就是一个新后端
# 参考实现:packages/session/session-persistence-jsonl

    

    
相关铁律：公开 API 处于预稳定阶段——但“已发布的会话数据契约”不随便变：alpha/beta/rc 的产品发布就建立了发布格式义务，GitHub 的 prerelease 旗子不使用户数据变得可抛弃。持久化类型的变更需要在 PR 中按流程“签收”(docs/cookbook/reviewing-persistence-type-changes.md)。


    
本章要点日志是唯一真相源；模型可见 ⟺ 已记录；代际只增不改；迁移每包一步；读状态走投影 seam。

包版图：52 组 · 280+ 包的全景地图

    
每个 npm 包都叫 @deepseek-ai/dsh-*，住在 packages/<分组>/<包名>/，且恰好属于一个分组；分组 README 是该家族的权威地图。下面的探索器收录了全部分组与包名(取自仓库实测)。

    
使用方式点分类胶囊按领域筛选；搜框支持包名/分组/职责关键词；点分组标题展开全部包。试试搜 tool-(模型工具 Consumer)、-local(本地 Provider)、session-format(迁移链)。

    


    
读懂命名规律

    

      
seam 三件套
很多分组呈现“定义 / Provider / 工具”三段式：如 shell(定义) + bash-local/bash-sandbox(Provider) + tool-bash(Consumer)。

      
依赖方向铁律
扩展插件依赖 Service Definition，永不依赖具体 Provider；UI/hook/工具插件用 dsh-agent，因为 dsh-agent-loop 可整体替换。

      
发布预期
多数分组是产品级；experimental/ 无稳定性承诺；test-support、runtime-diagnostics、util 是支撑级、兼容性预期更低。

    

    
依赖图由生成器维护：docs/module-graph.md(pnpm run gen-module-graph，CI 保鲜)。每个包 README 都有固定栏目：用途、配置、扩展点、Model Experience、Known Limitations。

    
本章要点分组即能力家族；命名自解释(tool-* / *-local / *-sandbox / session-format-*)；依赖只指向定义、不指向 Provider。

  


  
  

    Chapter 07
    
工具与能力接缝

    
工具是模型能力的出口：注册在 ctx.tools，schema 自动加入提示词组装，执行时穿过带守卫的流水线。而工具背后的能力，由“接缝”解耦：换一个 Provider，整个产品的执行世界随之切换。


    
Capability Seam：定义 / 提供 / 消费

    

      
    

    
seam 是完整能力，不是单个角色：新增能力意味着同时设计三角色(一个包可以兼任多角色，但只在角色独立演化时才拆开)。它的威力在于“一次替换，整产品联动”：文件系统与子进程 Provider 共享一个执行世界，指向远程沙箱(如 ssh 家族)后，Bash、PTY、LSP 一起搬家，无需为每个工具 fork 一份实现。


    
工具执行流水线

    

      
 一次工具调用的旅程

      
tool/call            # 持久事件:模型的调用意图入帐
tools/pre-execute    # waterfall:审批、改写、拒绝的策略挂点
tools/execute        # waterfall:真正执行(guard 的截止时间强制器也在这层)
tools/post-execute   # waterfall:结果后处理(溢写、裁剪、呈现元数据)
tool/result          # 持久事件:结果入帐,回传模型

    

    
配套规则：每个工具在设计之初就要规划 UI 呈现 —— Host presenter 保持纯函数，Web 卡片从原始事件与持久化结果元数据派生(docs/cookbook/adding-a-tool.md)。作用域规则见术语表：工具可以全局或按 agent 作用域注册，同名时作用域胜(shadowing)，tools.restrict 按交集过滤。


    
工具目录探索器(72 个 schema)

    

    
本章要点工具 = Consumer 角色；流水线五站两头持久、中间三个 waterfall；seam 让“换后端”变成配置问题而非重写问题。

    Chapter 09
    
测试体系：推理在这里很便宜

    
DSH 的测试哲学有两个鲜明立场：① 能用真实实现就不用 mock；② “我们是 DeepSeek，不要吃真实 API 测试的米”——无密钥测试只能证明管道通，只有带密钥的运行才证明 agent 真的能干活。


    
七层测试塔

    

      
unit · pnpm run test vitest；每个注册表都有 HMR 安全测试(卸载 fiber、断言清理)；偏好边界/错误路径/事件顺序/并发竞争

      
coverage · test:coverage CI 门禁：packages/*/*/src 逐文件 100%。未覆盖行往往是该删的死代码；行覆盖必要但永不充分

      
expected · test:expected 无密钥的 CLI/进程期望输出；驱动器 *.expected.e2e.ts；CI 跑已构建导出

      
bench · test:bench benchmarks/ 用户路径性能门禁(Linux PR 必过)；计时代码跑纯 Node，绝不 TSX

      
snapshot · test:snapshot 无密钥录制会话回放：父代录制同时充当输入、模型回放与期望结果；跨 headless/SDK/ACP/Web 四入口

      
web · test:web Chromium 比对 snapshots/web/ 与 UI 期望输出；CI 强制只读 replay，录制留在本地

      
e2e · test:e2e 真实 API：无密钥自动跳过；覆盖写文件任务、多轮对话、工具使用、中流取消；最高价值是 boot 真 profile 的冒烟测试

    

    
悬停/点击每层查看说明。注意：test:coverage 才是 CI 覆盖门禁，test 不是。


    
四条铁律

    

      
真实优于 mock
只 mock 昂贵或非确定性边界(LLM 适配器、网络、时钟)，下游全部真实。桥接测试用真工具注册表 + 真流水线 + 脚本化 MockAdapter。

      
验证世界，不验证自报
e2e 断言要重新执行命令或重读文件；对 agent 自己输出做关键词探测会让“作弊”的 agent 通过。未触碰的文件要断言字节级一致。

      
测真实入口路径
产品可见插件必须有 REAL-composition 测试：测试专属 cordis.yml 经 Loader 启动；发布物用构建产物冒烟(bin 跑 lib/的纯 Node)——tsx 会掩盖的故障在这里暴露。

      
测试自己管好资源
并发 worker 共一台机器：端口、路径、子进程不隔离。谁申请谁释放(afterEach 即使失败/超时)；“只有单跑才过”是测试的缺陷而非环境问题。

    


    
快照测试：什么时候必须写

    
每个非平凡的“模型可见 / 协议可见 / 人类可见”变更，必须在同一个 PR 里新增或更新一个无密钥录制会话场景；包内单测、mock 测试、理由陈述都不能替代“组装后的真实成稿”。agent-loop / 会话生命周期 / SessionEventMap 的变更还要同步更新 TypeScript 与 Python 两个 SDK 的期望输出。

    

      
 快照工作流

      
pnpm run test:snapshot -t "场景名"   # 无密钥回放
pnpm run test:snapshot:record        # 模型成稿变了 → 重录(需密钥),逐 diff 评审
# 回放输入仍有效、仅派生变化 → 用 test:snapshot:refresh

    

    
本章要点覆盖门禁逐文件 100%；mock 止于非确定性边界；断言世界而非自报；模型可见变更必须附录制快照；e2e 无密钥自动跳过。

这个仓库的协作文化

    

      
按面选检查，不跑全量
推送前只跑覆盖本次 diff 的最小检查集：行为测试、相关快照、文档改动跑 doc-sync。CI 才拥有穷举覆盖与平台矩阵；默认全量重跑是反模式。

      
Agent Notes 文化
非平凡改动在同一 PR 写决策记录(.agents/notes/)：为什么、放弃了什么、需要什么验证。归档的 note 冻结为历史，永不当现行权威引用。

      
PR 历史是设计出来的
独立改动拆 PR；在引入问题的 PR 里修而非向下传播；重写只用 --force-with-lease且远端有新提交即中止；每个 PR 打一个 kind/* 标签、所有相关 area/* 标签。

      
文档与代码同行
README/JSDoc 随代码同 PR 更新；文档一段一物理行、中英双语成对；每个事实只有一个“家”，其它地方链过去(还有字数预算门禁!)。
