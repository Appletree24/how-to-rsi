# 改进器自应用：可逐条追踪的有限实验

这个实验实际运行一个时长解析器，并修改它的补丁配置与改进器的尝试顺序。所有补丁、评分函数和搜索规则由人编写，没有 LLM 调用或生成代码执行。它帮助区分“解题器变好”与“改进器参与修改自身”，不复现 STOP、DGM 或 HGM 的基准成绩。

## 运行

Python 3.10+，标准库。在仓库根目录：

```sh
python labs/improver_lab.py
python labs/improver_lab.py --rounds 2 --output lab-output/improver/two-rounds.json
python -m unittest tests.test_improver_lab -v
```

默认报告在 `lab-output/improver/report.json`。源码：[improver_lab.py](../improver_lab.py)。章节源文件：[01](../../content/chapters/rsi.html)、[R1](../../content/chapters/research-contract.html)、[R2](../../content/chapters/paper-lab.html)；阅读网页请在站内导航中打开相应章节。

## 被修改的东西

`Solver.enabled` 是四个补丁的子集，共 16 个配置。解析器返回非负整数毫秒，不支持负数、科学计数法或小于整数毫秒的结果；不支持的格式返回 `None`。

| 操作 | 修改 Solver | 修改 Improver |
| --- | --- | --- |
| units | 识别 ms / s，后者乘 1000 | 将 units 移到尝试顺序最前 |
| case | 先转小写 | 将 case 移到最前 |
| trim | 先去首尾空白 | 将 trim 移到最前 |
| decimal | 允许小数，结果仍须为整数毫秒 | 将 decimal 移到最前 |

`Improver.order` 是四种操作的排列，共 24 个配置。`improve` 先评价原目标，再按控制者顺序依次提议；严格涨分才接受，相同得分不接受。每个候选在当前已接受目标上产生，但同一次调用中的控制者顺序固定。返回的新控制者只在下一次调用接管。

这几个固定规则让过程可完整枚举。它不会自行发明补丁、改写贪心算法或扩大搜索空间。

## 两层评分

对解题器的 U：在十条开发输入上执行解析，计算通过比例。

对改进器的 M：从空 Solver 开始，让该改进器提议两次，再取终选 Solver 的 U。每次 M 包含三次整组评分：初始状态一次，加两个候选。最终得分从已测缓存取出，不再额外执行一次评分。

训练时执行 `improve(I0, I0, M, budget=4)`。外层四个提议由 I0 的顺序产生。初始 M 为 0.4；候选 M 依次为 0.4、0.3、0.8、0.4，只有 trim 优先被接受。随后在新的 Solver 上实际应用训练得到的 I1。

## 默认实际结果

| 方法 | 开发 | 同模板确认 | 格式比例变化 | 训练 + 应用评分 |
| --- | --- | --- | --- | --- |
| 冻结 I0 | 4/10 | 4/10 | 8/10 | 0 + 3 |
| 自应用得到 I1 | 8/10 | 8/10 | 3/10 | 15 + 3 |
| 全部配置穷举 | 10/10 | 10/10 | 10/10 | 0 + 16 |

初始顺序是 `units, case, trim, decimal`，训练后是 `trim, units, case, decimal`。训练包含初始改进器和四个候选的 M，所以是 `5 × 3 = 15` 次整组评分，共 150 次单条输入执行。

每个方法还另做 30 次单条输入检查，供最终三个任务集的报告使用。上表不将这部分报告开销混入搜索；JSON 单列 `final_report_task_executions`。成本单位是整组评分次数，没有测量各配置不同的 CPU 耗时。

`--rounds 2` 保持同样顺序与终选 Solver，训练成本变为 30。多跑一轮没有增加能力。空修改也耗费评分预算；演示有意不跨候选缓存 M，以便看清嵌套开销。

## 怎么读报告

- `initial_order` / `updated_order`：改进器更新是否真的发生。
- `training.trace`：内层标记为 `meta-0/inner`，外层为 `meta-0/outer`，按实际调用顺序记录。每条包括操作、父配置、候选、分数和接受状态。
- `meta_history`：每轮外层搜索结束后的顺序与该轮成本。
- `methods.*.trace`：训练结束后，各策略从新起点执行的求解器搜索；穷举只报告最终配置与完整计数，不生成贪心 trace。
- `methods.*.results.*.trials`：逐条输入、期望、实际返回值与通过状态。
- `code_sha256`：运行时的源码摘要，用于识别实验版本，不是签名或防篡改措施。

`DEV` 之外的数据不传入训练。所有方法选择结束后才调用 `measurements` 生成最终报告。源码及三个任务集都是公开的；confirm 沿用开发集模板、只换数字，不是隐藏基准，也没有代码隔离保障。

## 解释负结果

I1 在两次补丁机会内更适合空白较多的开发模板。变化集含更多大写单位，I0 学到的 `units + case` 更合适，I1 的 `trim + units` 发生退化。这是任务构成变化带来的结果，不是随机波动。

从零开始，总共 18 次评分仍劣于 16 次穷举。若把训练成本摊给后续多个任务，需报告复用次数并重新比较质量与成本。不能只拿应用的三次评分声称整个方法更便宜。

## 继续动手

1. 调用 `improve` 将内层预算改为四次，遍历 24 个顺序。解释为什么先提 case/decimal 会在没有 units 时被拒绝。保存所有被拒候选，检查哪些是互补补丁。
2. 增加保留相同得分候选的策略，与严格贪心比较。这项改动由实验者定义；要让程序选择搜索规则，需要将规则本身纳入候选空间。
3. 构造第三种格式比例，在看到结果前写下预期顺序。报告全部任务构成，避免只挑支持结论的样本。
4. 接到 RepoOps 时只改变提示或检索参数，保持模型、评分与预算固定。实现候选生成和独立运行后，重复完整搜索，比较真实模型下的结果与成本。
