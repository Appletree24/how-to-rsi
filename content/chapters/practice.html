项目任务书：知识助手、仓库修复与评测平台

知识助手、仓库修复 Agent 与评测平台面对三种不同的工程问题：答案是否有当前证据支持，执行能否修复故障且不越权，运行结果能否形成可靠比较。本章分别给出输入输出、实现路径与失败实验，再介绍可用于承载这些机制的 DSH 插件练习。

项目范围仓库提供教学 runner、检索与租约机制实验及统计比较程序。生产鉴权、真实模型接入、Harbor 修复任务、分布式控制面和发布服务属于下文的扩展实现。候选不得修改审批规则、权威评分器或未经授权的工作区；DSH 的审批与 Provider 边界见安全与护栏。

共同的运行底座

三个项目都需要版本身份、执行轨迹、外部评分与状态恢复。本章后半部分的五项 DSH 练习依次处理组合检视、插件加载、日志持久化、评测接入与策略替换。也可以采用其他运行载体；项目契约中的记录与权限要求保持不变。

项目 A · 只读知识助手：证据、版本与拒答

需求：值班人员给出服务故障工单，助手从自己有权读取的事故记录和手册中提出处置建议。存在旧手册、相互矛盾的建议和不完整证据时，宁可返回证据不足，也不能把最相似的段落当作当前事实。先做只读问答，不执行处置。

契约具体要求与边界
输入task_id、工单、允许访问的文档集合、文档 revision 与运行预算；租户和访问策略是扩展项目需要新增的可信输入，不能让模型从正文推断授权。
输出建议动作、所依赖证据及版本、明确的拒答原因；每条引用能关联到本次真实读取。当前 runner 的 finish(answer,citations) 只提供基础答案/引用协议，版本与拒答结构需扩展。
预算先冻结工具步数、上下文长度和超时，再调 top-k。生产延迟目标按目标硬件与样本测量；不能把离线脚本耗时称为线上 P99。
验收物一条逐步可重放轨迹、候选集合与最终上下文、答案/引用评分、旧版误导反例与权限过滤反例。

工单场景：checkout-0 出现 POOL_EXHAUSTED，工单建议回滚，但当前手册要求 resize_pool。直接服从工单无法区分建议与证据；将全部检索结果放入上下文又可能让旧版抢占位置。P3 把处理过程分为候选召回、版本过滤、上下文选择、答案生成四个阶段，可以分别观察当前规则在哪一步丢失。

A 的现有起点 · 仓库根目录，Python 3.10+，不调用真实模型
python -m projects.repoops.runner demo
python projects/repoops/retrieval_failure_lab.py

第一条生成 lab-output/repoops/ 下的策略报告和数据库；第二条打印独立检索机制实验的 JSON。通过率来自公开教学工单与人为规则策略，只检验链路，不代表自然语言知识助手的质量。

失败实验：分别把正确手册降到预算边缘、加入同标题旧版、让正确文档对当前用户不可见。第三种情况下，返回结果应不受不可见内容影响，并进入证据不足路径；补充检索仍须遵守同一访问策略。将问题改为需要事故与手册两段联合证据后，Recall@k 只描述召回，答案正确性与引用覆盖需要分别评分。

比较方法：固定工单和预算，对照直接采用建议、现有词法检索与修改后的策略，将失败定位到读取权限、召回、上下文或答案消费。生产鉴权和向量/混合检索需要新增实现；通用自然语言的证据支持判断与真实模型效果，需要按 P1、P4 扩充数据和 grader 后测量。

项目 B · 仓库修复：行为验证与受限执行

需求：把同一连接池故障从“建议扩容”变为“提交配置 patch”。验收必须同时满足负载下不耗尽、连接总数不超过数据库配额、修改没有越过允许文件边界。把池大小设得无限大可能通过单项测试，却违反资源约束。

契约具体要求与边界
输入固定仓库快照、失败日志、行为要求、允许修改路径、容器 digest、CPU/内存/时间/网络限制；隐藏评分逻辑不进入候选可写域。
输出受限 patch、实际命令轨迹、退出与超时状态、独立 verifier 的行为结果；Agent 的“测试通过”文本不是评分。
最小执行边界专用无凭据环境运行 Agent；只把白名单产物传给 verifier，在干净环境应用并重新验证，不整体复制候选环境。
验收物可重建任务目录、oracle / 空 patch / 错误 patch 三组结果、修改范围校验、超时与残留副作用检查。

现有 search/read/finish 协议不写工作区。加入 shell 会新增文件、进程、网络和持久副作用边界，因此修复项目的第一步是用行为 verifier 定义成功，再开放完成任务所需的最小执行能力。工具调用成功与修复满足约束分别记录。

B 的起点 · 第一条现在可运行，后两条需先安装并锁定 Harbor/容器环境
python -m projects.repoops.runner run --policy evidence --max-steps 2
harbor run --help
harbor task init repoops-checkout

第一条用受限步数观察教学 runner 的预算终态，不执行修复。后两条用于确认本机 CLI 和创建任务目录；本仓库没有预生成的 Harbor 任务或容器实测结果。任务、oracle、环境与 tests 的配置流程见 P8。

失败注入与约束变更：提交只修改可见测试的 patch、越界写文件的 patch、能通过正常负载但超过配额的 patch，以及不退出的进程。分别检查独立评分、产物白名单、边界行为和硬终止。若改为允许外部数据库写入，恢复代码指针不能撤销已提交事务；在引入补偿前，应继续禁止该权限。

验收条件：oracle 在冻结环境通过，空 patch 与错误行为失败；篡改候选侧 grader 不改变独立裁决；基线与候选在同一预算下保留所有终态和实际成本。Harbor 适配、白名单产物传递与隔离环境是实现重点，完成后才能比较真实代码 Agent 的修复质量。普通容器共享宿主内核，其隔离能力不能直接外推为抵御任意恶意代码。

项目 C · 评测平台：重试身份与结果账本

需求：把冻结的任务×重复运行矩阵交给 worker 执行。worker 会慢、会失联、可能在重领后迟到提交；平台不能删掉失败提高成功率，也不能把两个 attempt 当成两道独立题。结果唯一性与实际费用是两本不同的账。

契约具体要求与边界
输入不可变 manifest：代码/模型/环境/任务/评分器版本、任务清单、重复次数、预算及确认协议。
输出完整 trial 矩阵、每次 attempt 的状态与费用、可重算配对报告、keep / reject / inconclusive；不完整报告不得触发发布。
最小机制先单机持久化与重跑；再以短事务领取、租约、单调 fencing token 和条件提交替换长事务。取消与迟到结果按同一权威状态判定。
验收物故障时序、旧 token 提交被拒证据、重复提交不重复接受证据、仍保留的外部费用、输入/裁决 JSON 与协议参数。
C 的起点 · 租约状态机与统计比较实验
python projects/repoops/lease_failure_lab.py
python labs/eval_lab.py demo --output lab-output
python labs/eval_lab.py compare lab-output/improvement.input.json

消息队列的至少一次投递语义不决定谁有权提交，也不消除已经发出的模型调用。P5 用 A 失联、B 重领、A 迟到的时序说明提交协议；平台任务书再把接受的执行结果接到统计裁决。租约实验运行真实 SQLite 状态转移，适合检查状态机而非估计高并发性能；评测实验消费合成观测，观测真实性仍依赖外部执行与验证。

失败实验：杀掉领取后的 worker、重复提交成功、删去失败 trial、伪造自报满分、让评分器版本不一致。领取中断与重复提交应保持接受结果唯一；缺失 trial 与版本不一致应阻止有效比较；自报分数不参与重算。报告分别呈现“输入无效”“候选被拒”和“证据不足”。扩展服务时还需实现 Go 控制面、多租户额度、公平调度、外部执行真实性证明、确认集访问控制与发布服务。

贯穿三个项目的 Harness 设计

Harness 将上下文、动作权限、运行恢复和评测连接起来。Harness 设计蓝图中的各组件可用下面四类记录落实到具体执行；设计方案与实际运行记录分开保存，便于定位实现缺口。

  1. 上下文清单：记录模型实际收到的指令、工具与证据版本，以及预算裁剪掉了什么。知识助手重点检查权限撤销，修复 Agent 检查仓库版本，评测 worker 检查评分信息没有进入候选上下文。
  2. 动作责任表：为每个工具写明副作用、授权点、审批绑定对象、幂等范围与未知结果的查证办法。不能把统一的“异常重试三次”应用于所有动作。
  3. 崩溃与取消记录：在准入前、动作后回包前、结果持久化后分别注入中断；区分未执行、结果未知、已经完成。除 UI 状态外，记录子进程是否退出及外部费用是否继续产生。
  4. 一次受控比较：固定模型、任务与总预算，只改变上下文策略或工具接口中的一项；保留全部失败和成本。先按 测试章 检验不变量，再按 P7 比较任务收益。

当任务从只读扩展到写生产配置时，身份传递、审批绑定、执行时再授权、隔离、未决结果查证与人工接管都成为执行前提。无法处理“已发生但未确认”的动作时，系统应保持只读，避免重试扩大副作用。

五项 DSH 插件练习

勾选进度保存在当前浏览器。各项练习的组合清单、版本、日志和评测结果可另存为实验记录，便于在后续项目中复用。

练习01 · 检视配置与运行时组合

配置文件描述计划加载的能力，运行时检视显示实际提供的能力。对照两者，可以发现 bundle、patch 与服务注册之间的差异，并确定后续插件的注册层。

故障定位：

  • dsh --profile web --dump-config 无输出或报错 → 确认 profile 名存在、Node ≥22.19；dump 是引导时打印，不是运行中查询。
  • cordis_inspect_list 返回空或工具不存在 → 当前 preset 没挂检视工具链（Host 侧检视注册表由 cordis-host-runner 提供，Creator 组合才有）；这是组合问题，不是权限问题。
  • Client 侧 query 一直 pending → Client 检视要等连着的浏览器页面应答；页面没开就没有答案。
  • “找不到某服务” → ctx 键与包名可能不同；Service.listService 提供签名目录，可用于定位确切服务。

记录当前组合清单：加载的 bundle/patch、最终配置与 cordis_* 工具可用性。练习02 用它确定插件的注册目标。

练习02 · 加载运行时插件

定义并加载一个插件，观察可调用工具或服务的变化，再停止插件，检查注册是否回收。审批行为、加载时机和卸载范围依实际使用的 DSH 版本确定。

故障定位：

  • cordis_define 成功但什么都没发生 → define 只校验并记录源码，不执行 apply；必须 cordis_run。
  • cordis_run 返回 awaiting-approval → 审批请求在 UI 上等人点，不是卡住，不要重发。
  • 返回 starting → 只是"进入异步激活"，不是成功；等 Run 卡报终态，失败就 cordis_inspect_self 读该包的 message/stack。
  • apply 里 ctx.xxx 是 undefined → 没声明 inject 的服务不许从 ctx 属性读；可选服务用 ctx.get('xxx') 并处理 undefined。
  • 卸载后副作用还在（同事件触发两次、工具残留）→ 有注册没走 ctx.effect()/ctx.on()；裸注册不归 fiber 管，stop 不会回收。
  • 审批被拒 → 该授权请求已终结，不应重复发送同一 package；代码调整后需 define 新 package 并重新申请审批。

记录 pluginId、packageId 与挂载/停止的完整状态。练习03 在同一加载流程中加入跨会话日志。

练习03 · 记忆：自改日志跨会话可读

保存改动、版本与结果，才能重建下一轮使用了什么反馈。跨会话读回还需要明确的检索路径，数据落盘并不意味着自动进入模型上下文。

故障定位：

  • storage 服务不可用 → 用 ctx.get('storage') 判断 undefined；当前组合可能未挂载 storage-sqlite 后端，可改用 session event。
  • 写了自定义 session event 却读不回 → SessionEventMap 读时必认：不认识的事件类型会被拒绝读日志，除非标 ignorable；动态插件更稳的路径是写 storage 或复用已声明的事件域。
  • fork/resume 后 agent"忘了"持续干活 → 这是特性：goal 激活（armed）故意不进持久日志，恢复后要人再授权才能自动续跑。
  • 日志落了账但下一轮看不到 → 落账不等于自动可见；要经 session 检索工具或投影读回，把"读回路径"也做成插件的一部分。

记录自改日志 schema：pluginId/packageId/意图/结果/时间。练习04 加入评分字段，第 25 章继续关联比较裁决。

练习04 · 为插件改动加入评测

给旧、新插件使用相同任务与评分规则，观察一次好改动和一次故意注入的坏改动。裁决写入候选无权覆盖的记录；两个不同插件名本身不构成隔离。代码指针恢复后，还要检查外部状态。

故障定位：

  • eval 没在挂载后触发 → cordis_run 的返回不是终态；监听 Run 的最终状态，或挂载后显式调用 eval 服务，别在工具调用里等浏览器侧结果。
  • 回滚未发生 → 回滚需要显式 cordis_run 到 currentPackageId；update 失败不会自动退回旧版，回滚由裁决门触发。
  • eval 结果被被测改动污染 → 工具限制与任务集只读只是局部控制；若评测仍在候选可修改的进程/文件域内，就没有独立评分边界。需要把权威观测与判定放到候选无权覆盖的控制域。
  • "分数涨了"但不可复现 → eval 输入要记 version 加任务集 hash；题目变了分数就不可比。

记录 eval(version) → {score, failures[]} 的最小实现与输入版本。第 25 章将其接入黄金集、隔离执行与裁决门。

练习05 · 策略插件化：改进改进过程

将候选生成策略抽成可替换服务，并验证下一轮真的调用新版本。手动替换只能证明可修改性；若要检验元改进，需要记录策略如何产生，并与冻结策略在同一起点和预算下比较。

故障定位：

  • 策略仍写死在宿主代码中 → 检查能否通过 cordis_run update 将策略换成另一个 packageId。
  • 替换后行为不变 → 检查回路是否每轮重新读取策略服务；仅在启动时读取会继续使用旧引用。
  • 策略绕过审批 → 策略插件同样受 cordis_run 审批约束；绕过意味着权限边界失效，详见第 11 章。

产物：一个可替换的策略服务与使用记录。接下来按 R1 设计共同起点、完整成本和冻结策略对照。

通用排查顺序

先定位版本指针和包级诊断，再检查审批、激活与资源回收，可区分配置问题、授权等待和执行失败：

步动作看什么
1cordis_inspect_self(pluginId)版本指针：currentPackageId / nextPackageId 各指哪；next 卡住多半是审批未完
2cordis_inspect_self(pluginId, packageId)该包源码与 message/stack——技术失败的唯一权威出处
3看 Run 卡状态awaiting-approval＝等人；starting＝Client 激活中；failed＝读第 2 步的诊断
4审批被拒不要重发同一 package；改代码 → define 新 package → run
5副作用未回收的征兆stop 后同事件仍触发、工具重复出现 → 有注册没走 effect/fiber
6全绿但行为没变监听器挂在从未分发的事件上：用 Event.listEvents 确认事件存在与分发模式

换用其他载体时，保留版本、观测、评估与策略使用记录，再按目标版本实现加载和恢复。是否能改提示、代码或运行时组件，要检查具体接口；这些实现选择不直接决定递归收益。
