在 Harbor 中运行仓库修复

前面的 Agent 只返回处置建议。现在把一张 RepoOps 任务迁移到 Harbor，让 Agent 修改服务配置，再由独立 verifier 检查修改后的行为。

写文件后的新增权限

前面已经确定任务契约、评分和预算，升级执行环境时才能定位新增问题。Host 上的 subprocess 不是沙箱；普通容器共享宿主内核，也不能仅凭“用了 Docker”宣称可承受任意恶意程序。学习实验使用无凭据、无宿主敏感挂载、受限网络与资源的专用环境；更强对手需要额外隔离设计。

迁移步骤与具体文件

  1. 阅读 Harbor 官方 Create a task，使用 harbor task init repoops-checkout 建目录。固定框架依赖版本和镜像 digest，保留安装日志；本站记录的是源码核对提交，不是已测试的兼容组合。
  2. instruction.md 描述验收行为：给定并发负载下连接池不得耗尽，最大连接数不得超过数据库配额，修改只允许落在配置文件。
  3. environment/ 放小型被测服务、公开失败日志和配置；solution/solve.sh 是人工 oracle；tests/ 保存外部行为验证。测试应覆盖边界负载，避免只检查配置等于一个固定数字。
  4. task.toml 写 agent/verifier 时间限制、CPU/内存与隔离配置。先用 oracle 跑通，再用空提交和错误配置确认 verifier 会失败。
  5. 接 mini-SWE-agent：把 provider、提示与工具预算固定，读取其轨迹；对照自研循环和该基线，只有在观测到具体瓶颈后才添加专用工具。
  6. 将 Harbor trial 结果适配到 RepoOps 实验账本，保留原始 status、reward、错误、耗时和 artifact；未知字段/缺失 reward 不得默认成功。

独立 verifier 需要显式启用

Harbor 文档说明，默认 verifier 与 Agent 使用同一容器；可通过 [verifier] environment_mode="separate" 或 verifier 专属 environment 配置启用独立环境。独立环境不会自动继承 Agent 的文件修改，因此必须声明要传递的产物。只传递允许的 patch/配置，不能把整个已被修改的测试环境复制给裁判。

官方 CLI 的最小操作；需先安装框架和容器运行时
harbor task init repoops-checkout
# 按本章填写任务、环境、solution、tests 和 task.toml
harbor run -p repoops-checkout -a oracle
harbor view ./jobs

本章命令是给学习者的操作步骤，本仓库没有预生成可直接运行的 Harbor 任务或完成容器实测。真实 Agent 的命令和可用名称以你锁定版本的 harbor run --help 为准。优先验证一个完整任务，再批量迁移。

公开基准怎样选

偏代码修复选 SWE-bench 风格的 issue→patch→tests；偏命令行和系统任务选 Terminal-Bench/Harbor 的任务形式。先按项目能力挑 10–20 个可运行任务作为开发子集，记录筛选标准、来源许可、镜像和排除项；这不是完整榜单复现，不与公开榜单直接比较。验证集须避免和用于学习工具的任务重叠。

需要读懂两处代码：mini 的环境执行如何接入 Agent；Harbor 的 Trial 如何关联任务、执行环境、verifier、结果和生命周期。固定版本入口见源码映射。源码审阅只能支持设计理解，不能替代你自己的兼容性测试。

练习：验证一张迁移任务

对迁移任务运行四次检查：oracle 应通过，错误实现应失败，Agent 修改可见的 grader 文件不应改变独立评分，超时任务应在预算内终止。记录 Agent 与 verifier 的权限范围。如果发现框架适配缺陷，保存锁定版本、最小复现和测试，作为开源 issue 或 PR 的依据。
