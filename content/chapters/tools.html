工具契约：授权、执行与副作用

仓库修复 agent 请求把 src/config.ts 的超时从 5 秒改成 10 秒。审批人点了允许，工具却在超时后继续写文件，下一次重试又应用了一遍补丁。这个故障跨越了参数、授权和执行三个边界：批准必须绑定具体操作，执行方必须管理副作用，结果必须区分已完成、未执行与尚不能确认的状态。

接口来源与案例范围本章 ToolDefinition、事件名、工具探索器与图来自本站保留的 DSH 历史接口整理，清单未保存上游 commit。输入与故障案例用于分析契约，未在 DSH 上运行。实际对接以锁定版本的字段、分发模式和取消实现为准；下方工具骨架仅展示结构。

Capability Seam：定义 / 提供 / 消费

模型表达操作意图，系统提供实际能力。历史 seam 结构将这两端连接为三种角色：Service Definition 声明接口，Provider 实现能力，Consumer 把能力包装成模型工具。以 shell 为例，工具接收请求并呈现结果，执行 Provider 管理进程、工作区和生命周期；两者依赖同一个契约，工具无需直接导入某个本地实现。

如果每个工具各带一个沙箱，Bash、文件、PTY 与 LSP 就会分别维护路径、凭据与生命周期，容易出现“读的是沙箱文件，测的是宿主副本”。共享能力接缝让组合层能够统一执行环境。隔离是否有效仍取决于实际绑定和权限；替代 Provider 的取消或文件原子性一旦变化，消费者也可能需要适配。

工具探索器

下面按历史来源分组保留工具索引。工具名是入口，资源的读写范围、所有权、审批要求和失败后的副作用则由完整执行路径决定。工具出现在模型 schema 中，仅表示模型可以提出相应请求，执行权限仍由宿主检查。

参数形状与资源授权

工具骨架(示意)
{
  name: 'read',                    // 模型侧名字 + 宿主侧唯一键
  description: '读 UTF-8 文本文件', // 引导模型选择工具，不是安全控制
  parameters: { /* JSON Schema */ },// 模型侧参数契约
  execute: async (args, ctx) => {…},// 宿主侧实现，不投影到模型 schema
  finalizeContent: (v) => …,        // 自定义落账形态(可选)
  // 策略字段(超时/审批标签/可见性)同样只在宿主侧
}

{"path":"../../secrets","encoding":"utf8"} 可以满足“path 为字符串”的 schema，却不应得到访问权。description 引导工具选择，schema 定义参数形状；对象权限、根目录、符号链接与执行环境必须在宿主可信边界处理。参数缺字段属于契约错误，字段合法但资源无权访问属于授权拒绝，区分两者有助于调用方决定如何处理失败。

历史 ctx.tools.schemas() 只投影白名单字段，execute、超时与审批标签留在宿主侧。宿主仍需验证模型输入，并保持审批与执行的一致性：tool/call 落账后，假如审批的是路径 A，执行前却被策略改成 B，历史、UI 和执行就会指向不同的行为。默认值解析和目标规范化应在明确的契约阶段生成执行规格，再让审批绑定最终目标。

拒绝发生在副作用之前

历史工具生命周期包含多个策略挂点，它们的执行时机不同。文件意图门禁发生在 execute 内部、实际文件操作之前；结果过滤发生在操作之后，两者不可互换。

tools 流水线
tool/call(先落账)
  → tools/pre-execute   allow / deny / cancel / ask
                          ask 需审批服务返回 allowed-once,缺通道即拒绝
  → 单调守卫            只能拒绝、无 allow 结果、顺序无法翻案
  → tools/execute       around 包装:超时/重试/指标;可替换 signal
  → tools/post-execute  accept / 替换 content|value / block(纠正→isError)
  → finalizeContent     定义自带的落账整形
  → tools/result        冻结通报
  → tool/result(落账)

timeout-policy 在 tools/execute 做包装；审批服务处理 pre-execute 的 ask 分支；fs-observation-policy 在 fs/write-intent / fs/edit-intent 拦截未观察就写的行为。单调守卫的意义是先前的拒绝不能被后一个监听器翻成允许，而不是监听顺序从此无关。会修改执行上下文的 around 包装仍需定义组合顺序。

事件顺序：修改 src/config.ts要成立的事实故障注入与预期边界
记录调用 → 审批调用标识、作用域、目标、变更内容与获准操作绑定批准后更换参数或作用域：旧批准不能复用；缺审批通道时不执行
读取版本 A → 意图检查 → 写入写入基于获准观察的版本，检查与写入之间的并发变化有明确策略其他进程先写成 B：拒绝冲突或重新读取、重新决策，不能盲目覆盖
执行 → 结果处理 → 落账记录实际状态，而非仅记录最终显示文本post-execute block 可以隐藏危险输出或标错，但不能声称磁盘写入已被撤销

“曾经读过这个路径”无法排除内容版本变化，也无法排除路径在检查后被换成符号链接。所需防线取决于威胁模型：协作编辑可使用版本前置条件；不可信并发进程还需要可信文件边界和抗竞争的访问方式。一次字符串前缀检查无法替代操作系统级约束，历史观察策略本身也未提供上述全部保证的实现依据。

超时后的状态与重试

设请求 call-17 已将配置写入磁盘，但确认响应丢失。调用方只知道超时，不知道是否提交；重试追加、付款、发信类操作可能造成双重副作用。超时是调用方观察，不是“操作没有发生”的证明。因此上面的 execute 包装虽可容纳重试，是否重试必须由工具语义决定，不能对一切异常统一重跑。

提交后响应丢失：预期故障轨迹
t0  call-17 获准，目标绑定到工作区与文件版本 A
t1  Provider 写入版本 B
t2  确认响应丢失，调用方超时并请求取消
t3  调用方不得将状态改写为“确定未执行”
t4  查询实际状态 / 等待执行终止；无法判定则保留未知状态
t5  只有接口明确支持时，携带稳定幂等键重试或执行补偿

读取通常更容易安全重试，但读取也可能耗费配额或创建远程任务。幂等键只有被副作用拥有方持久处理、且与请求内容绑定才有效；在内存里记住一个 ID 不能跨重启去重。取消也应区分“发出 signal”和“Provider 已静止”。如果进程在收到取消前已经发信，kill 不能撤回邮件；返回结果必须保留已知事实和不确定性。

工具可见性与评测器的只读边界

历史 tools.restrict 让作用域可见工具取子集：被过滤的全局工具不进入 schema，执行查询也应拒绝，与不存在无法区分。这样既挡住正常选择，也挡住手工构造隐藏工具名的调用。但若保留任意 shell，“去掉 write”仍能通过 shell 改文件；若多个作用域共享可写存储，子 agent 仍能间接影响评测器。

因此 RSI 评测角色需要同时约束工具面、Provider 权限、文件/网络可达性和评分资产归属。作用域或 isolate realm 的名称本身不等于操作系统沙箱。把候选的 patch 作为数据交给可信执行器，通常比允许候选自己修改并调用评分插件更容易解释信任边界。

写入与取消的故障实验

在锁定版本的隔离工作区中，可以用四组实验检查上述契约。正常批准的写入应只改变目标工作区；拒绝和缺审批服务时文件摘要应保持不变；隐藏工具被直接调用时仍应拒绝；超时、进程退出和磁盘最终状态应分别记录。随后注入“读 A 后外部写 B”和“提交后响应丢失”，观察是否发生覆盖或重复执行。调用与审批的关联、实际副作用、最终结果和资源释放记录共同说明故障发生在哪一层；日志只需记录必要标识与摘要，避免复制敏感文件内容。实验结论限于所覆盖的环境与故障模型。
