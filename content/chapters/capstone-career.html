RepoOps / P11 · 项目面试

项目面试中的系统分析与证据

项目面试压缩了工程工作的时间尺度：一条运行轨迹呈现实现细节，一个条件变化暴露系统边界，一组结果记录说明测量是否可靠。讨论的深度来自这些材料之间的联系。本章以 RepoOps 为例，分析应用工程、评测工程和平台后端的共同问题，并给出可用于 45–60 分钟项目讨论的问题树；场景与评价框架均为本文设计，不是企业原题。

岗位方向决定讨论范围

应用工程侧重需求与用户结果，评测工程侧重测量与归因，平台后端侧重执行的可靠性与资源边界。一次面试通常围绕一个主方向展开，研究问题作为加深分支，并不要求所有项目都包含元改进。成功与失败轨迹、结果报告及其配置、具体代码改动共同界定可讨论的范围。个人原型和生产系统承担的约束不同；无法现场调用外部模型时，脱敏原始产物也可用于分析，但重放状态需明确。

RepoOps 的三个职责提供了一个分解方式：知识助手负责受权限约束地检索、引用和回答；仓库修复器负责在隔离环境生成允许范围内的 patch；评测平台负责分发任务、恢复执行、记账、独立评分和版本比较。三者可共享任务标识与报告，权限和成功判定则各有边界。当前 starter 实现规则/可选本机模型工具循环与串行账本；Harbor、GEPA、分布式服务和元改进属于扩展设计。

主方向关注的工作能力相关项目材料材料的局限
Agent / AI 应用工程把实际需求变成可用原型，评估失败与解释方案P2 循环、P3 检索、真实错误与兜底只展示正常聊天与框架调用
评测 / Research Engineer定义能力、独立判分、定位回归、控制比较条件P4、P7、负结果与选择历史只有排行榜分数或模型 API 包装
AI 基础设施 / 研究平台后端一致性、恢复、资源预算、隔离与容量判断P5、P8 的故障时序和边界把本机负载与设计图称为生产规模经验

岗位样本来自 Anthropic 的 Model Evaluations、Research Infrastructure、Applied AI Research Engineer 招聘页，核对日期为 2026-09-19，仅用来识别工作能力，不代表中国市场比例，也不保证地点、资历和工作资格匹配；申请前需重查状态。模型训练岗位还需额外训练实践，本主线不声称覆盖。

45–60 分钟的讨论结构

时间讨论对象可观察的信息
0–5 分钟用户、失败代价、输入输出与完成范围实际运行与设计的区别；成功契约
5–15 分钟一条 trial 的输入、工具、终态、grader、报告及相关代码控制流、权限与数据来源
15–25 分钟一个条件变化：权限撤销、worker 迟到或测试可写旧方案的失效位置、可检验预测与局部修正
25–35 分钟一个效果数字的分母、预算、任务相关性与选择历史汇总到 trial 的可追溯性与因果声明范围
35–45 分钟失败案例的竞争解释，以及发布、拒绝或证据不足的决策判别实验、剩余解释与后续行动
45–60 分钟，可选岗位相关的局部编码、时序推演或 P9/P10 研究分析新反例下的不变量与设计取舍

这是一种时间分配方式，后面的问题树提供分支而非逐项必答清单。一个已经由代码与轨迹解释清楚的节点，无需重复讨论。问题条件、观察到的行为和证据位置构成记录；时间不足而没有覆盖的能力属于“未观察”，与错误回答不同。

问题树一：从一条运行轨迹理解 Agent

根问题是：“一张工单从输入走到最终判定，哪些动作由模型选择，哪些约束由程序强制？”它把讨论落到执行路径上：模块图说明职责，具体 tool call 及其前后状态说明职责如何落实；失败轨迹还会暴露正常演示中看不到的分支。

  • 工具选择分支：非法工具名、缺参数、重复动作和预算耗尽各自进入什么状态？schema 校验和终止位置说明程序的强制边界，仅有 prompt 约束仍留下执行风险。
  • 证据分支：文档存在、实际读过、内容支持结论分别由什么信号确认？新旧手册冲突时，讨论延伸到 P3 的排序、上下文与版本选择，也能解释召回提高而答案变差的情形。
  • 完成分支：Agent 返回 success 后，独立 grader 接收什么输入？答案正确但引用伪造的反例，可以检验运行终态与业务成功是否被区分；grader 本身的误判则需要审计记录。
  • 框架分支：迁移针对哪项已观察到的缺陷，哪些行为契约需要保持？工具错误、状态、费用与产物的适配成本决定迁移价值，自研代码量本身无法回答这个问题。

以 starter 的结构化评分为例，ok 表示正常提交，grade 还检查答案和引用，但这种规则检查没有证明自然语言证据蕴含。当前文档已读、最终动作却来自旧版时，最终请求中是否仍保留该证据是关键线索；授权 oracle 证据可以用于干预，但恢复结果尚不足以唯一归因于检索。这样的分析同时连接状态机、上下文和测量边界。

问题树二：条件变化下的系统边界

场景变更问题与分支相关机制
知识助手：文档已缓存，但用户权限刚被撤销缓存命中还能否返回？刷新方案涉及缓存键、读取时授权与失效窗口；放弃缓存则涉及成本和可用性授权判定位置，以及旧内容进入上下文与日志之前的阻断机制
平台：worker A 超时，B 重领后 A 又提交数据库保留谁的结果？锁释放后的旧提交、fencing 的条件更新，以及已发外部请求分别怎样处理？P5 的租约/epoch/提交条件时序，账本与结果的不同边界
平台：从 2 个 worker 扩到 20 个吞吐一定十倍吗？按队列、数据库、provider 配额、环境启动拆瓶颈；追问共享预算与取消竞态容量假设、每层排队与限流指标；没有负载实测就标推演，不编造 QPS
仓库修复：Agent 可改 tests，且提交 reward=1成功由什么过程确定？独立容器接收哪些文件，整目录复制是否污染运行入口？P8 的基线、patch 过滤、可信测试入口与拒绝反例

迟到提交把逻辑 trial 和物理 attempt 的区别暴露出来。更高 epoch 的新租约配合条件提交，可以拒绝旧结果；旧 worker 已发出的外部请求却不会被这一数据库检查撤销。账本仍需保留重复费用，有副作用工具还依赖外部幂等键或其他执行协议。串行 starter 不实现该服务，独立的租约机制实验与生产服务运行记录因此属于不同证据。

修复场景中的关键同样是边界位置。冻结 patch 应用到可信 commit 后，路径、文件类型与最终树检查限制可进入 verifier 的变更；可信入口再运行行为验证。删断言、伪造 reward 和越界路径分别检验这条链的不同环节。独立容器提供执行位置分离，无法替代产物过滤。

问题树三：成功率提升的测量依据

根问题可以落在一个具体结果上：“这个数字对应哪些任务、哪些配置和什么分母？”正收益、负结果和机制实验都可展开；决定讨论价值的是测量过程是否可恢复。

  1. 从汇总到明细：一个组成项能否回溯到 task、重复、trial、grader 版本与原始输出？缺少明细时，精确百分比的可靠性需要先由测量流程解释。
  2. 从差值到归因：两组改变了几处、是否同预算、失败与重试怎样计入？模型和 prompt 同时变化只能支持组合比较，单独归因还缺对应的消融组。
  3. 从运行数到样本单位：10 题各跑 100 次增加了随机性观测，并未产生 1000 道独立题；任务同源时还需考虑家族或仓库聚类。
  4. 从区间到选择历史：确认集是否参与过 prompt 调整，停止时机是否依赖“差一点显著”？这些适配会改变推断前提，单换统计方法不能恢复数据独立性。
  5. 从效果到采用：关键家族退化或成本越界时，原定发布规则怎样处理？总体涨分不能替代约束检查。

公开教学任务上的描述性差异，与真实 LLM 的能力收益不同。后者需要固定处理变量、任务级配对和全量消耗；同源任务还涉及独立家族层面的分析。最终集一旦参与 prompt 选择，便已提供开发信息，需要另取未参与选择的数据确认。结论范围由这些前提决定，而非由百分比的大小决定。

问题树四：回归诊断中的竞争解释

设新版本掉分，模型、索引或 grader 都可能有变化。讨论可从两个竞争假设及其不同预期开始，再选择最小实验。日志字段只有在某种取值会改变判断时才有诊断价值；保存轨迹的重评分则可能免去一次全系统重跑及其随机性。

诊断方案进一步的问题解释边界
同轨迹重评分新规则纠正了旧误判怎么办？以任务契约审查分歧，不为了恢复分数就回滚 grader
给 oracle 证据恢复是否证明唯一根因是检索？承认干预改变输入难度，回到真实检索修复后确认
排除 provider 错误这条排除规则何时定的？用户端超时去哪了？同时保留端到端完成率与条件成功率，不删除坏分母
直接换更大模型它区分了哪个假设？新增成本如何记？换模型可能绕过故障，却无法单独定位原因；归因仍依赖判别实验

被排除的假设、配置与干预结果也是诊断记录的一部分。它们连接 P6 的复盘与 P7 的修复确认，并解释为何没有采用其他方案。故障推演可以展示推理过程，但其观察范围不同于真实事故与修复运行。

加深分支：研究机制或局部实现

研究分支围绕资源与重复单位展开。反思搜索相对固定策略涨分，仍需相同总搜索预算的无反馈基线，才能区分反馈与额外尝试；一次完整搜索才是对应实验的重复。元改进进一步要求 I、共同 S0、冻结 I 对照与新家族确认，并计入元成本及只更新一份 I 的不确定性。P9 与 P10 的设计可以用于讨论，但已验证的收益需要实际结果支撑。

实现分支适合选一个与岗位相关的局部边界。例如两个乱序 attempt 的条件提交与取消竞态；Top-K 合并去重中的“高分文档无权限”反例；重复任务结果的配对差值与同仓库相关性。这类短题观察异常路径、边界与不变量，范围小于完整平台，也无法仅凭一次现场实现推定生产可靠性。

按观察行为组织评价

“描述 / 可执行 / 可审计 / 可迁移”提供四种证据深度，另设“未观察”表示本场未覆盖。每项评价附具体材料位置，使口头表达与实际实现能够相互核对。以下框架用于本文的问题分析，不代表企业通用招聘分数线。

维度描述：仍欠实证可执行：能走通机制可审计：能检验失败可迁移：条件变了仍能决策
需求与完成边界泛称提高效率/准确率给输入输出、失败代价及当前完成范围用反例检验成功契约，不把建议当执行权限、负载或用户目标改变后，主动修订契约与方案
实现与系统边界能画模块，找不到决定行为的位置从 trial 走到代码、状态与产物能展示非法动作、迟到提交或作弊 patch 的拒绝证据解释副作用/隔离剩余风险，提出最小修改而非无界重写
测量与因果只有平均分或最佳种子解释分母、预算、版本和逐题结果保留失败，处理配对、相关性与选择偏差在成本/分布改变时收窄结论，设计能否定主张的对照
诊断与改进罗列可能原因提出可区分假设和最小实验保存被排除的解释，并在原条件确认修复认识干预局限；负结果能改变后续资源分配
证据诚信与表达事实、计划、依赖能力混说区分自己实现、上游能力和待做设计数字可回溯，未知用量/未验证结果明确标注受质疑后按证据改结论，不编补实验或夸大外推

这些维度不适合简单相加。核心实现能够运行，测量和诊断可以复核，研究主张有独立对照，分别回答不同的问题。合理的负结果也能体现实验判断；没有正收益不自动构成能力缺口。最终招聘决定还依赖岗位要求、基础能力与其他环节。

项目主张失效的几类情形

  • 完成范围与证据不符：任务说明、HTTP mock 或离线夹具无法证明服务已上线或真实模型已被测量；项目规模小本身不影响这一判断。
  • 成功信号不独立：Agent 自报成功、可修改的测试或伪造 reward 无法承担独立验收，相关业务结果仍需可信验证。
  • 恢复契约不成立：迟到 worker 能覆盖新结果，或重复费用与副作用没有定义时，exactly-once 主张缺少关键机制。
  • 结果口径发生选择：删除失败、隐去重试成本或反复调整确认集，都会改变结果可支持的范围。
  • 研究缺少对照：没有冻结 I、共同起点或预算匹配，S 的涨分无法区分解题器变化与改进器收益。

一次可纠正的计算错误、尚未运行 Harbor、或没有显著收益，与上述主张失效不同。某项结论不成立、岗位核心能力存在缺口、本场没有观察到该能力，也需要分别记录，避免用笼统的“不够深入”替代具体分析。

项目描述中的分母、条件和贡献范围比孤立的“准确率提升 50%”更有解释力。课程原型与依赖项目的能力属于背景，新增实现和实际测量才界定个人贡献。career-evidence.md 提供岗位矩阵与投递记录结构，可把地点、资历要求与相关作品对应起来；投递时机取决于材料成熟度和岗位匹配，固定的周数或投递数量不保证回复。

项目材料也有覆盖不到的基础能力。算法与复杂度、JSONL 校验、Top-K 合并、有界并发取消、退避、幂等写入和配对统计可以独立练习；Go 的 goroutine/channel、内存与 race，Python 的异常、迭代器、类型与异步 I/O，需要各自的实现经验。模型相关讨论还涉及 Q/K/V、prefill/decode、KV cache、采样与结构化输出。训练岗位的 SFT/LoRA、偏好优化及真实实验属于额外范围，不能由 Agent 项目经历推定。

从未解决的问题到补充实验

面试记录可以保留触发条件、缺失证据与最小实验。例如，迟到提交的讨论尚未完成时，可构造旧 attempt 迟到场景，同时观察结果是否被覆盖、重复费用是否记账。后续材料沿这一具体问题补充，比重新扩写整段项目介绍更容易解释能力与结论发生了什么变化。
