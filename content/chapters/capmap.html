自修改实验的版本、运行记录与发布控制

候选 candidate-017 已经入档，线上仍使用旧版：这可以是有意的设计。搜索档案保存可继续探索的候选，发布系统只激活满足发布条件的版本。两者之间通过版本标识、运行记录、评分和决策建立关联。本章以缩小代码检索范围的变更为例，描述可接入 RepoOps 的记录与控制结构；自动候选生成、隔离执行和发布控制属于扩展设计，尚非现有实现。

变更对象由使用阶段决定

设 candidate-017 把 search_scope="repository" 改成 "changed_files"。若任务执行时读取它来检索代码，这是改变解题器 S；若候选生成时读取它来决定下一次如何提补丁，这是改变改进器 I。第一章中 Solver.enabled 与 Improver.order 的区分也是如此。字段的作用取决于读取阶段与调用点，同一份 Python 或 JSON 文件甚至可能同时承载两层策略。

改动实际影响需要检查的使用点
给任务提示增加检索说明可能改变解题策略 S任务调用是否加载这个提示版本
提示改为“先分析超时，再提候选”如果用于候选生成，会改变 I下一轮候选生成是否由新版本执行
保存过去的错误可能只是记录，也可能进入 S 或 I谁读取、在什么阶段读取、是否改变决策
替换文件系统 Provider改变执行环境及可用操作对照组是否仍共享相同环境条件

实验配置据此划定可修改的路径或字段，并固定作为比较条件的模型配置、任务集、计账器和评分规则。研究评分规则本身时，需要另外建立共同标准，否则候选与答案表同时变化，通过率便无法归因于能力改进。

候选、修改者与运行的独立身份

工作目录不断变化时，“v2”没有确定含义；固定 commit 能解决部分内容身份，却没固定提示词、依赖、模型、任务快照与运行参数。最小记录先区分候选、修改者和运行：同一候选可运行多次，同一修改者可产生多个候选，每次运行绑定实际加载的制品。第一章使用不可变 dataclass；真实代码可用提交、制品摘要或镜像标识。摘要帮助核对内容，不替代可信来源、隔离或正确性。

候选记录结构示例
{
  "candidate_id": "candidate-017",
  "parent_id": "candidate-009",
  "artifact_digest": "sha256:...",
  "improver_id": "improver-003",
  "proposal": "reduce search scope after repeated timeout",
  "development_run_ids": ["run-108", "run-109"],
  "decision": "archive",
  "decision_reason": "valid candidate; confirmation not run"
}

parent_id 表示改的是哪个起点，improver_id 表示谁生成修改。二者必须分开，否则无法区分“好起点容易改”和“修改者变强”。运行记录还要指向实际评分器版本、任务集标识和配置快照；只保存结论字符串，之后无法追查分数变动是哪个条件造成的。

candidate-009 是被修改的解题起点，improver-003 是做出修改的策略。若一个强起点由弱修改者处理，另一个弱起点由强修改者处理，只比较子代分数无法分辨两者的贡献。候选关系图保存父子边，运行账本保存观测；单一版本树难以表达同一候选多次运行、同一改进器跨起点工作的关系。

候选、运行、证据与决策的关联
candidate-017 ← parent=candidate-009, generated_by=improver-003
run-108       → candidate-017, task=issue-042, snapshot=repo-a
                model=model-revision-a, config=config-a
                runner=runner-a, grader=grader-a, budget=120s
evidence-108  → run-108, tool-events, patch, exit-status, observed-state
cost-108      → run-108, generation + execution + verification
decision-017  → frozen candidate + complete run set + protocol revision

这些 a 后缀是示意标识，落地时应替换为可解析的不可变版本或完整配置快照。若模型服务只提供会漂移的别名，应记录可获得的响应元数据与运行日期，并明确无法保证逐字重放；不能凭一个本地 hash 声称远程模型也被固定。

完整任务清单与可信观测

运行记录包含三类信息。行为轨迹记录候选读取、调用和写入了什么；外部观测记录断言、产物、退出状态、超时与拒绝；成本记录模型调用、token、CPU 时间、墙钟时间与验证费用。这些信息用 run ID 关联，并注明生产者。Agent 自述“已经修复”只是待评估的输出，执行端观测才提供对应的运行事实。

假设预排 12 个任务，收到 10 份产物，另外 2 次超时。若 10 份全部通过，任务完成率也是 10/12=83.3%，不是 100%。如果有 1 份产物未过断言，就是 9/12=75%。这两个数是手算情形，不是仓库运行结果。执行端应保留 12 条终态记录；超时没有输出可以判未完成，结果整条丢失则先暴露账本完整性问题，不能假装已获得可信观测。候选若可写 passed 列，必须先修权限，再讨论统计。

RepoOps 当前的规则代理与 SQLite 结果存储可以展示这些关联；它们不执行任意自生成代码，也不是一个现成的安全沙箱。接入候选执行时还需处理进程超时、任务目录、凭据和网络边界。仅把评分器放进另一个 Python 模块，候选仍可能读取或覆盖它。

搜索入档与发布采用不同准入条件

candidate-017 能启动、能继续生成补丁，却尚未完成独立确认，此时可以进入搜索档案而不发布。开发数据服务于继续搜索，确认数据检验冻结的终选候选；若每产生一版就读取确认结果并修正策略，确认集便参与了选择。因此，控制流分别保存搜索档案与当前发布版本，避免用一个 current 指针混合表示两种状态。

开发搜索与独立确认的控制流伪代码
candidate = propose(parent, improver, development_feedback)
artifact = freeze(candidate)
observations = run_development(artifact, fixed_runner)
ledger.append(artifact, observations, full_cost)

if valid_for_further_search(observations):
    archive.add(artifact)  # 不要求超过当前发布版本

# 在预先约定的终选时点才执行：
selected = choose_using_development_only(archive)
confirmation = confirm(selected, incumbent, locked_protocol)
if confirmation.decision == "keep":
    incumbent = selected

valid_for_further_search 可以检查候选能否启动、接口是否满足约定、能否继续生成候选，这些条件并不要求任务表现已经提高。发布决策 keep 则要求满足预先规定的质量、成本与关键错误约束。数据不足时，inconclusive 保留这一不确定性，当前发布版本保持不变。

发布还有两个需要协调的状态：确认决策与实际激活版本。若确认通过后，进程在更新发布指针前退出，重启后需检查实际激活状态，以幂等操作重试；决策本身须绑定候选摘要与协议版本。反过来，若指针已改成 candidate-018，迟到的 017 确认结果不能无条件覆盖它。发布端还需校验预期现任版本，再决定是否重评；上述伪代码仅表达搜索与发布的分离，未展开这部分并发控制。

恢复范围包括代码之外的状态

一种故障注入方式是让 017 先向记忆写入 issue-042 → skip-tests，再使任务失败。若只将代码指针指回 009，后续任务仍可能读取这条错误记忆。版本回退恢复了代码选择，数据库、检索索引、后台进程和外部资源却可能保持新状态。恢复检查因此需要比较前后的状态清单，并重跑会读取该记忆的任务，单看回滚函数的返回值无法发现残留影响。

对离线仓库任务，从相同快照创建独立工作区，结束后销毁，通常比设计任意逆补丁更可靠。知识助手还要固定索引与记忆命名空间，否则新版暖缓存、旧版冷缓存会污染对照。对退款、邮件等真实操作，销毁目录也撤不回副作用，需要事务、幂等键、补偿或事前审批；补偿不是时间倒流，已发送邮件通常只能追加更正。05 将按这些状态与权限约束选择载体，而不是按热加载速度排名。

从运行记录重建实验结论

完整记录允许从 candidate-017 沿 parent 与 improver 还原修改来源，再找到所有预排运行及其终态。每条 run 关联真实补丁、可信断言与成本，决策记录说明候选入档或发布的原因。错误记忆的故障注入则检验运行结束后的状态是否会泄漏到下一次离线任务。缺失的关系若只能靠事后口述补全，就无法独立重建实验过程。

可追踪性是比较递归收益的基础，但不直接证明收益存在。检验 I₁ 仍需让 I₀ 与 I₁ 从同一批起点分别完成搜索，保留候选序列、失败、成本和终选结果。让 I₁ 从 I₀ 的末代接力，再比较末代成绩，会混入起点与累计预算优势。第一章的两层 trace 在有限空间中实现了这种比较；RepoOps 扩展可以先将改动范围限制在少量检索或提示参数，使搜索过程和记录关系保持可检查。

账本中的分母与提升幅度

旧版 5/10、新版 6/10，对应增加 10 个百分点或相对提升 20%。还原这两个比例需要相同任务、起点、冻结时点和评分器，以及完整的超时、重试与训练成本记录。删掉超时、只给新版补跑或漏计训练开销，都会改变比较含义。小样本不确定性的处理见 04 与 R3。
