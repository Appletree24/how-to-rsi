检索证据在排序与上下文中的流失

同一个 E_CONN_POOL 故障，v1 手册要求回滚，正在运行的 v2 手册要求扩容连接池。把候选数从 2 扩到 4，正确手册终于被召回，答案却仍是回滚。候选集合、排序、上下文与答案分别处于不同边界；沿这条链追踪证据，才能区分漏召回、预算裁剪与读取策略造成的错误。

问题范围与参考材料

切块与重叠、Lost in the Middle、检索和生成的分阶段评估，以及短期与长期记忆，是 RAG 系统中相互关联的问题。Datawhale 的公开整理在固定 commit 203e9fac 的第 5 节第 3、6、7 题和第 4 节第 4 题列出了这些主题；其来源说明为作者备战 2025 秋招的个人面试经历，未经企业确认。

本文通过版本冲突、oracle 对照、权限与缓存分析这些机制。技术依据包括 Corpus.search / RulePolicy、本章独立的确定性实验及所引官方文档；实验不调用语言模型。以下项目推演不属于上述面试记录或官方答案。

不同项目中的检索对象

知识助手需要找到当前权限与运行版本下足以支持建议的资料；仓库修复器需要固定代码快照中的实现、测试与调用约束；评测平台则依靠不可变 artifact 定位某次失败。三者可以共享证据 ID、修订和来源记录，但“相关”必须由具体任务定义。语义近邻不能替代实验主键，相似仓库也不能提供当前工作目录的事实。

目标检索契约错误的检索范围
知识助手查运行手册租户/角色、部署版本、事件时点、原文引用与拒答条件未确认索引可见范围就把全部文档送外部 reranker
仓库修复查代码repo+commit+path+源码范围；精确符号、相关测试与依赖约束把相似仓库的同名函数当当前环境证据，或把隐藏测试答案加入检索

资料少、授权一致且能完整放入窗口时，完整上下文是合理基线，它避免了漏召回。资料增长或权限不同时，按需检索可以降低输入成本、缩小暴露面，同时引入排序与裁剪风险。两种方案需要固定用户可见资料、模型和生成预算，再比较端到端正确性与延迟。

证据相关性的操作定义

输入固定为：service=checkout, error=E_CONN_POOL, runtime=v2, role=operator。任务要求给出动作，并同时引用故障记录与适用于运行版本的手册。金标证据集合是 G={incident@1, runbook@2}；旧手册即使逐字包含错误码，也不是当前任务的正确操作依据。

证据单元脚本中的完整文本适用范围 / 成本
incident@1checkout E_CONN_POOL runtime=v2 incident故障事实；operator 可读；4 单位
runbook@1checkout E_CONN_POOL action=rollback revision=v1仅 v1 规则；operator 可读；4 单位
runbook@2checkout E_CONN_POOL action=expand_pool revision=v2仅 v2 规则；operator 可读；4 单位
latency@1checkout latency investigate other主题相近但无所需规则；4 单位

实验注入固定候选顺序：incident@1 → runbook@1 → runbook@2 → latency@1，不经过 embedding 模型。上下文预算为 8 个空白分隔词，每个单元完整装入，放不下就跳过，因此前两条占满预算。真实模型接入时需改用目标 tokenizer，并从窗口扣除 system、问题、工具协议、历史与预留输出；这里的 8 仅是夹具的计数单位。

词匹配基线的限制

Corpus.search 用小写英文词的集合重合数排序，最多返回 5 个标题；它不是 BM25，也没有中文分词或语义理解。英文教学夹具让机制清晰；改成中文工单、缩写和自然语言后，必须先测词法分词与同义词的影响。

从词匹配到混合检索

混合检索首先需要稳定的证据标识。输出可包含 doc_id, revision, chunk_id, score, source，并关联服务、适用版本、有效期与访问策略。引用映射到不可变文档版本和原文范围，重新分块后仍保留旧版本映射。授权信息由可信边界校验，不直接作为用户可见结果返回。

词法支路可接入 BM25，并保留现有词匹配作为基线；错误码、路径和函数名是精确匹配的重要对象。向量支路则固定 embedding 模型、归一化方法与语料 hash，在同一任务和候选池上比较词法、向量与融合结果。这样能将检索器变化与数据变化分开。

RRF 通过名次融合两路结果：每个排序贡献 1/(c+rank)，名次从 1 起，平滑常数 c 与候选数 k 分开命名，并在开发集固定。它避免直接相加不可比的词法和向量分数。Elastic 官方 RRF 文档给出公式与候选窗口裁剪行为（2026-09-20 版本范围）。融合之后的重排只处理前 m 条，参数选择需要同时观察开发选择集表现、延迟与调用量。

例如证据 A 在两路排序中的名次为 1、4，B 为 2、2，取 c=60，则 A 得 1/61+1/64≈0.03202，B 得 2/62≈0.03226，B 略高。这是公式推导，不是最佳参数测量。某证据若在一路候选窗口外，该路没有贡献；两路都遗漏的证据也不会因融合出现。两个检索器若共同偏爱旧手册，排序共识反而会强化错误，版本与权限仍须单独约束。

上下文组装根据证据相关性、文档有效期和 token 预算选择内容，同时保留任务目标、已读证据 ID 与待验证假设。压缩可能降低长度，也可能删掉错误码、否定词或适用条件，所以最终送入的内容仍需独立测量。

候选指标与任务指标

问题测量诊断实验

分层定位证据丢失

召回率与上下文覆盖率

候选集合 C 的 Recall@k=|G∩C|/|G|；送入生成器的上下文集合 H 则有 Coverage=|G∩H|/|G|。二者分母相同、边界不同。金标包含版本和访问范围；将 v1/v2 都标成相关，会奖励错误规则。多证据任务还需统计 G⊆H 的全覆盖率，因为平均覆盖率可能掩盖一条缺失的关键前提。

扩大候选可能让旧规则、重复块或长文挤走当前证据，也可能在证据完整时增加冲突。本章实验中 Recall 从 0.5 升到 1，答案仍然错误，展示了召回改善无法自动传递到最终结果的机制；它没有测得成功率下降。上下文覆盖不变而答案变差时，顺序、干扰和读取规则才是进一步对照的对象。

真实掉分需要在同一批有金标的任务上，固定模型、提示词、生成预算与语料快照，逐任务比较候选、上下文和答案。单列原来正确、改动后错误的样本，并观察新增证据是否改变上下文、拒答和引用支持，才能判断改动影响了哪个环节。

Oracle 对照的干预边界

直接给生成器理想上下文，会同时绕过召回、排序与裁剪。回答恢复正确只能说明这条样本在理想证据下可答，无法单独定位某一级故障，也不能代表所有分布上的性能上界。不同 oracle 的解释取决于它替换了哪个边界。

干预固定什么 / 替换什么能得出的结论与反例
候选 oracle补入遗漏金标，保持候选总数与后续规则，明确替换掉哪条新增证据若仍被预算裁掉，答案不变不能说明召回无用；先看它是否进入上下文。
排序 oracle同一个候选集合，将已存在的金标前置；预算、组装、消费者不变若修复，排序与预算交互足以解释此例；尚未证明某个真实 reranker 能学会这种排序。
上下文 oracle候选和原排序不变，绕过组装，直接给满足预算的完整金标若修复，上游上下文是可修复因素；若仍错，应先核对金标充分性、提示模板和消费者，而非立刻归因模型能力。
生成端对照保存逐字相同的上下文，换读取策略；真实模型需固定配置并重复采样规则程序正确不等于 LLM 正确；真实模型能复述不等于能正确应用版本条件。

干预必须保持预算，且不能把答案动作直接加入 prompt。脚本中的 rank_oracle 保留候选池，context_oracle 保留原排序，二者均使用 8 单位预算；只有诊断和评分读取金标，正常版本过滤不读取金标。

重排的适用条件

重排有效的前提是所需证据已经进入前 m 条，输入包含可区分它们的版本、时间或正文，并且预算容得下必要证据。相关块排第 51、重排只看前 50 时，更大的重排模型也无法处理它；两个版本若只截到相同标题，同样缺少判别依据。

权限和版本兼容属于硬约束。需要 v2 的请求应排除仅适用 v1 的操作规则；历史复盘则按事件时点和部署版本取证，不能一律取最新。适用版本不明时，需要补查部署事实或拒答，文档发布日期无法确定实际环境。

增大 m 会增加要评分的 query-document 对；长块截断还可能删去否定词或适用条件。比较不重排、现有重排与排序 oracle 时，固定授权候选池和 token 预算，分别统计覆盖、冲突率、端到端正确率及 p50/p95 延迟。RRF 融合召回名次，cross-encoder 式重排在候选内进行细粒度判断，两者都无法补回缺失证据。

权限过滤与版本过滤的位置

权限先于不可信边界，不能只在答案后处理。可信检索层在取 top-k 前按租户和角色限定可见集合；不可见正文、标题、摘要和标识都不送给用户、外部 reranker、模型或共享日志。单文档 read 也必须独立鉴权，不能因为它有一个猜得到的 doc_id 就返回正文。真实系统若只能先取 ANN 候选再过滤，应在可信服务内部完成并按预算补取，禁止泄漏过滤前结果；“最终删掉答案里的秘密”不能撤回已经发给模型的数据。

过滤时机也影响召回。如果前 k 个都是其他租户或不兼容版本，先截断再过滤会留下空集，即使后面存在有效证据。支持元数据预过滤的索引更直接；不支持时需要度量补取成本与剩余覆盖。版本约束与权限都应在使用缓存/读文档时再校验：索引快照正确，不意味着发出响应时仍被授权。

本章脚本把检索函数视为可信边界：权限过滤先于 top-k，修复组再加运行版本过滤；上下文消费者完全不变。它验证了这条数据流上的不泄漏，并没有实现身份认证、租户隔离基础设施、并发撤权或侧信道防护。

接入 starter 的替换边界

本章脚本使用 E_CONN_POOL / expand_pool，starter 使用 POOL_EXHAUSTED / resize_pool；它们是两个独立夹具，不能把一边的动作直接写入另一边的金标。将真实检索接到 starter 时，先保持 search 返回 ID/标题、read 才提供正文的行为，再明确扩展 revision 与源码范围的协议。否则“换检索器”同时让模型直接看到更多正文，就无法判断改进来自召回还是信息量变化。

接入实验可选取版本冲突、精确错误码、自然语言改写和无答案的独立开发例，绑定语料快照与授权范围。每次保存候选及排序、预算后实际送入的证据、最终引用三份轨迹，并区分授权过滤、版本过滤、去重与截断。敏感原文仅进入受控审计存储，观测链路同样受 ACL 约束。

词法索引、向量融合与重排逐项替换，沿用同一生成器和上下文预算，分别对比原基线与同预算 oracle，并记录索引构建、embedding 和重排成本。若正确证据已送达却被忽略，改动应落在条件表达或读取策略；若预算装不下必要证据，需调整组装或任务协议，增加候选数无法解决这一限制。

服务级实验还需覆盖索引发布中途、权限撤销、文档删除和 commit 切换。旧快照用于重现历史，在线响应则服从当前授权；长期保存历史与永久复用缓存是两回事。这些接入与压测属于后续设计，前述单例实验不覆盖这些服务状态变化。

记忆的版本与可见范围

短期状态保存当前任务、已经验证的事实和待办；长期记忆保存经验证的通用经验，不写入确认题答案。给 memory 记录来源、适用范围、创建时的代码/模型版本和有效期。运行测试任务时冻结记忆快照；禁止把 test_public 的评分结果回灌，再声称下一次是独立测试。

一种简单的存储形式是 memory.json：{id, claim, evidence_ids, scope, revision}。读取前校验 scope，可以用 billing 的修复经验误用于 checkout 构造失败例。若进一步拆分 Planner/Executor，额外调用和上下文也计入预算，才能与单 Agent 的瓶颈进行比较。

缓存依赖与撤权

query→候选 ID、候选→重排结果、证据→摘要、完整 prompt→答案这几层缓存具有不同的失效依赖。只用 query 文本作 key，会让相同问题跨租户、角色、运行版本或语料快照复用。以下讨论缓存的服务设计，前述脚本的内存权限自检不覆盖缓存撤权。

  1. 固定可解释的键。检索键至少包含查询及过滤条件、租户/授权范围指纹、ACL 版本、运行版本/事件时点、索引快照、分块与 embedding 版本；重排再绑定模型版本；答案缓存再绑定证据版本集合、模板、生成配置。可按层引用上游键，不必把一切重复存到每层。
  2. 按依赖失效而非只等 TTL。v2 手册纠错为 v2 的新修订时，运行版本没变，但不可变 revision 和语料快照应变；依赖旧修订的摘要、记忆和答案一并失效。空结果缓存也要随索引发布失效，否则补入正确手册后仍持续拒答。TTL 只能限制陈旧时间，不能承担立即撤权的安全语义。
  3. 响应前再授权。用户从 security 降为 operator 后，即使命中旧缓存，也必须按当前权限重验所有引用；失败则丢弃整个派生答案并重算，而不是只隐藏链接，正文可能已经复述秘密。若没有可靠的当前授权信息，敏感答案应关闭共享缓存或拒绝返回。
  4. 复现竞态。设计验收顺序：旧修订填充缓存 → 发布新修订 → 同问题必须命中新修订或显式失效重算；高权限填充缓存 → 撤权 → 同问题不得返回旧文或派生摘要。异步失效还需用 ACL 代际/响应前校验封住“事件尚未传播”的窗口。此顺序需要真实缓存与授权服务验证，不能用本章内存夹具代替。

长期记忆本质上也是派生证据：不能把“遇到连接池错误就回滚”保存成无条件经验。应保存“在 checkout 的 v1、满足指定症状时按某修订手册回滚”，并保留可重新验证的引用。把多份记忆压缩为一段摘要若丢了条件，就是又一次上下文组装失败，而不只是检索问题。

预算与干扰的单变量实验

在脚本副本中将预算从 8 改为 4，必要证据无法同时装入，预期应拒答，自检也会报告不再满足原夹具的修复预期。将另一条 v2 干扰块排到新手册前，可以观察版本过滤的局限。预算扩大到 12 时，原排序会同时装入新旧手册，但第一规则策略仍选择旧动作：上下文全覆盖后，读取策略仍可能失败。

真实检索接入后，可比较现有词匹配、升级检索和同预算 oracle 三组结果。每个失败例保存候选 ID、不可变 revision、排序、删除原因、最终证据原文与答案引用，按旧版本冲突、证据不足、跨权限和无答案分类。固定语料及记忆快照、记录端到端成本，再用单变量干预检查证据在哪个边界丢失、错误是否随干预消失。
