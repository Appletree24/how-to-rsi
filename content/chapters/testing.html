测试设计：最小反例与真实执行路径

PR 中的测试全部通过，应用启动后却找不到工具。如果故障发生在包加载阶段，增加 execute 单测也无法覆盖它；一个经过真实 Loader 的用例反而可能直接复现问题。测试的价值取决于它保留了哪段因果链。覆盖率记录代码是否执行过，而测试入口决定了哪些装配错误有机会暴露。

历史案例与实验范围保留的 DSH postmortem 0001 摘要记载了“178 个单测全绿、100% 行覆盖，真实 Loader 仍失败”的案例。该摘要未绑定上游 commit，事故也未在此复现；数字仅作历史线索。下文 Loader、快照与门禁名称按历史接口讨论，具体行为以目标版本为准。实验部分描述测试设计，不包含 DSH 或 RepoOps 的运行结果。

从可见故障定位测试入口

设 profile 应提供一个只读工具 read。测试直接导入插件实现并调用 ctx.plugin()，随后断言 read 能返回文本。真实应用先解析包入口、处理 exports、建立 inject 拓扑、选择 isolate realm、计算 disabled，再注册工具。如果包导出形状不符合 Loader 约定，单测完全可以通过；它从失败点后面才开始执行。

最小反例的构造：示意，不是现成 DSH 测试代码
输入：一个 profile + 一个工具插件 + 必要 Provider + 固定模型请求
单测捷径：直接导入 apply → 手工注册 → 调用 read → 得到内容
真实路径：包入口 → Loader 导出解析 → inject → 工具注册 → 调用 read
故障注入：只改变包入口导出形状，不改 apply / execute
可观察断言：应用启动失败，或模型可用工具面缺失；不能被当作成功会话
修复后：同一路径启动，固定请求得到预期文本并进入持久结果

工具是否可用、返回什么、是否落账，都是消费者可观察的结果。Loader 决定工具如何进入应用，因此最小反例虽然只保留一个工具与必要依赖、去掉网络和无关 UI，仍需经过真实包加载。如果 mock 掉 Loader，导致故障的入口解析也随之消失。

三种验证层次的覆盖范围

包内单元测试

用 vitest 或同层测试检查纯转换、明确的错误和局部状态转移。手工 ctx.plugin() 可以覆盖服务与事件行为，但通常不经过包入口解析、注入拓扑和真实 realm。它适合检查最小输入到输出的关系，完整装配需要另外覆盖。

会话快照回放

历史 snapshots/session、sdk、acp、web 用录制输入与模型响应驱动回放。它验证固定轨迹下的模型可见、持久或用户可见结果；是否覆盖真实 Loader，要看具体回放入口。固定模型响应不证明新提示词在真实模型上仍能成功。

真实组合与进程验证

以测试 profile 经 Loader 启动真实应用或子进程，只替换外部、非确定性输入。无密钥可验证启动、注册和固定响应链路；真实模型调用另设有密钥场景。跳过模型测试不是这些测试已经通过。

局部确定性错误适合放在能够复现它的最小层；包边界和进程生命周期则需要保留真实组合。跨进程缺陷也可能被一个窄集成测试捕获，目录是否名为 e2e 并不决定覆盖范围。模型质量另需固定任务、独立评估与预算对照，无密钥回放只能说明固定输入轨迹下的系统行为。

用最小反例检验不变量

“函数不抛错”“列表非空”“注册调用了三次”可能只说明测试环境已经搭好，却没有约束消费者得到的结果。一个有用的不变量应对应具体的破坏方式。下面各行分别给出一条承诺及其最小反例，可以独立运行并定位失败。

不变量最小反例输入 / 顺序证据与断言
被拒绝的操作不产生目标副作用一个写请求，守卫拒绝；再让后续监听器尝试允许明确拒绝结果，目标文件摘要不变；不能只看守卫返回值
已完成卸载的作用域不再发布新结果启动任务 → 卸载 → 延迟完成通知进程实际退出，结果流不新增；仅断言 abort 被调用不够
模型可见上下文可由日志重建一次用户输入、一次工具结果，再从持久日志恢复按契约投影的请求内容一致；不拿运行时临时字段硬做全文相等
评测器拒绝未知或无效候选状态候选返回 UNKNOWN_TOOL 或缺少测试产物明确无效状态且不记成功分；不能录成新的成功基准
超时与退出码是正交事实进程超时后处理终止请求，以 0 退出仍报告超时并保留 exitCode=0，不能折叠成普通成功

卸载用例需要控制的是完成通知与卸载的先后关系。可控的完成屏障能在卸载后释放迟到结果；真实进程退出则由它的完成信号确认，并设置等待上限。这样无需假设某台 CI 机器能在 100 毫秒内完成调度。随机任务还需要保存 seed 与原始输入，失败后将轨迹缩减到最少事件；一次重跑通过无法解释原来的失败。

Harness 故障注入：固定模型脚本，打断真实执行边界

脚本化模型的替换边界这里的模型适配器按测试指令输出流片段、完整动作或断连；流解析、权限门、调用去重、上下文构造和终态提交仍使用待测实现。这样可以控制故障时序并检查执行可靠性，真实模型能否选对工具则留给模型评测。

实验为一个 run 设置流读取屏障、工具完成屏障和终态提交屏障，通过事件推进顺序。观察窗口覆盖取消后的迟到回调，同时记录消费者看到的结果、持久调用状态、模型下一轮实际收到的请求，以及目标资源的最终状态。这些观察不依赖内部类名、队列结构或回调数量，内部实现替换后仍可沿用。

注入点与受控时序消费者可观察的不变量最小验收证据 / 反例
流中断：先输出半段工具参数，再断连；另一条轨迹在完整动作已经派发后、结果返回前断连未完成且未经严格解析的参数绝不执行；已派发动作不能因断连被当成“从未执行”而盲目重放。恢复后同一调用只有一个被接受的最终结果；无法确认外部结果时明确保持待对账状态，而非伪装成功前一条目标计数仍为 0，后续请求不含伪造 tool result；后一条释放工具屏障后检查调用账本与目标回执。不支持恢复的版本应显式终止并保留未决调用，不把截断 JSON 自动补成可执行动作
重复 tool call：重放相同 run / call ID 与参数；再用同一 ID 携带不同参数；补一条相同参数但不同 ID 的独立调用同 ID 同参数复用已有状态或结果，不产生第二次副作用；同 ID 异参数明确冲突，不覆盖旧记录。不同 ID 不能仅因参数相同被误判为重放，仍按独立动作与权限策略处理以隔离的计数工具及操作回执观察副作用次数，不断言 execute 调用次数。进程在外部提交后崩溃的场景需要接收端幂等键或对账；本地去重表不构成跨系统 exactly-once 保证
cancel race：分别把取消放在派发前、工具运行中，以及完成结果提交之后；在取消提交后释放迟到的工具和模型回调取消与完成由同一权威提交点排序，终态只能接受一次。取消先提交则不得再派发新动作，迟到结果不能把 cancelled 翻回 ok；完成先提交则保留完成事实，取消返回已终止。取消请求不等于外部动作已经撤销检查结果流和持久终态一致、取消后无新操作回执。运行中的工具即使退出，也须保留取消前已发生的副作用及待结算费用；不能用“收到 abort”代替退出或停止证据
压缩后权限 / 证据丢失：让摘要遗漏拒绝记录与引用版本，甚至写入“用户已授权”；压缩后再撤销真实 ACL，并请求读取或引用旧资料摘要不是权限源：每次执行仍查当前授权；证据引用只能解析到已记录且仍允许使用的来源版本，正文缺失时按策略重新取证或明确证据不足。不能从摘要文字重建授权、read_ids 或未读过的引文检查拒绝后的资源状态、下轮实际模型请求与最终可见引用。保留证据时应能定位来源与版本；权限撤销后不得把历史正文再次注入模型。若压缩无法保留最低证据契约，运行应降级或停止，不能无证据地继续 finish

恢复包含两个独立条件：系统仍能辨认中断前可能已经发生的动作，也仍有权继续执行。前者需要稳定调用身份和可对账记录，后者需要独立的权威权限状态。完整对话记录既不能保证外部副作用只发生一次，也不能使旧授权永久有效。故障脚本需要分别破坏这两个条件，覆盖动作状态丢失与授权过期两条路径。

每类故障的复现材料包括输入脚本、屏障释放顺序、预期不变量与实际观察。同一条轨迹在缺少对应防护时应能暴露故障，在修复后则满足原有契约。如果实验只有进程内回放，其覆盖范围不包括进程崩溃与真实外部工具。这些确定性测试对应 P2 的 Harness 责任划分；模型质量与消融见 P7，两者分别衡量执行可靠性与策略效果。

快照差异与行为契约

快照变化可能来自有意的契约调整，也可能来自故障。例如 UNKNOWN_TOOL 从错误变成一段固定文本，直接更新快照会把断开的工具链固化为预期。历史 dsh-session-snapshot 对这类结果设拒绝门禁，防止将坏运行录成标准答案。门禁只覆盖它识别的错误，其他差异仍需结合行为契约审查。

对比时需要区分允许变化的字段与必须保持的行为。运行标识可以按契约规范化，模型输入、工具结果和审批决定则可能影响真实语义。将错误文本、调用顺序和退出码一并抹去，会让快照失去发现回归的能力。绑定旧实现细节的断言也需要替换为可观察行为断言，而非逐字接受所有新输出。

静态门禁与运行验证

历史 scripts/ 中的 verify / gen 家族把约定转成可执行约束：verify-application-entrypoints 检查入口分类，避免绕开 CLI + profile；verify-cordis-config 限制表达式出现位置，历史规则只允许在 config / disabled 使用 !!js；gen-doc-graphs 生成事件生产/消费图并核对 JSDoc @mode；benchmarks 提供性能检查入口。

结构门禁检查声明与规定形状是否一致，组合验证观察实际输入下的行为。声明正确的系统仍可能死锁，快照稳定的运行仍可能超预算。性能检查还需要固定环境、工作负载、并发和测量口径，才能区分实现变化与测量波动。

Loader 故障的回归实验

以导出问题为例，固定目标版本与 profile，让一个工具调用经过真实 Loader；比较修复前后的模型可见结果与持久结果，并记录外部模型是否由回放替代。错误导出形状可以保留为回归输入，确保后续变更仍能识别装配失败。执行 pnpm run test:snapshot 或 pnpm run test:e2e 时，脚本定义、过滤方式与无密钥跳过范围均以目标 DSH 版本为准；这两个历史命令不属于本站前端测试流程。
