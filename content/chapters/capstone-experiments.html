RepoOps / P7 · 实验判断

固定预算下的版本比较与 Harness 消融

假设知识助手误用旧手册，增加一次证据检查后，开发集得分上涨。这个变化可能来自更好的证据使用，也可能只是更多调用或对开发样本的适配。实验需要分别估计效果、成本与退化范围，才能判断这项修复是否值得采用。

处理变量与决策指标

本文以“是否启用结构化证据检查”为处理变量，模型、检索和其他 prompt 内容保持固定。知识助手的成功契约是答案及证据正确；仓库修复器要求允许范围内的 patch 在独立环境通过行为验证；评测平台保证试验完整、可归因、可追溯。运行完成、答案正确和修复生效是三个不同层次的结果，需要各自的判定依据。

用 实验卡 预先写清主指标、最小有意义收益、成本上限、严重违规、停止规则、基础设施排除规则与最终确认方法。两组共享模型修订、任务、工具、环境、grader 与最大调用/时间预算，只改变证据检查策略。若确实更换模型，就把结论命名为模型或组合系统比较，不把差异归到 harness 上。

RepoOps 已能保存两组不可变配置及逐题报告；随机交错、Harness 组件切换、聚类推断与密封确认协议仍是下文的实验设计。全部 12 个任务均为公开教学夹具，包括 test_public。规则策略不读取 prompt，因此提示词与模型效果比较需要固定修订的真实模型，公开夹具也不能承担秘密确认集的角色。

配对、执行顺序与补跑规则

给每道题同时分配 A/B，随机或交错执行顺序，避免把早晨稳定的服务全部分给 A、晚间限流全部分给 B。共享种子可帮助控制某些本地随机性，但 provider 未必保证确定性；配对的核心是同一任务、相同可见信息与资源约束，而不是声称同一个 seed 使两次输出相同。

预算先固定上限，再记录实际消耗。B 在 6 次调用上限内用满额度、A 只用 3 次，并不违反上限公平，但“同上限更高成功率”不等于“同实际成本更有效”。应同时报告成功率、实际 token/费用/墙钟时间与成本约束；若问题是资源效率，还应比较预算—效果曲线。B 的证据检查或 judge 请求必须算账，不能藏在“评估开销”之外。

服务超时后的补跑遵循预注册规则，原失败与新增 attempt 的成本都保留在账本中，主要分析明确二者如何计入。根据已看到的答案决定剔除，会改变比较口径。若一组发生系统性配置错误，则需中断诊断、修正配置并重新冻结协议；失配运行反映的是实验故障。

固定模型下的 Harness 消融矩阵

开发阶段的消融设计以下矩阵先比较单组件，再检查组合效果；表中没有测量结果。运行前需实现对应候选、冻结配置，并保留每行的变更集。

把 Harness 配置拆成 P（提示词）、T（工具接口）和 C（上下文策略），模型 M、数据与执行环境单独锁定。P 只改变任务指令和取证要求，不改变工具参数；T 只把相同工具能力的参数约束与错误结果变得明确，不偷偷增加检索覆盖或 ACL；C 只改变观察的保留、压缩与回取策略，不能加入基线无法访问的新资料。T 的收益可以来自更少的协议错误，C 的收益可以来自更少的证据丢失，都不等于模型权重变强。

实验行固定模型与可变项预先声明的对比必须保存的解释材料
A · 基线M0 / P0 / T0 / C0所有候选的共同参考原始失败类型、逐题消耗、实际输入与工具观察
B · 只改提示词M0 / P1 / T0 / C0B−A：取证指令改变是否有收益prompt 差异及哈希；增加的输入 token 也计入预算
C · 只改工具接口M0 / P0 / T1 / C0C−A：等能力接口是否减少非法动作与错误恢复成本参数 / 返回错误契约差异；资源范围和底层检索结果保持不变
D · 只改上下文策略M0 / P0 / T0 / C1D−A：证据保留 / 压缩是否改善长轨迹压缩前后请求、来源指针、回取次数和额外模型调用
E · 组合候选M0 / P1 / T1 / C1E−A：组合效果；与 B/C/D 对照识别潜在依赖，不能把差值直接相加各组件开关、组合退化轨迹、所有辅助消耗
F · 模型对照，另立问题M1 / P0 / T0 / C0F−A：固定 Harness 的模型替换，不计入 Harness 改进结论模型修订、服务配置和价格差异；不能拿 F 的收益填给 E

该矩阵缺少 P1/T1/C0 等二因素组合，无法识别所有交互。若 E 有效而单项都无效，只能提出“存在组合依赖”的假设，尚不能确定是哪两个模块协同。后续可追加二因素行，或从 E 每次去掉一个组件；这些新增选择仍属于开发探索，需要另行确认。预算有限时，单个明确组件的对照通常比覆盖不全的因果分解更容易解释。

预算向量与全量资源账本

max_steps 只约束部分开销。每次 trial 的预算向量还包括模型请求数、累计输入 / 输出 token、工具派发数、工具结果字节上限、墙钟 deadline 与费用上限；P/T/C 变化共享该向量。调用前按可知输入和最大输出预留，返回后结算。只能事后计量费用的适配器无法保证硬费用封顶。token 单位与费用可比性依赖 tokenizer、服务与计价口径，尤其 F 更换模型时需要单独说明。

压缩模型、格式修复、内部证据 judge、重试和失败请求只要参与候选决策，就进入该候选预算；独立最终 grader 不参与决策，保持两组相同并单列评测总成本。工具调用预算还应约束总输出量，避免把十次 read 合成一次超大批量请求来“节省调用”。若候选增加动作能力或批处理范围，就不再是等能力 T 消融，应另开实验。

报告同时回答“同上限能否多完成任务”和“同实际资源能否更有效”。前者保留所有被分配任务，含超限、超时与取消；后者使用预先固定的多个预算档位画预算—效果关系，不能事后只挑花费相近且成功的样本。未知 usage / 费用保留为未知，并按预注册规则标记成本裁决不可用；不补 0，不剔除它来制造廉价优势。

安全约束与候选选择偏差

所有行都应先经过 脚本化 Harness 故障门禁：未授权动作无目标副作用、重复调用不重复提交、取消后不复活、压缩不产生授权或伪造证据。相同故障脚本与评判规则适用于基线和候选；候选即使答案更准，只要出现预定严重违规也不得发布。如果基线也失败，应报告共同缺口，而不是降低门槛让新版本过关。模型任务中的越权、数据泄漏和隐藏答案访问还需独立安全检查；无密钥故障回放不能证明模型抗注入。

在 B/C/D/E 中挑最高分会产生选择偏差，即使每次只改一个因素也一样。开发矩阵用于选择和机制诊断，全部候选及失败历史都属于这段搜索过程；冻结候选后的独立配对确认才用于估计选中版本的效果。若同时确认多个候选，主比较和多重比较方法需事先确定。只报告反复调整 C 后的最高分，会遗漏选择过程带来的乐观偏差。

矩阵配置、逐行变更集、预定对比、共享预算向量与全部 trial 账本共同定义实验。单组件差值才能承担对应组件的归因；组合行用于估计整体效果。逐题轨迹中的实际请求和辅助成本则解释成功率差值来自哪里。减少协议错误、改善特定任务与提高一般模型能力是不同强度的结论，采用哪一种取决于测量覆盖范围。

统计单位：从重复运行到任务级差值

任务级配对 · 同仓库任务需在更高层聚类
d_i = mean_r(success_B[i,r]) - mean_r(success_A[i,r])
delta = mean_i(d_i)
bootstrap: 重采样独立的任务/家族，保留该簇内全部 A/B 配对和重复
成本约束: cost_B <= predetermined_ratio * cost_A
裁决: 严重违规或成本越界 → reject
      收益下界超过预定阈值 → keep
      否则 → inconclusive，保留原版本

考虑手算例，不是运行结果：任务 1 的 A 三次为 [1,0,0]，B 为 [1,1,0]，所以 d₁=1/3；任务 2 的 A 为 [1,1,1]，B 为 [1,0,1]，所以 d₂=−1/3；两题等权的 delta=0。只展示任务 1、只选 B 最好的那次，或把 12 次执行当作 12 道独立题，都会改变问题而非改善证据。

现在把两题改为来自同一个仓库、共享同一套手册。重复只能测模型/运行随机性，不能增加独立仓库数量。若目标是“随机抽一道任务的效果”，保持预设任务权重；若目标是“随机抽一个服务家族的效果”，先算家族内均值，再等权平均家族。两者在家族规模不同时不同，不能看到结果后挑较好的一种。bootstrap 应重采样独立家族并保持簇内配对，不能拆散 A/B，也不能靠大量重复制造窄区间。

labs/eval_lab.py 提供独立任务假设下的保守 Hoeffding 门和描述性 bootstrap，不会自动识别仓库相关性。当前 12 题仅来自 6 个服务家族，且是手工构造，不能据此对真实任务总体作独立同分布能力推断；很少的簇也会让 bootstrap 区间不稳定。此时展示全部家族差值与范围，比强行给一个“显著”标签更诚实。

候选冻结与独立确认

  1. pilot 只用于设计。在开发数据上发现格式问题、估计失败率、用量分布和方差，允许改方案；不要将这轮作为最终确认。
  2. 冻结可执行候选。保存模型实际修订、prompt、检索与 memory 内容哈希、工具配置、grader 和镜像。仅声明模型名字不足以排除服务端漂移。
  3. 隔离确认数据。最终任务、隐藏规则与答案不进入候选工具、优化器反馈或公开日志。公开 starter 仅支持流程演示，不满足这一保密条件。
  4. 运行并完整记账。每题 A/B、全部重复、失败、取消和重试都进入账本；缺失 trial 先标 partial，不从剩余题推导完整结论。
  5. 一次确认，按规则裁决。先给效应与区间，再 keep/reject/inconclusive。若看过最终集后改候选，该数据已经变成开发信息，需要新的外层确认，不能改个文件名继续声称独立。

根据“差一点显著”的中间结果继续加题，会使停止时机依赖观测结果。序贯检验可以处理这类设计，但检验方法和预算边界需要事先确定；反复查看普通区间后停止，已不再满足固定样本的错误率解释。P9 的反复候选选择还会增加一层适配，因此搜索与最终确认需要进一步分离。

有限资源下的研究范围

总预算分为 pilot、开发选择、最终确认和基础设施失败预留，比例取决于前期用量与方差。一个调用上限的手算是：20 题×2 组×3 次×每题最多 6 个模型调用=720 次，评分调用另算。美元预估来自 pilot 的输入/输出 token 分布与带日期的 provider 价格；离线策略没有真实 token 数据，只能报告实际可测的调用和时间。

预算只够少量家族时，研究范围可以限定为“在这些任务上证据检查是否改变错误类型”，并展示配对轨迹与成本。低代价地重复一千次也无法补足只有一个仓库的外部有效性：运行重复估计随机性，新增独立家族才扩大任务覆盖。

例如，成功率点估计提高，但成本增加且收益区间跨零，按原定规则仍可能保留旧版。这表示当前样本与预算不足以支持采用，并不能证明机制无效。即使收益下界超过门槛，结论也仍受任务来源、模型修订与预算限制；统计显著无法消除数据污染或错误评分。

重放与分析口径检查

在新目录按 README 重跑 pilot，将汇总数字追溯到 trial，再检查任务来源与候选选择历史。同仓库任务需要保留簇内配对并调整分析单位；参与过 prompt 选择的确认集已经提供开发信息，需要新的外层确认。重放验证运行过程，来源与访问记录验证推断前提，两者缺一不可。
