Cordis：依赖与插件生命周期

一个检索插件依赖数据库服务。重载配置时，如果数据库先关闭，旧工具可能仍在处理请求；如果只撤销注册，已经开始的调用又未必停止。依赖注入决定插件何时可以启动，生命周期管理还需要处理停止入口、收尾调用与释放依赖之间的顺序。

本章以 DeepSeek Harness 固定提交的 Cordis primer 及复盘为案例，讨论依赖注入与生命周期的通用问题。活动调用的 drain、取消与资源所有权是本文分析的设计责任；框架的可逆注册不涵盖任意异步任务或外部副作用回滚。示例省略导入、工具定义与类型细节，交互组件仅模拟分发规则。

服务可用期间的注册与调用

设工具消费者 C 需要服务 P。C 未激活时不应接单；P 可用后才能发布注册；停止时先关入口，再处理飞行中的调用，最后释放 P。服务键让 C 不依赖 P 的具体类，inject 表达所需服务，事件承载协作，effect/disposer 记录需要撤销的注册。五个概念都服务于这个时间窗口，而不是五种独立语法。

资源生命周期的两个约束接受新调用 ⇒ 依赖仍处于可用生命周期；释放依赖 ⇒ 已无依赖它的未收尾工作。撤销监听器只能关闭相应入口；连接、定时器、子进程和已经启动的 Promise 仍由资源拥有者管理。

一种实现是记录活动调用，在停止入口后 drain；另一种是取消所有活动调用再等退出。只等待可能永远不收敛，只发 AbortSignal 又可能遇到不合作的 I/O。若允许长任务跨重载存活，就得给旧依赖代际保留所有权，而不是把新 Provider 塞进旧对象。这是需要明确选择的产品语义，不能由 dispose 顺序碰运气决定。

模块导出形态会改变依赖注入

固定提交中的 事故复盘 0001 报告了一个入口路径问题：命名空间插件导出 name/inject/apply，但又添加 export default apply。复盘展示 Loader 的 exports.default ?? exports 归一化优先取得裸函数，同级的 inject 不再随模块命名空间传入。

函数插件的命名空间形态（教学骨架）
export const name = 'my-plugin'
export const inject = ['tools']
export interface Config { greeting: string }

export function apply(ctx: Context, config: Config) {
  // register 返回的 disposer 由这个 effect 持有；不代表工具副作用能撤销
  ctx.effect(() => ctx.tools.register(myTool))
}
// 不再添加 export default apply；Service 子类则采用其服务包约定

手工测试 ctx.plugin({ name, inject, apply }) 可以通过，因为它直接构造了正确对象，绕开了模块解包。这类测试覆盖插件本身，却没有覆盖发布入口。针对导出形态的检查需要从目标构建产物、实际 profile 和 Loader 启动，执行不需模型密钥的 session/new，再检查依赖是否激活。导入路径也需区分源码与旧 lib/，否则旧构建产物可能掩盖当前版本的问题。

同一复盘还记录了另一个服务查找错误：可选持久化服务在外来 shadow 调用路径下，经属性代理只沿祖先 fiber 查找，兄弟分支服务无法命中。该版本规则是：声明注入的服务用 ctx.serviceName；机会性读取的可选服务用 ctx.get(name)，并处理缺失。将可选服务列入 inject 会改变启动条件，无持久化演示可能因此永远等待一个不会安装的后端。ctx.get 仍按 isolate 键和活跃状态解析，不能绕过隔离域。

服务作用域与代码隔离

两个会话都注册同名工具，如果共享了不该共享的服务实例，A 的重载会影响 B，或 A 的工具定义泄漏给 B。用作用域与 isolate 区分服务身份，解决的是对象图中的可见性和所有权；它并不让同进程插件失去文件系统、网络或 Node API 能力。不可信插件需要进程或更强执行环境边界，不能拿 Context 当沙箱。

跨会话共享连接池时，完全隔离又会浪费连接与缓存。一种组合是保留共享池，同时隔离会话授权与工具注册；查询始终携带正确主体，池的生命周期覆盖全部使用者。共享层级因此取决于资源成本与权限契约，而非包所在目录。

事件模式是一份等待与决定权契约

“写入已提交”是向 UI 与遥测广播的事实，“准备关闭会话”则可能要求等待存储排空。前者不会因观察者离线而撤销已提交事实；后者需要聚合完成结果，才能继续释放资源。这一区别决定了事件应该通知、等待，还是允许某个监听器修改决策。

模式是否等待分发顺序返回值
  • emit：观察通知，不是持久化屏障。session/event 的广播与后端异步落盘必须分开理解；不能从“监听器被调用”推出“数据能抗崩溃”。
  • parallel：扇出并等待，用于聚合完成条件。session/flush 适合这里，但一个监听器的失败如何聚合、其余是否仍完成，要读具体实现与契约，不能只靠名称判断。
  • serial：按顺序等待，可按该事件的 bail 规则停止。agent/created 初始化失败要阻止发布；agent/turn-stopping 没有 next()，不要照抄 waterfall 回调。
  • waterfall：环绕式委托，能修改或短路决策。primer 的模式表写“非等待”不意味着异步事件调用方不用 await；返回 Promise 的具体分发点仍需消费它，回调是否异步由事件签名决定。
  • bail：找到首个有效应答即可停止。若需求是“所有策略都能否决”，首个允许就结束的设计会漏掉后续拒绝；不能把策略合取写成首个应答者获胜。

waterfall 的委托与短路

设外层监听器只想计时，忘了调用 next()。内层审批从未运行，但外层已经返回。反过来，权限插件确实拥有否决权时，短路才是正确行为。因此“所有监听器必须 next”也不成立：先明确哪个回调拥有决定权，再决定是否委托。

区分有权否决与只做注释（教学示意）
ctx.on('tools/pre-execute', async (exec, next) => {
  if (violatesPolicy(exec)) return { kind: 'deny', reason: 'policy' }
  annotate(exec)
  return next()  // 委托剩余策略；不是自己宣布最终放行
})

DSH 工具流水线文档另设只拒绝或弃权的单调守卫，正是为了让强约束不因某个普通监听器的位置而失效。守卫只约束经过该流水线的调用；恶意同进程插件绕开它直接写文件，仍属于更外层的隔离问题。

配置表达式的求值边界

复盘 0002 描述历史 Loader 曾将 disabled: !!js … 的表达式对象直接当布尔值，对象恒为 truthy，工具因此始终未挂载；刷新快照又把 UNKNOWN_TOOL 接纳为预期。固定提交的 primer 已描述 config 与 disabled 两处插值，不能把历史故障规则当成当前规则。其余元数据应按字面量处理，环境选择优先用显式 overlay。

cordis.patch.yml（教学示意，需对应版本核对）
# 按 id 定位行；这里替换的是整个 config，不是递归合并
- id: my-llm-row
  plugin: dsh-llm-deepseek
  config:
    baseURL: !!js process.env.DEEPSEEK_BASE_URL

YAML 解析成功只覆盖语法层。表达式求值后的插件树、必需工具的注册情况，以及禁用时的调用结果，才反映配置的实际语义。快照能发现输出变化，但若错误输出被接受为基线，它也会稳定地保留错误。

将 RepoOps 的只读能力组织为插件

RepoOps 当前在每个 run_agent 中构造 Corpus 并同步执行只读动作，没有 Cordis 重载生命周期。移植为知识工具插件时，Corpus/索引的版本与作用域决定 search/read 注册在哪个 Context；关闭策略则决定是否允许已有读取完成。若进一步支持仓库修复，还需要为进程、工作区和授权分别建立所有权。

这个迁移方案可以通过双会话故障实验检查：让 A、B 同时调用同名工具，延迟一个 A 请求并移除 A 的 Provider。观察 A 的新请求是否被拒、旧请求是否按关闭策略结束、B 是否继续工作，以及 A 的资源能否最终释放。另从构建产物经 Loader 启动，可以覆盖手工挂载遗漏的导出路径。
