研究主线 R1 · 问题定义

把“会自改”写成一个可检验的问题

读完后，你应当能为任何一个自改系统写出：谁在改谁、哪些部分固定、预算是多少、什么结果会推翻“它变强了”。这是研究协议，不是某个框架的成熟度排行。

三个必须分开的命题

  1. 可修改性：系统能改源码、提示词、权重或持久记忆。这是操作权限与实现能力。
  2. 有效改进：在预先指定的任务分布和资源约束下，新版本比旧版本更好。这需要对照与不确定性估计。
  3. 递归收益：改进后的系统参与下一轮改进，并且比冻结的改进器更有效。这需要把“改进器更新”单独拿出来做消融。

热加载没有验证第 2 项；benchmark 涨分没有自动验证第 3 项；第 3 项成立也没有证明无限加速。本文采用“改进产物反馈到后续改进过程”的工作定义，不要求每轮一定变好、不要求去掉所有人类参与，也不把权重必须变化当作所有论文共享的标准。STOP 自己对“full RSI”使用了更严格措辞。

最小数学模型

S_t = (W_t, P_t, T_t, M_t, I_t)  # 权重、提示/策略、工具、记忆、改进器
C_t = I_t(S_t, D_dev, B_search)   # 用搜索预算生成候选集合
S_next = Select(C_t, E_fixed, D_select)
U(S; D_target, B_infer) = E[任务得分 | 推理预算固定]
Δ_task = U(S_next) - U(S_t)
Δ_meta = E[U(Search(I_new, B_search))]
       - E[U(Search(I_frozen, B_search))]

Search 的两组实验必须从同一批起点开始，使用同样的基础模型、数据可见范围与总预算；终选候选只在开发/选择数据上决定。最终评估用独立任务与完整搜索重复。否则 Δ_meta 同时混入了模型升级、更多调用或更好的初始代码，不能归因给递归。

评分器 E_fixed 在本次比较里固定。如果研究目标就是改进评分器，可以在另一个实验里更新它，再用独立的审计集与外部标准比较。把候选与它给自己打分的尺子一起更换，旧分数和新分数就失去共同含义。

不要把一个维度排成六级智能

维度应记录什么常见误判
修改对象权重 / 上下文 / 工具 / 搜索器 / 数据生成器 / 评分器“写代码一定比改 prompt 更深”
反馈闭环只修改解题器，还是新解题器也参与下一轮修改把普通迭代次数当递归层数
外部依赖模型 API、人工选择、任务数据、预算和部署审批有人审批就不算任何自改
证据强度自述、开发集、独立确认、跨分布迁移、元改进消融把权限更大当成能力更强

一个改 prompt 的系统，如果 prompt 控制下一轮的实验设计，也可能构成元级闭环；一个能替换任意 Service 的系统，如果替换后从不对照测试，只有可修改性。原站的 L0–L5 只保留为教学索引，不能用于比较这些维度。

资源账本决定“更好”是什么意思

至少分开记录搜索成本、单题推理成本、验证成本和人工时间。成功率从 60% 到 70%，但每题从 1 次调用变成 20 次，可能是有价值的质量提升，却不能写成“效率提升”。应提供固定预算对比，或展示质量—成本的 Pareto 前沿：不存在另一版本同时更便宜且更准确，才叫非支配候选。

还要记录延迟分位数、超时和失败。并行线程数上升可以缩短墙钟时间，却增加总 CPU 小时；API 价格变化可以降低账单，却没有改进算法。度量需先定，不能见到哪条曲线漂亮就用哪条。

从局部闭环到智能爆炸，还缺哪些证据

局部改进可能遇到任务饱和、搜索空间限制、验证成本上涨、数据耗尽和收益递减。要支持“加速”，必须明确横轴：每单位时间、计算量还是资金的增益；再排除外部算力增长。有限轮次的最优值上升，也可能只是更多次随机搜索的自然结果。

练习：把重试次数从 1 改成 8，算哪种改进？

先问该策略是否由系统产生并反馈到以后，再问固定总调用预算下是否仍获益。它可能是自修改，也可能提高成功率；只有和冻结改进器、同预算搜索相比，才能讨论元改进。没有这些实验时，应报告“增加推理预算后的任务收益”。
