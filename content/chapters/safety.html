隔离与审批：把授权绑定到真正执行的动作

人已经批准“运行测试”，agent 却在批准后改写了测试脚本；执行器仍拿着旧批准执行新内容。审批记录与容器都可能正常工作，授权却没有约束到实际动作。这类检查与执行之间的时间差，说明安全边界需要落实到执行身份、不可变输入和资源权限，才能把批准决定延续到真正执行的时刻。

下面的检查项对应不同控制环节。实际效果取决于身份与资源配置；若多个控件共用一个高权限 runner，它们也可能因同一凭据或进程被攻破而一起失效。

检查与执行之间的对象变化

考虑一条假设时序：t0 agent 提议执行 ./test.sh；t1 审批界面展示旧版脚本及其工作目录；t2 人批准；t3 agent 修改脚本或替换其依赖；t4 高权限执行器运行路径上当下的内容。缺口在于批准对象与执行对象未绑定。审批记录只说明 t2 接受了旧内容，无法授权 t4 的新动作。

外部执行器可以对不可变快照计算动作摘要，在执行时核对版本、身份、目标、参数、输入与有效期。脚本依赖可写文件时，只绑定脚本哈希仍不足够；任意 shell 命令也可能通过间接调用执行更广泛的动作。因此，高风险审批需要绑定完整快照与权限范围，模型生成的自然语言摘要仅用于辅助理解。

候选权限与可信控制域

候选 agent 可提出补丁和动作请求，不应持有评分器写权限、确认集、预算控制、发布凭据或审批签发权。不同插件、packageId 和提示词不是不同安全主体；同一账号运行的任意代码仍可能绕过应用内封装。每次任务使用一次性工作副本，资源限制和凭据生命周期由候选之外的控制平面实施。

资源候选允许的能力可信侧必须掌握的能力
源码与任务产物在明确路径内读写，生成待审补丁按快照接收产物，限制大小与文件类型，拒绝越界路径
评分器与确认数据可看公开开发反馈，不可修改权威评分逻辑独立身份重跑、保存裁决及版本；确认数据不挂载给候选
外网与外部系统只访问任务所需端点与操作身份、目标和数据范围授权；不把长效生产凭据注入环境
依赖、缓存、共享存储固定只读基线，私有可写层审批跨任务产物提升，管理命名空间与服务端 ACL
日志、预算、发布指针提交事件或提升建议，不可覆写权威状态外部追加记录、终止进程树、签发或拒绝提升

工具接口、容器与外部执行器

工具白名单限制暴露的接口，适合知识助手只读检索；一旦白名单包含通用 shell，它并不限制 shell 内部动作。容器提供文件系统、进程和资源的隔离构件，但挂入宿主敏感目录、特权模式或管理套接字会重新开放高权限路径；容器名称也不会自动隔离共享对象存储与网络凭据。强隔离环境能进一步缩小宿主暴露面，却仍不能纠正错误的云权限。

外部执行代理则把“模型建议”和“真正持权执行”分开：它按结构化请求验证授权，而不是执行模型拼接出的任意字符串。代价是维护动作协议与审批队列，也可能限制合法的动态调试。对仓库修复，通常允许候选在受限环境内广泛调试，但提升只接收补丁；对知识助手，默认只读并把发送消息、改权限等动作单独审批；对评测平台，候选 runner 与 verifier 的身份、数据和结果写面必须分开。三者不需要相同工具集，却需要相同的授权原则。

P8 的独立 verifier 将评分移出候选写面，解决的是评分权限问题。宿主暴露面、网络凭据和依赖来源仍由各自的部署配置决定。后文的状态机与故障注入描述设计要求，不能据此视为教学 runner 或容器配置已经完成生产安全审计。

审批状态机：批准旧动作不能授权新动作

执行协议示意
proposal = {run_id, action, target, args, snapshot_digest,
            input_digest, resource_scope, expires_at}
pending → approved(proposal_digest, approver, one_time_token)
approved → executing   仅当摘要、身份、有效期及一次性令牌核验通过
approved → stale       任一输入、快照或权限范围发生变化
executing → succeeded | failed | outcome_unknown

模型只能提出 proposal；不能签发 approved 或直接修改发布指针。

外部操作还可能处于执行结果未知的状态。例如，服务已经发送消息，客户端却因超时没有收到成功回执。直接重试可能重复发送，此时需要查询外部操作状态，或在服务支持时使用幂等键。outcome_unknown 因而是独立状态，不能记录为“未发生”。一次性批准令牌限制请求重放，业务幂等性则处理实际副作用，两者解决不同问题。

审批服务不可用时，动作类别决定后续处理。读取公开资料可以采用预先声明的低风险策略；发布、权限变更和不可逆写入则应拒绝执行或保持等待，形成 fail-closed 行为。审批界面也需要展示真实差异、目标和副作用，避免候选自行编写的“安全修复”摘要掩盖授权对象。

代码回滚与外部状态恢复

一次自改可以同时改变代码、依赖、数据库和外部消息。恢复 git commit 或 packageId 只处理其中一部分。对每个动作分别记录可逆性：本地文件可从快照恢复；数据库改动可能需要补偿事务与冲突检查；已发送消息可能只能更正；已泄露凭据需要撤销轮换，不能靠删日志“撤回”。有不可逆副作用的操作，应在发生前缩小范围与加强授权。

事件发生后先冻结候选提升与待执行请求，撤销相关短效身份、保全外部日志，再恢复可信版本并核对外部状态。不能为了快速清理而先删除一次性环境里唯一的证据。对于 outcome_unknown，要把人工确认与业务补偿记录进恢复过程；没有确认，不能宣称回滚完成。

监控覆盖与共同失效源

监控可能漏报、超时或排队，CoT 可能缺失，日志也只能记录已采集的通道。第 07 章 的基率分析说明，少量告警既可能来自低风险，也可能来自低检测覆盖。资源权限负责阻断明确禁止的动作，审批处理需要语义判断的授权，监控再提供调查与处置线索。执行侧将原始请求、决策、实际执行身份与结果写入候选不可覆写的存储，可以保留独立于模型自述的记录。

这些控制仍可能共享失效源。若同一个管理员凭据能够修改 verifier、删除日志、放开网络并更新发布指针，凭据失守会同时影响多道控制。AI Control 在明确对手能力与协议的前提下评估风险，容器或审批只是协议中的具体构件。Concrete Problems in AI Safety 还将合法操作的负面副作用纳入分析，补充了未授权动作之外的风险。

审批与隔离的故障注入

以下实验方案在本地隔离 fixture 中使用合成数据，不使用真实凭据或生产目标，本章不包含其运行结果。合法任务提供正对照，故障动作提供负对照。P8 的执行侧记录与 P4 的功能评分分开解释：合法任务因权限过严而失败属于可用性问题；攻击被拒绝属于控制生效；攻击成功则是安全失败，即使最终功能测试全绿。

故障注入检验的控制属性观察结果
批准后修改脚本、依赖或输入审批绑定不可变动作旧令牌被拒绝且进程未启动；合法原快照仍能执行
用候选身份写评分器、日志和发布指针可信控制域在候选权限外OS/服务端拒绝与目标完整性，而非模型拒绝语句
经符号链接写越界路径，或启动子进程持续写入路径及生命周期边界有效实际写目标不变；预算终止后受管进程树结束
A 写随机标记、B 读共享缓存运行间没有未批准的信息流跨身份读取拒绝；共享对照组能读到标记
外部测试服务处理成功但响应丢失重试不会重复副作用进入未知状态、查询/幂等处理，服务端动作只发生一次
断开监控或审批服务关键动作不因控制失联而放行高风险请求未执行，低风险处理符合预先声明策略

身份与权限配置、环境与候选摘要、受保护对象前后状态、拒绝事件和实际副作用，共同限定实验结论。新的挂载、依赖缓存或外部身份都会改变可达路径，需要重新纳入威胁模型。RSI 提升的是这些边界内的候选版本，候选修改控制规则的权限仍保留在外部。

工具本身的安全范围

DSH SAFETY.md（固定 commit） 标明 developer preview、未安全审计，不能作为不可信工作负载的唯一安全措施。这一限制适用于将它纳入部署协议的方式：额外隔离、凭据控制与独立裁决仍需由具体系统提供。

评分器可信度、CoT 边界与外部执行域进一步讨论这些控制如何配合。安全结论需要对应明确的身份、权限配置与攻击路径；配置变化后，旧结论不会自动延续。
