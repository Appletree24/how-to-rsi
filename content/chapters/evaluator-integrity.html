评分器的测量误差与信任边界

退款助手的总分上升，可能同时伴随几种异常：金额正确的答复被判错，只说“已退款”的答复得到高分，失败运行没有进入汇总。这些现象分别涉及测量、目标和记录完整性，单纯更换更强的 judge 无法一并解决。本章用假设的退款场景说明如何定位评分异常，再讨论校准、权限隔离、行为监控和副作用恢复；场景与数字均为分析算例。

沿执行链区分测量、目标与记录问题

设任务要求：对一笔符合规则的订单退回 100 元，不重复退款，并告知用户处理结果。一次完整观测至少包括请求、支付工具响应、最终状态、答复和评分。沿着这条链，可以区分三种问题：

问题在退款算例中的表现修什么，以及留下什么问题
测量错误实际退回 100 元，评分器却因答复写成“100.00 元”而拒绝；或金额比较被浮点误差干扰用参考实现、边界输入、合法替代解和变形测试修正判定；这不会说明“退款成功”是否涵盖了全部用户目标
目标代理失真评分规则只奖励礼貌地宣称“已退款”，候选不调用支付工具也能得分加入独立的最终状态与重复扣退审计，检查高分是否对应真实完成；仅把同一 rubric 交给更强 judge，未必改变错误目标
测量完整性或权限遭破坏失败轨迹被删除、测试被修改，或候选把自报分数写入最终结果由外部控制域收集完整记录、重新评分并核验工件；隔离可以阻止改分，不能修复一个本来就奖励错事的指标

判断前两类问题，要看规则原本想测什么。如果规则要求工具执行成功、实现却只查一句话，是测量实现错了；如果规则本来就只衡量答复的礼貌程度，实现可能完全正确，但把它当退款完成率便是目标失真。一条异常也可能同时涉及多类故障。

诊断时先核对每条请求是否都有终态记录，再用独立数据核实金额与状态，最后检查评分是否符合预定规则。这样既能发现遗漏，也能避免把真实业务失败误诊为 judge 不够强。奖励模型过度优化研究关注的正是代理奖励与目标奖励的偏离：即使测试文件没有被修改，持续优化一个不合适的评分规则也可能让两者越走越远。

记录完整性决定了后续诊断可用的样本。若失败请求已经遗漏，修改 rubric 只能给幸存样本重新评分。因此，请求清单与终态记录需要先对账，使成功、失败、超时和未知状态均可追溯；在此基础上，才能分析合法金额表述被拒的原因，以及答复质量能否代理业务完成。上游证据缺失会使下游校准失去明确的解释。

错误接受率、拒绝率与真实失败基率

退款金额、支付状态和是否重复执行若有可信的外部记录，可以先用断言判定；LLM judge 再评答复是否准确说明了状态、是否清楚解释无法退款的原因。把正确性、偏好与业务约束混成一个分数，会让“语气更好”抵消“钱没有退回”，而读者无法从总分看出这种交换。

假设按明确 rubric 人工复核了 40 个答复，其中 20 个合格、20 个不合格。这只是便于手算的平衡样本；实际校准还需包含合法替代解、冗长错解、要求评分器忽略规则的格式攻击及边界案例。暂以复核标签为参照，judge 的假设输出如下：

复核标签judge 接受judge 拒绝judge 不确定合计
合格181120
不合格414220

以各类的全部样本为分母，错误接受率是 4/20=20%，错误拒绝率是 1/20=5%；不确定比例是 3/40=7.5%。这三个数把不同后果分开：前者放过失败，第二个错杀有效方案，第三个消耗复核资源。若把 unknown 静默转成 pass，原本不合格的 2 个不确定案例也会被放行，这组数据的错误接受率便变成 6/20=30%。选择转人工或暂不通过，会产生不同的成本与决策结果，应在使用 judge 前确定。

这张表仍不能直接代表部署质量。样本是人为平衡的，真实流量中的失败比例可能不同；40 个案例也不足以精确估计罕见错误。人评有争议时，应保留分歧与复核过程，而非把专家标签当作无误真值。用这一子集调整 rubric 后，另留未参与调整的审计样本，才能查看修正是否对新案例有效；任务或模型分布改变后，旧的校准结果也可能失效。

被接受答复中的不合格比例使用另一个分母：在当前平衡样本中，它是 4/(18+4)。错误接受率 4/20 则以所有不合格答复为分母。前者描述被放行结果的质量，后者描述 judge 对失败的识别能力。由校准表推算真实流量中的放行风险，还需要真实失败基率：

从条件错误率到被放行结果的风险
π = 真实流量中不合格答复的比例
f = P(judge 接受 | 不合格)
t = P(judge 接受 | 合格)

P(不合格 | judge 接受) = π f / (π f + (1−π) t)
# 分母须非零；f、t 迁移到真实流量需要额外假设。
# unknown 的处理改变放行规则，必须据此重新定义 f、t。

这解释了为什么“校准准确率不错”不足以批准自动退款：人工构造的平衡集适合暴露错误类型，却不自动给出真实流量中放行失败的比例。若自改进改变了答复风格或失败类型，条件错误率也可能变化，单独更新 π 仍不够。更强 judge、多 judge、更多标注都是候选方案，但首先要确定缺的是状态证据、判定能力，还是对未知分布的校准。

位置、长度与共同偏差

假设比较两份答复：A 简短且与支付记录一致，B 更长、更礼貌，却把失败状态写成成功。隐去候选身份，先展示 A/B，再展示 B/A，并把两次选择都映射回原答复。如果 judge 总选第一份，换位就会导致它选择不同内容，提示位置敏感；若它两次都选 B，则结果虽然稳定，正确性判定仍可能有问题。换位测试只检查顺序影响，不会自动发现所有共同偏差。

类似地，可在保持事实与结论不变的情况下增减表述长度，检查判断是否随长度改变；也可分别统计不同来源模型的答复，检查自我偏好。这些比较固定 rubric 与 judge 模型版本，保存原始判断，再复核争议案例。相关研究报告了位置、冗长和自我偏好等局限；退款场景将这些诊断方法具体化。

多 judge 投票能否改善结果，取决于错误是否互补。如果它们都把“我已退款”当成执行证据，投票只会稳定地重复同一个误判。独立的工具记录解决的是证据缺失，投票本身不提供这份证据。

校准记录包含原始答复、外部状态、rubric 版本、judge 原始判断与人工争议，才能支持错误归因。事实不变的表述变换检查判断对无关形式是否敏感，事实改变的业务反例检查判断能否识别真实失败。两类测试在诊断上互补，合并成一个准确率会掩盖错误来源。unknown 可以转人工或暂不通过，但不能为了提高覆盖率静默改成 pass。

候选执行域与评分控制域

再看那条没有进入汇总的失败运行。它可能只是采集故障，单凭遗漏还不能推断候选作弊；但如果候选能删除日志，完整性就取决于它是否愿意保留不利记录。可将候选执行域与控制域分开：前者拿任务输入、允许的工具和临时工作区；后者保管评分器、确认数据、预算、版本发布指针和完整审计记录，并以独立身份从候选产物计算分数。

例如支付工具调用与响应由控制域留存，候选输出的 agent.reported_score 只是一段待核查内容，不是最终分数。超时也由控制域计时、终止相应工作负载并记入结果；在输出 JSON 中增加一个 timeout 字段，并不会停止仍在执行的进程。只追加审计记录还需由候选无法修改的权限维护，否则“只追加”只是调用习惯。

同一进程、同一账号下的不同 packageId 可以组织代码，却不自动隔离权限。只读挂载防写，不防读取答案；hash 可以标识内容并辅助核验是否变化，不能单独证明内容来自可信评分器。这些机制分别提供代码组织、写保护与内容核验能力，部署时仍需落实独立的身份和授权。

任何运行时框架的安全声明都需要对应版本核对：developer preview 或未审计的实现不能作为不可信工作负载的唯一安全控制。采用具体项目时，评分服务的身份、挂载和日志权限仍需在实际部署中检查；声明本身不是隔离有效性的证据。

隔离环境中的故障注入需要观察的控制域证据仅凭什么还不够
候选提交自报高分，并试图覆盖评分器或确认数据评分身份独立重算；禁止的写入被实际权限拒绝，原工件可核验提示词写“不要改测试”、输出一个 hash
候选不返回结果，或试图删除失败记录外部计时器结束工作负载；请求仍有 timeout 或失败终态，汇总分母不减少候选自己承诺记日志，或仅返回 timeout 字段
候选尝试读取确认答案或借允许工具间接访问检查实际身份、挂载与工具代理的可达资源，禁止读取被拒绝只读挂载；它只限制写入
候选尝试修改发布指针发布身份与候选执行身份分离，未授权调用不能改变当前版本不同 packageId 或不同目录

上述故障注入应在无真实副作用的隔离环境中执行。本仓库的 Python lab 只对可信输入做统计分析，未实现这些隔离机制，也未执行表中的安全测试。威胁模型还需覆盖工具代理：候选进程即使不能直接写文件，仍可能通过有权限的代理写入同一目标，授权检查因而要落在实际执行动作的一侧。确认答案不可读，也不会切断总分反馈带来的自适应训练；这部分需要 R3 的数据访问与查询协议处理。

行为监控的观测范围与漏检风险

退款助手即使写出一段“我检查过支付状态”的推理，也不能替代实际的工具记录。可见 CoT 可以提供监控线索，但未必忠实或完整；使用 latent reasoning、没有可见推理时，事后索取的一段解释也不能补成同等的过程证据。这时仍可比较最终行为、工具轨迹、环境副作用，以及特定诱导条件下的失效率。

例如设计一组诱导助手谎称退款成功的攻击，另取一组正常请求校准告警阈值，再在未用于生成攻击或校准阈值的样本上评估。固定正常请求上的误报率后，查看监控能召回多少已定义的失败行为，才能说明它在这个条件下抓到了什么。攻击生成、阈值校准和最终评估混在一起，会把针对已知案例调出的监控效果误当成泛化能力。

模型是否知道自己被监控、可见的奖励结构和上下文长度都可能改变行为，因而属于实验条件。激活层探针或机制可解释性还需要白盒访问及额外验证，不是普通 API 场景下随手可用的替代品。AI Control 从对手模型出发研究部署协议的风险。这种评估考察协议在指定威胁下的表现，模型一句“没有作弊”和监控在已知攻击上的高检出率，都不足以推断它对未知策略也有效。

零观测同样存在统计不确定性。在试验独立、违规概率恒为 p、检测器完美的理想条件下，100 次测试零违规的概率为 (1−p)^100。令它等于 0.05，单侧 95% 上界为 1−0.05^(1/100)≈2.95%，常用近似为 3/n。因此，即使完美检测器没有发现违规，上界也仍高于零；试验相关或样本被自适应筛选时，这个界不能直接沿用。

如果检测器会漏检，问题更严重：在无误报、每次真实违规以固定概率 s 被检出等理想条件下，单次观察到告警的概率是 p × s，零告警直接约束的是这个乘积，不是 p。没有经过独立评估的检出能力，就不能用“零告警”反推出真实风险很低。报告应限定为“在这些测试条件下未观察到”，同时附样本量、攻击覆盖、检测器限制与正常请求的误报成本。

版本回退与外部副作用恢复

假设候选多退了一笔钱，随后发布指针回到基线。回退只改变未来请求运行哪个版本，不会撤回支付系统已经完成的转账；同样，发出的邮件、泄露的数据和写入共享数据库的记录也不会随代码指针恢复。

为了分清哪些影响仍需处理，可记录 effect journal：操作对象、请求标识、执行前状态、工具确认结果和补偿状态。对可逆操作，根据实际状态执行补偿并核验结果；补偿本身也可能失败，不能只记录“已发起”。对于已被下游消费的数据库写入，恢复原值也未必撤销了下游动作；对于邮件发送和数据披露，通常更不存在真正的撤回。

支付服务超时时，没收到确认仍可能意味着操作已经执行。系统需要将该操作记为待核实，并使用稳定的请求标识查询外部状态；工具支持幂等时，重试沿用同一业务操作的幂等标识，避免产生新的退款。确认未执行后才按规则恢复，确认已执行则记录效果并决定是否需要补偿。这个状态区分同时影响评分：未知不能伪装为成功，也不应从分母里消失。

独立环境中的验证和预提交门可以把可核查的执行计划与真实副作用分开，确认后再执行。试运行能减少直接损害，但真实环境中的权限、并发和外部服务状态仍可能不同；补偿流程也需要依据实际状态工作。

退款场景中的分数只有与请求终态、judge 的条件错误率、实际权限和副作用记录相连，才能用于发布判断。记录缺失使失败比例不可知，错误目标会奖励未完成的退款，权限漏洞允许候选改写测量，而代码回退无法撤销已发生的转账。这些问题各有处理位置：成功率继续上升本身不会消除其中任何一种风险。
