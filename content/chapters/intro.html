Harness：一次执行的责任边界

模型已经返回“修改 README”的工具调用，编辑器这时断线，用户又按了取消。文件可能已改，界面却没收到结果。重连后的处理取决于执行端留下了什么：尚未派发的动作可以停止，已完成的动作需要核对，结果未知的动作不能盲目重试。DeepSeek Harness（DSH）的运行时结构，可以从这个失败窗口开始理解。

版本与来源DSH 部分依据提交 ddefc45fbc7f 的架构文档及子系统文档。文中的通用设计、代码骨架和故障时序为分析示例；本地 RepoOps 的实现范围在后文单独说明。

模型输出、工具结果与任务完成

“模型说改好了”只能证明它生成了文字；“工具返回成功”说明一次调用给了结果；“文件内容符合要求且结果可恢复”才接近用户的完成条件。取消与断线让这三个事实分离：网络响应丢失不代表写入没发生，回合结束也不自动代表日志已越过持久化屏障。

边界上的判断最小机制必须留下的证据
模型到底获准看到什么、调用什么？提示词组装、作用域工具 schema、调用准入可重建的请求历史、路由与工具定义；不能只有 UI 文本
动作是否已进入执行？先记录调用身份，再通过策略与工具执行路径callId、参数、准入决定、结果或未决状态
能否重试或恢复？区分请求重试、工具副作用、日志恢复结果是否持久、外部动作能否查询、是否有幂等键

Harness 管理的是一次执行从取得输入到释放资源的所有权。模型给出候选动作；运行时决定动作何时允许发生、如何观测、谁来收尾。工具循环只是其中一段，日志、授权和资源管理共同决定了这段循环在失败后能否继续。模型生成更好的代码，也无法补上运行时丢失的写入结果。

从责任边界组织 Harness

Agent 提出动作，Harness 为策略提供受控运行环境。两者可以在同一个进程，但授权、预算与终态由运行时持有，不能交给模型的自由文本决定。固定工作流同样需要这些边界，只是下一步通常由预定规则选择。以下分层按决策所有权划分，不要求每一层对应独立服务。

设计层拥有的决策不能越权的边界
宿主与准入确定用户身份、任务范围、预算与审批渠道检索文本、模型参数不能扩大授权范围
上下文编译把可信指令、历史、证据与工具定义组织为模型请求摘要不能把工具输出升级为系统指令；裁剪不能抹掉证据来源
执行控制器调度模型与工具、处理 deadline、取消和预算耗尽策略可建议重试，不能自行重置总预算
工具网关与隔离环境校验输入、重新授权、绑定审批、执行受限动作schema 校验之外仍需业务授权；插件卸载后已发生的副作用仍然存在
状态与观测记录执行事实、持久化屏障、未决动作与费用UI 断流不改变权威状态；日志重放不自动重发外部动作
独立验收用行为结果判定任务完成，比较不同 Harness 策略Agent 的完成声明和自报分数不能成为最终裁决

用一次受限文件修改串起全部设计

用户要求修复配置，只允许修改 config/pool.yaml。宿主冻结仓库 revision、允许路径和总预算；上下文编译器加入故障证据，而不是把整仓无差别装入提示词。模型提出 patch 后，工具网关将规范化后的路径、patch 内容摘要与基准 revision 绑定到同一审批。执行前再次检查权限和文件版本；若等待审批期间文件变化，原审批不能静默复用到另一份修改。

执行器在隔离工作区应用 patch，独立 verifier 检查资源上限与修改范围，再发布结果。若应用后进程崩溃、成功事件尚未持久化，恢复端先比对实际文件与预期 patch，不能直接重做所有动作。文件检查能解决这个示例的一部分未知状态，但不能推导出任意 shell 命令都可安全重试。详细拆分见 上下文与架构、执行调度、恢复协议。

任务依赖决定协调规模

方案适合条件新增代价与升级信号
固定工作流步骤稳定、结果格式明确，失败可定位到预定阶段异常分支逐渐变成规则森林时，再考虑让模型选择下一动作
单 Agent + 受控工具循环路径不确定，但一个上下文和单一写入所有者足够需要明确停止条件，防止无效循环持续消耗预算
协调器 + 多个子任务任务真能拆分、各自输入和产物可定义、独立读取收益明确预算分配、取消传播、上下文重复与产物冲突；共享写入仍须明确唯一合并者

子 Agent 的收益来自可独立推进的任务分支。任务依赖图决定哪些分支可以并行，每支还需要明确预算、产物格式与合并责任。若三支都修改同一文件且没有可独立检查的产物，增加协调器可能只会增加冲突。父任务取消后，子任务尚未退出，资源所有权就仍须保留；具体调度与故障处理见 Harness 故障注入。

正常轨迹只能展示各组件如何协作。审批期间撤权、动作完成后丢失回包、父任务取消后子进程仍在运行，这三条故障轨迹分别暴露授权、结果核对与资源释放的边界。比较架构时，可以记录这些切点上的权威状态、恢复动作和用户可见结果，再按 P7 的 Harness 消融实验 衡量各机制的实际收益。

DSH 的插件化执行循环

固定提交的架构文档把模型适配器、工具注册表、会话日志和 Agent Loop 都定义为可配置插件。服务定义是消费者依赖的接口，Provider 是实现，Consumer 通常是工具或宿主。替换实现的范围由这三类角色之间的契约确定：消费者不必知道具体 Provider，但仍依赖它的错误、取消和生命周期语义。

职责与文档中的接口可替换什么不能借替换丢掉什么
ctx.systemPrompt / ctx.tools上下文提供者、工具集合模型所见与日志重建一致；执行端仍须对已暴露的工具做授权检查
ctx.agents / ctx.agentLoopAgent 接口背后的默认驱动器输入领取、取消传播、结束状态与清理责任
ctx.llm模型路由与适配器流协议、实际用量的未知值、错误与取消语义
ctx.sessions / ctx.sessionPersistence日志的存储后端单写者、连续事件序号、flush 后的持久承诺
tools/* 能力扩展点审批、观察与执行包装不能用后处理“撤销”已发生的外部副作用

一个进程、一个类持有全部依赖，是固定、只读、短任务中较容易理解和验证的方案。多个载体、不同执行环境与独立生命周期出现后，插件化才有明确收益，同时也引入服务查找、配置合成和卸载顺序等故障面。第 13 章讨论依赖失效，第 14 章讨论执行环境替换与跨会话隔离。

三类产品中的运行时约束

知识助手：先守可见性

查询只读也可能泄露数据。工具少不代表无需权限；检索作用域、引用可追溯与租户边界必须先确定。未读证据不能因模型“知道答案”变成已读事实。

仓库修复：再守副作用

编辑、命令与子进程让取消变得不可逆。需要隔离工作区、可检查的差异、进程退出与产物断言；返回一个取消标记不会回滚文件。

评测平台：再守恢复身份

重复投递、worker 失联、评分版本变化要求稳定 trial 身份与提交规则。任务跑完和成绩可晋级是两条不同的状态线。

本仓库 RepoOps 是一个只读实现：projects/repoops/agent.py 提供 search/read/finish 协议；runner.py 串行执行 trial，并把结果与完整轨迹放入同一 SQLite 提交。它尚未接入 DSH，也没有文件修复工具、会话级恢复或强制进程取消。扩展为仓库修复工具时，写入所有权、执行中持久化和取消收尾会成为新增的实现责任。

固定版本与启动入口

试用入口和固定版本源码回答不同的问题。第一条命令解析当时的 npm 版本，适合了解产品入口；分析本文契约则需要锁定对应提交。运行前应检查该提交的运行时要求、锁文件和安全说明，并使用可丢弃环境。

试用入口，不是版本锁
npx @deepseek-ai/dsh web
# 未指定 npm 版本；启动参数、端口及浏览器行为以该版本 --help 为准
固定文档对应的源码，再按该版本 README 核对命令
git clone https://github.com/deepseek-ai/deepseek-harness.git
cd deepseek-harness
git checkout ddefc45fbc7f8e46dd73185e68295696d1297887
# 先检查 package.json 的 engines/packageManager 与该提交的 README
pnpm install --frozen-lockfile
pnpm run typecheck
pnpm run build
pnpm dsh web
pnpm dsh --profile headless "修掉 README 错别字"
# 此处是待执行路线；不要在持有敏感资料的工作目录试运行
插件生命周期与安全隔离固定提交的 SAFETY.md 明确：DSH 是未安全审计的实验性 developer preview；沙箱、审批和权限控制不能保证隔离，更不能保护已授权访问的资源。最小权限、可丢弃环境、备份与凭据隔离仍由部署方负责。

沿执行路径定位源码

deepseek-harness/ ├─ vendor/ Cordis 生命周期与 Loader 的定位入口 ├─ packages/ 插件与能力服务 │ ├─ core/ session / tools / agent / agent-loop / scope │ ├─ llm/ fs/ shell/ sandbox/ subagent/… 定义、实现与消费者 │ └─ bundle/ 组合层；与 profile / patch 一起决定启动树 ├─ apps/ 载体，不应另造一份循环契约 ├─ python/ SDK 载体；固定提交文档描述其启动同一 dsh CLI ├─ snapshots/ 回放线索，不是实模型能力或安全证明 ├─ docs/ 架构 → 子系统 → API 声明 → 事故复盘 └─ scripts/ 文档生成与静态门禁的定位入口

固定提交文档要求受支持的 Node 应用通过命名 profile 启动：web、headless、sdk、sdk-minimal、acp。这是该项目的载体契约，不是所有插件框架的普遍定律。手工 ctx.plugin() 可用于单元测试，却不能据此宣称真实 Loader 路径已经验证。

一次工具调用跨越请求、准入、执行、结算和持久化五个边界。文档规定契约，源码调用点决定顺序，运行观测说明具体环境中的行为，三者提供不同层次的依据。RSI 实验同样依赖这些边界：若候选改动改变了执行方式或评测责任，即使提升数字不变，实验之间也可能失去可比性。
