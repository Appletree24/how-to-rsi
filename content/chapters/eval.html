Agent 评测：从执行证据到发布决策

新版客服 Agent 在 20 个任务里多做对两题，却在其中一次重复退款。成功率提高了 10 个百分点，仍不足以支持发布：收益幅度、违规代价、预算和抽样不确定性分别约束这个决定。本章以订单 O-104 的 80 元退款为例，说明如何从授权、执行过程和环境终态形成评分，再比较新旧版本。

退款任务、20 题手算与发布情境均为说明方法的假设案例。Claude Code、Bolt、Descript、SWE-bench 与 LangSmith 部分依据公开资料介绍实践及其适用范围，不涉及内部题库、发布阈值或未公开的生产成绩。

退款任务的终态与过程约束

任务：取消订单并退回 80 元

用户要求取消自己尚未发货的订单 O-104。测试环境中，该订单实付 80 元、尚无退款。业务规则要求先核验身份，只能退回实际支付的金额，重复请求不能重复退款。

任务输入
用户请求、退款政策，以及查询订单、核验身份和发起退款的工具。每次从同一份干净订单快照开始。
环境终态
O-104 已取消；恰好一笔成功退款，金额 80 元、收款人为原付款人；其他订单未改变。
过程约束
执行退款前完成身份核验。这个顺序是业务约束；不要求 Agent 按参考解的固定顺序查询资料。
执行成本
模型与工具调用费用、墙钟时间、重试次数。超时和崩溃留在任务清单中，不能只汇总成功运行。

这份输入、初始状态与成功条件组成一个 task；从头执行一次是一个 trial。对话和工具事件组成可观测的轨迹（trace），退款记录是环境终态（outcome）；读取这些证据并判分的是评分器（grader）。Agent 的完成声明属于输出，是否实际完成仍由终态检查确定。

人工参考解可以帮助确认任务可解，评分器则还需识别四类错误：未退款却声称成功、退了两次、金额不是 80 元、改了其他订单。仅检查余额净变化仍会漏掉违规：先退 160 元再扣回 80 元，可以得到相同净额，却违反退款权限。交易明细和执行时的授权状态因此也是评分依据。终态与过程约束互补，同时保留正确解在查询顺序等非关键步骤上的自由。

网络故障还会引入“结果未知”的中间态。例如退款已成功，工具响应却超时，立即重试可能产生重复退款，直接宣称失败也可能误导用户。此时允许按业务幂等标识查询可信状态，再如实答复。评分同时检查最终恰好一笔成功退款，以及身份核验和重试是否满足政策；重试的副作用与成本也必须计入。

硬约束与开放质量分别评分

沿用退款任务：不同问题需要不同证据
检查实现方式结果怎么用
金额、收款人、重复退款代码读取可信状态快照，逐项断言任一违规，任务失败
身份核验发生在退款之前核对工具执行端记录的事件与授权状态作为必需约束，不靠模型自述
解释是否准确、是否隐瞒失败LLM 按明确 rubric 对照工具结果，给出证据位置单独报告质量；证据不足标为待审
边界案例与评分分歧人工复核同一份产物、轨迹与政策修订规则或任务，记录评分器版本

退款未发生，即使回复语气很好，任务仍然失败。代码与执行端证据负责检查硬约束，解释准确性则单独评分。身份核验、问题识别可以设置部分分来定位失败，但这些诊断分不能抵消越权。金额相等和唯一交易记录能够精确判断，使用 LLM judge 反而会引入不必要误差；解释是否隐瞒 pending 状态，则可以通过明确的 rubric 辅助人工复核。人工判断同样需要保留分歧并校准。

一个可复核的 LLM 评分条目
评分 rubric · 只评价“是否如实说明退款状态”
输入：用户可见回复 + 可信退款结果
PASS：退款成功时说明成功；失败或待处理时明确说明尚未完成。
FAIL：工具报错或状态为 pending，却向用户宣称已到账。
UNKNOWN：缺少退款结果，无法判断。
输出：verdict、回复中的原句、所依据的结果字段、简短理由。

这个条目可用人工标注样本校准，重点测量“实际失败却判 PASS”的误放行与待审比例。模型、提示词或政策变化后需要重新校准。UNKNOWN 表示缺失证据，不能静默计为成功，也不能从分母中删除。

公开产品中的证据分工

代码修复、应用生成和视频编辑同样需要区分完成声明与实际结果。公开实践展示了不同证据的组合方式：执行测试检查功能行为，模型与人工评审处理开放式要求，线上观察补充离线任务未覆盖的失败。下面分别说明资料中已有的做法，以及将其用于具体任务时的设计示例。

产品实践 / Anthropic · Claude Code

把“改代码体验变差”拆成具体行为

Anthropic 披露，Claude Code 早期依赖员工和用户反馈迭代，随后先为简洁度、文件编辑等较窄行为补充评测，再覆盖过度工程等复杂行为。自动评测与生产监控、A/B 测试、用户研究配合使用。原文没有给出可直接复制的内部题库或发布阈值。

评测对象
具体投诉可以转成固定输入与可检查产物，而非只保留“用户不满意”的标签。与生产接近的运行时和完整失败轨迹有助于复核问题。
任务示例
对于一个只需修边界条件的 issue，测试检查问题是否修复、旧行为是否回归；评审再判断新引入的依赖、抽象和文件改动是否必要。diff 长度本身不足以代表质量。
适用边界
代码测试覆盖功能结果，未必覆盖维护成本；LLM 对“过度设计”的评分需与维护者判断校准，不能取代真实使用反馈。

产品实践 / Bolt 与 Descript

应用生成与视频编辑中的多层质量

据 Anthropic 对客户实践的介绍，Bolt 把静态分析、浏览器 Agent 测试和 LLM judge 组合起来：分别检查生成代码、应用交互与指令遵循。Descript 则把视频编辑质量拆成“不破坏已有内容、完成请求、完成得好”，从人工评分发展到产品团队定义标准的 LLM 评分，并定期人工校准，分别运行质量与回归两套评测。这里依据的是 Anthropic 的公开转述，并非两家公司开源的完整流水线。

证据分工
静态检查发现编译与类型问题，浏览器执行用户操作，模型评审检查开放式要求。分别保存评分明细，有助于定位退化发生的层次。
任务示例
一个可筛选订单页的评测，除了编译通过，还包括在浏览器中选择“已退款”、核对列表与测试数据一致，以及检查需求中的空态提示。页面截图无法单独说明筛选功能是否正确。
适用边界
浏览器 Agent 本身也会点错或超时。保留操作记录、截图与后端状态，复核是被测应用失败还是测试驱动失败；重试策略必须提前确定。

公开基准实现 / SWE-bench Verified

补丁的修复测试与回归测试

SWE-bench 与 OpenAI Preparedness 合作发布的 Verified，是经过人工质量验证的 500 条任务子集。人工审核的是题目质量与可解性，不是逐次批准模型答案。Agent 接收 issue 与修复前的仓库版本，交付补丁；参考补丁属于评测资料，不能作为待解任务的输入。

实际执行
官方 harness 在 Docker 环境中应用补丁并运行测试，保留测试输出与逐题报告；不是读取 Agent 最后一条“已修复”消息。
两组验收
FAIL_TO_PASS 检查问题对应的测试是否由失败变为通过；PASS_TO_PASS 检查原有测试是否保持通过。2026-09-20 的 main 判分源码要求两组均满足才记为 resolved；该源码快照与 2024 发布版实现须分开看待。
项目中的对应设计
历史 bug 可以绑定固定仓库版本与环境，分别保存修复测试和回归测试。每次比较关联补丁、日志与运行标识，使汇总分数能够追溯到实际执行。
适用边界
resolved 表示满足这组测试，不代表代码所有性质正确，也不等于生产安全。容器化减少环境差异，但不会自动消除数据泄漏或评分器漏洞。

配对比较、样本量与发布约束

20 题的用途影响结果含义。开发集用于挑候选，确认集用于检验终选；“能力 / 回归”区分测量目的，“开发 / 确认”区分数据用途。能力题和回归题都可能用于独立确认。如果已经依据这 20 题的结果调整提示词，它们就参与了选择，不能再充当该轮独立确认集。

旧版成功 12+2=14 题，新版 12+4=16 题，观察差值是 (4−2)/20=0.10，相对提升约 14.3%。但支撑方向的分歧只有 6 题。在“每个分歧独立且两种方向等可能”的零假设下，观察到至少 4 次新胜的单侧精确概率为 (15+6+1)/64=0.34375；这不是优势成立的强证据，更不是总体提升恰好 10 个百分点的证明。这里的简化检验不是实验室脚本的算法说明；正式设计需预先确定指标、置信区间、配对单位与停止规则。

开头的重复退款即使已经计入新版失败，平均分仍可能更高，但硬约束会否决发布。若没有违规，却超过预先约定的成本上限，也属于明确的拒绝条件。若质量与成本均未显示明确失败，只是样本不足，结论应记为 inconclusive。它表示证据不足，不能解释为“没有效果”，因此需要与 reject 分开。

比较对象包括模型 + 提示词 + 工具 + Agent 运行时。新旧版本在固定任务版本、相同初态与预算下逐题配对运行。任务超时记为未完成并保留成本；基础设施故障单独分类，依预先约定的规则处理。只给新版补跑到通过，会改变两组获得成功的机会。

逐题新旧结果、重要违规、失败类型、成本与延迟共同解释汇总差值，差值的不确定性则决定现有证据能支持多强的结论。证据不足时保留旧版，与发生越权后拒绝发布，是不同原因导致的同一部署状态。置信区间、重复试验与停止规则见 R3。

离线确认还不能覆盖真实身份、并发、超时与政策变化。无外部写入的影子比较可以检查建议质量，但不执行真实退款链路；有限放量才会暴露这部分行为，因此需要明确授权、监控与止损条件。线上出现异常时，停止新的危险操作并查询可信交易状态，比单纯退回模型版本更直接：版本回退不会撤销已经退款的金额。发布策略最终仍包含对暴露范围与副作用的风险取舍。

工具落地 / LangSmith 官方工作流

把线上失败整理成下一轮离线样本

LangSmith 的 dataset 保存样本输入、可选参考输出和元数据；experiment 保存一个应用版本在这些样本上的输出、评分与轨迹。离线运行将样本输入交给被测应用，再由 evaluator 判分；参考输出供评分器使用，不应泄漏给被测应用。

  1. 离线比较：在同一数据集版本上运行 baseline 与 candidate，对照逐例结果，不只比较均分。
  2. 线上发现：检查真实 runs / threads。这里通常没有参考答案，应使用无参考检查或人工复核，不能直接照搬依赖标准答案的离线评分器。
  3. 人工整理：失败或低分记录进入 annotation queue，复核输入、输出与评分标准，纠正参考输出后再用 Add to Dataset 收入回归集。失败回复本身不能直接成为标准答案。

本节依据 2026-09-20 的在线官方文档介绍平台概念与工作流；具体接入仍取决于 SDK、接口与数据版本。本仓库未接入 LangSmith。平台提供轨迹与实验管理，任务代表性和 rubric 校准仍由评测设计决定。

多次尝试的成功率与可靠性

假设同一题每次通过的概率为 p = 0.75，各次独立且条件不变。给三次机会，至少做对一次的概率是 1 − 0.25³ = 98.44%；三次全部做对的概率只有 0.75³ = 42.19%。这是理想化算例，不是某个产品的实测。

  • pass@k：适合能生成多个候选、再验证选解的任务。还要计入 k 次生成与选解成本；用户未必有可靠验证器帮他挑中正确答案。
  • pass^k：用来观察重复运行的一致性。退款等带副作用的任务不能在生产中为“多试几次”而重复执行；应在重置的测试环境中测量。

真实数据里每题难度不同，不应先取所有题的平均成功率再套幂次公式。HumanEval 的有限样本 pass@k 估计与 τ-bench 的可靠性指标见 R3；共享缓存、环境故障和相关重试也会破坏独立性。

不同任务对多次尝试有不同约束。离线仓库修复可以在三份隔离工作区生成补丁，再用可信测试选解，成本包含三次生成与验证。退款则必须在业务层防止重复副作用；三次独立测试的成功率不构成三次真实退款的授权。知识助手即使生成三份回答，没有可靠的事实验证器，也未必能选出其中正确的一份。指标的适用性因此取决于选择器和执行环境。

运行合成实验：三态裁决与数据完整性

仓库中的合成实验展示同一套规则如何处理提升、回归、高分违规和成本超限。程序比较两组观测后输出 decision 字段：keep、reject 或 inconclusive。下文将这种按预定规则得出的三态结论称为“裁决”。实验无需模型 API，只检查统计与判断逻辑，不测量真实 Agent 能力。

在仓库根目录运行 · Python 3.10+
python labs/eval_lab.py demo --output lab-output
python labs/eval_lab.py compare lab-output/improvement.input.json

生成的报告可以与输入逐题记录对照，查看各场景的 delta、区间与 decision。一个数据完整性实验是在输入副本中删掉一条失败记录，再运行 compare：程序预期拒绝不完整的 task × run 矩阵，避免删样本抬高分数。保留原始输入和修改副本，便可确定差异来自完整性约束，而非另一次随机运行。完整字段与场景见 R6；这段实验检查合成统计管线，不涉及真实退款系统的上线验证。

接真实 Agent 时，先在 P1 定义任务与快照，在 P4 接入独立证据评分，再按 P7 比较固定预算下的候选。模型版本、任务清单、评分器版本、运行状态、产物位置与费用都应关联同一个 run ID。

交互示意：自报分数对选择的影响

七个任务的通过状态由随机布尔值模拟，不调用真实 Agent。默认开启“作弊改动”，模拟虚报分数污染基线；“哨兵检测”开关用于比较识别作弊标记前后的判断结果。

哨兵直接读取预设的作弊标记，不是真实检测器。这个玩具用“分数不低于基线”决定保留；实际实验还需独立判分、硬约束和统计协议。

自修改循环中的评分器完整性

若新版将判分函数改成恒真，20/20 的成绩就失去了测量意义。候选可以修改工具的某些部件，但评分器、确认集和发布记录必须由独立权限控制。候选输出的日志也是不可信输入，应优先采用工具执行端、环境快照与隔离验证器生成的证据。插件名称不同并不构成权限隔离，具体边界见 R4。

评测记录将固定任务及初态、真实执行及终态、可信评分及费用、冻结候选的发布判断连在一起。03 介绍按 run ID 保存这些关联的方法，05 讨论执行载体的权限与状态边界。DGM/HGM 可以依据成绩选择父代或分配搜索预算，但调度效果始终依赖底层评分的可信度，搜索选择本身也不授予发布权限。

查阅：证明、任务分数、人审与支系估计的区别

这些方法回答不同问题，不组成能力等级。经验评测给任务分布上的证据；形式化证明依赖公理、建模与证明系统；人审检查意图和副作用；支系估计服务于后续搜索分配。
