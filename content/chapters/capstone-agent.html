让 Agent 的每一步都能解释、终止和重放

完成一个 search → read → finish 的 Agent 循环。你应能指出一次错误究竟发生在模型、解析器、工具、上下文还是终止逻辑，而不只是说“模型不够聪明”。

从源码看控制流

精读 mini-SWE-agent 固定提交中的 DefaultAgent.run / step / query / execute_actions：run 管异常与保存，step 组织查询和执行，query 检查限制并记账，environment 执行动作。注意费用限制可能在上一次调用已超限后才阻止下一次调用；预算检查的时机是工程语义的一部分。本站借鉴职责划分，没有复制其全部工具、并发或安全能力。

实现顺序
创建初始消息 → 检查剩余预算 → 调用 policy
→ 记录调用与 usage → 严格解析动作
→ finish: 提交结果；search/read: 取观察并追加消息
→ 下一步；异常或预算耗尽: 写明终态并交给评分器

把三层契约拆开

模型层返回文本和 usage，不决定是否成功。动作层只接受严格字段集：search/query、read/id、finish/answer/citations；未知工具和额外字段直接结束为 invalid_output。环境层只查询内存文档，无 shell、文件写入和网络工具。即便文档写着“删除日志”，它也不能增加工具权限。

输入范围收窄以后，仍不能宣称解决了 prompt injection：模型可能选择错误答案、漏读证据或反复调用。代码里的规则策略抗注入测试只证明该夹具和分发器的行为，不能推断真实 LLM 的鲁棒性。

亲手改造，而不是只运行

  1. 在 agent.py 中跟踪 checkout-0 的四个动作；给每个字段写出消费者。删除一步 read，观察哪条评分条件失效。
  2. 用 --max-steps 2 运行 evidence，确认 budget_exhausted 仍有 trial 和调用计数。失败调用也必须计入成本，不能靠重试抹掉。
  3. 加入一个格式修复机会：只把 schema 错误交还模型，不暴露 expected_answer；修复也消耗同一个总预算。先固定协议，再比较“不修复/一次修复”。这是作业，不是默认实现。
  4. 保留只读工具，接本机真实模型。首先跑一题，人工检查完整轨迹，再扩大到开发集。不要先让模型操作主机 shell。

可选：用本机 Ollama 做第一轮真实调用

准备已经安装好权重、监听 127.0.0.1:11434 的 Ollama。执行前记录本机模型的精确 digest；模型名可指向不同权重，单记名字不够。适配器使用官方 /api/chat 的 messages、stream=false、format=json 和 token usage 字段。本仓库未预装模型，本次维护未测量真实模型质量。

将两个占位值换成你的本机模型信息
python -m projects.repoops.runner run --policy ollama \
  --model YOUR_LOCAL_MODEL --model-revision YOUR_MODEL_DIGEST \
  --limit 1 --max-steps 6 --timeout 120
python -m projects.repoops.runner report RUN_ID

这是 JSON 动作协议，没有使用 Ollama 原生 tool-calling API。故障优先查：服务未启动、模型未安装、JSON 缺字段、finish 太早、上下文遗漏。温度为零不保证跨硬件与版本逐字复现；保留原始观察、usage 和模型修订。HTTP timeout 是单次请求等待限制，当前实现没有进程级硬取消，后续执行 worker 需要外部 deadline。
