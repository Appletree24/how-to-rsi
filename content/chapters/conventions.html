工程契约：资源、错误与持久格式

一个插件增加了“后台验证补丁”功能：启动进程、订阅完成事件，再把结果写进会话。代码只有几十行，却同时改变了资源生命周期、错误语义和持久格式。插件卸载需要终止它拥有的进程，重复完成需要避免重复落账，新事件还会影响旧版本的读取与恢复。这些跨组件行为需要由明确的工程契约约束。

历史约定与案例范围守则卡片、API 名称与防御模式来自本站保留的 DSH 历史整理，未绑定可复核的上游 commit。当前规范以目标版本的 AGENTS、接口声明、持久格式与复盘为准。下文生命周期与迁移案例是设计示例，未在运行时验证。

资源所有权与卸载过程

设插件接受任务 job-9，启动一个测试子进程，同时注册结果监听与工具入口。如果它把进程句柄存在模块全局，插件卸载只移除 UI 卡片，旧进程仍会完成并发布结果；重新加载后还可能有两个监听器同时消费一次事件。“页面看起来卸载了”不是生命周期终止。

历史约定要求注册通过 ctx.effect() / ctx.on() 归属于作用域，注册表的 register() 返回 disposer。背后的原则是创建资源的作用域拥有结束它的责任。disposer 只是清理入口，不自动证明子进程已经停止；异步资源还要等待终止。

生命周期示例：状态和方法名为示意，非 DSH API
状态：active → closing → closed；不能从 closing 返回 active
start(job-9)：登记任务所有权，启动进程，订阅完成
unload：
  1. 标记 closing，拒绝新任务，停止对外注册与完成通知
  2. 对在途进程请求取消 / 终止
  3. 等待进程退出；若优雅终止失败，按明确策略升级
  4. 清理句柄，完成 closed
迟到的 completion(job-9)：不再向已关闭作用域发布结果
第二次 unload：复用同一清理完成状态，不重复发起资源操作

请求取消之后，进程可能忽略信号并继续写文件，因此第 2 步结束时只能确认“已请求终止”。卸载完成还需要进程退出的确认。等待也需要上限，以及无法清理时的外部处置方式。丢弃迟到通知可以防止关闭后的结果发布，但进程若仍存活，资源清理就尚未完成。

默认值、错误与状态的解释权

假设调用方未传执行目录。若 read 默认到会话工作区，bash 默认到宿主当前目录，两者各自可用，组合后却操作不同代码。历史 request/spec 分离将默认值解析集中在拥有方：由 resolve(request): Spec 生成完整规格，下游消费同一结果。各个 run() 自行填入 ?? default 则容易引入语义分歧。

具体输入或结果契约处理被排除的“省事”方案
配置引用不存在的执行 Provider在加载或最早可解析处失败，保留可定位错误默默换成本地实现；表面可用但越过执行边界
外部 JSON 把会话 ID 传进任务 ID 字段边界解析并验证；内部用不同品牌类型避免误接以为 TypeScript 类型能验证网络字节；或在每个内部函数重复猜测输入
子进程超时后处理信号并以 0 退出分别记录 timedOut、signal、exitCode；退出码不能覆盖超时事实只看 exitCode，给用户显示“按时成功”
模型服务失败与消费者代码缺陷按公开接口归一化服务失败；保留消费者缺陷的异常语义catch 一切并转成空答案，让缺陷被当成一次正常模型输出

校验的位置取决于输入的可信边界。同进程已验证的静态类型数据不必层层重复校验；配置、持久文件、模型 JSON、网络和进程输出则需要在进入系统时解析。品牌类型防止编译期串线，运行时授权、资源路径的安全打开和环境变量隔离仍需要各自的实现。

持久格式迁移与读写兼容性

继续 job-9：旧格式只有最终结果，新格式增加 verification/started 与 verification/completed。如果 started 会改变模型上下文或恢复后的调度决策，旧版本跳过它后继续运行，得到的不是同一个会话。历史守则要求 SessionEventMap 默认“读时必认”，未知事件只有明确允许忽略时才可跳过；结构变化才涉及 SESSION_FORMAT_VERSION。事件名和版本号不是语义兼容性的替代物。

迁移示例：事件名用于演示，非仓库现有定义
{"format":1,"type":"verification/result","job":"job-9","ok":true}
{"format":2,"type":"verification/completed","job":"job-9","status":"passed"}

对于 v1 → v2，可以将 ok:true 确定性映射为 passed。但不能凭空补出旧日志从未记录的开始时间、测试套件版本或耗时；应保留缺失语义，或明确拒绝需要这些事实的功能。若 v2 新增 cancelled，反向映射为 ok:false 会把取消变成测试失败，改变报告含义。存在向前迁移不蕴含存在无损回退。

历史相邻迁移规则让每一步只拥有 vN → vN+1，已发布代际不覆盖、不删除。这样旧输入在相同迁移链上不会因一次代码修改悄悄变义。迁移检查需要固定旧格式样本、逐步验证转换并重建模型可见内容；支持执行重试时，还需要版本前置条件和提交机制防止双重转换。它与转换函数本身的幂等性是不同要求：vN → vN+1 的输出未必仍是该函数的合法输入。

滚动升级可能需要双读双写的兼容窗口，但每多一个写入者就多一条一致性链。支持的读写版本矩阵、窗口终点与退出条件共同限定了迁移的复杂度；能够停写后一次切换的系统，通常不必永久维护两套数据表示。发布与数据恢复的衔接见工作流章。

历史工程守则索引

下面的历史守则覆盖资源注册、事件分发、包边界、持久化和协作，各条规则都有对应的输入或时序前提。例如，封闭联合的 assertNever 能抓遗漏分支，可扩展联合却需要显式定义未知分支的行为；waterfall 的 next 控制是否短路，省略调用会改变事件传播。适用条件决定了规则如何落在具体实现上。

防御性模式的适用条件

错误隔离需要区分通知与决策。通知订阅者的失败可以隔离并记录，负责否决操作的策略失败却不能自动变成允许。环境处理也有类似边界：清洗环境变量名称只能处理名称问题，派生进程仍需最小环境与隔离。路径删除必须区分链接与实体目录，不能对来源不明的路径直接递归删除。这些模式只有在各自前提成立时才能阻止对应故障。

生命周期与迁移实验

生命周期实验可以从一项真实任务开始：任务未完成时卸载插件，再释放迟到的完成通知并重复卸载，观察结果流与进程状态；重新加载后，再检查一次任务是否只发布一次完成。迁移实验则固定 v1 输入与预期 v2 输出，加入未知事件，并让旧版本读取新日志。没有兼容承诺时，应明确拒绝读取，避免遗漏事件后继续运行。这两组实验分别检查资源是否真正结束，以及持久信息是否保持原有语义。
