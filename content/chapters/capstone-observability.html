RepoOps / P6 · 可观测性

从评测回归到故障定位

通过率下降是一种结果，原因可能在模型决策、检索输入、评分规则，也可能在执行环境。相同的汇总数字可以对应完全不同的修复。本章沿一条失败工单展开观测链路：先恢复版本与任务条件，再用保存的事件提出竞争假设，最后通过受控干预缩小故障范围。

比较范围与成功契约

沿用 checkout 工单：知识助手应读到当前手册，建议 resize_pool 并提交证据；它没有实际修改连接池。P8 的仓库修复器则必须交付能在独立环境通过负载验证的配置 patch。评测平台负责记录二者的运行与裁决，不能把助手的 finish 或修复器的“测试通过”自述直接计为业务成功。

回归分析从旧新两版任务清单与 manifest 开始。数据、模型修订、prompt、索引、工具、grader、环境、种子、并发和预算共同定义了比较条件。模型与索引同时改变时，差异只能归于组合版本；报告尚未完成时，缺失 trial 也属于当前状态，已完成的容易题不能代替新版全集。

当前 report RUN_ID 输出完整 trial、顺序事件、状态、调用数、耗时和 usage；macro_success 在每题内先平均重复，再对题平均，完整性不足时标为 partial。规则策略的 usage=null，model_calls 仅是调用计数。本文在此基础上讨论跨进程 trace、attempt 层级、dashboard、provider 费用账本与差异页的扩展设计；这些结构尚未进入当前 report schema。

从已有报告取证 · RUN_ID 使用运行命令返回的值
python -m projects.repoops.runner run --policy evidence --max-steps 2
python -m projects.repoops.runner report RUN_ID

这条命令用于观察预算终止与轨迹的关系，不模拟真实 provider 故障，也不证明模型质量下降。规则策略的退化不能归因为 prompt 的好坏。

沿失败 trial 还原因果顺序

定位可以从 grader 的裁决向前展开。答案错误、引用错误和预算终止对应不同路径；引用对应的文档是否被读取、读取时的版本、搜索返回的候选以及工具报错时间，进一步决定检查范围。原始事件与组件版本保留这些先后关系，自然语言总结则容易把“发生过”压缩成“导致了”。

在同一失败 trial 中观察到优先怀疑还需要排除
当前手册没有进入候选索引、过滤或查询问题任务权限是否本来就不允许读取；语料是否缺失
当前手册被读过，却提交旧动作证据冲突、上下文截断或决策问题“已读”不等于模型最终上下文仍含该片段
同一答案仅在新 grader 下失败判分规则或参考答案改变新规则可能纠正旧误判；分数恢复不是回滚 grader 的充分理由
无有效提交，集中出现 provider_error服务、限流、配额或适配协议新版本请求更长或并发更高也可能触发同一症状

用受控干预区分检索与决策故障

假设 H1 是“检索没送到正确证据”，H2 是“证据到位但模型不会用”。可以在同一失败任务上固定模型、prompt 和预算，将检索输入替换为当前、授权的 oracle 证据。如果答案恢复，H1 得到支持；如果仍错，检查生成与上下文使用。oracle 同时改变了输入难度，因此这项干预只能提供诊断线索，不能确定检索是唯一根因。线上收益仍需在真实检索修复后、原始输入条件下确认。

若怀疑 grader，先对同一份保存的输出与轨迹用旧新两套规则重评分，形成分歧列表，再由任务契约裁决分歧；不要重新调用模型引入新随机性。若怀疑基础设施，按请求发出时间、错误类型、队列等待与限流响应分层，交错重跑旧新版本；只看失败发生得“很快”还不能区分无效请求和服务拒绝。

多种干预都可能让成绩恢复：它们可能改变了同一个中间变量，也可能分别掩盖了另一个缺陷。组合关系因此需要保留。固定 grader 后再对检索做单变量修复，最后回到原始预算与真实输入复验，才能把局部诊断连接到 P7 的版本比较。

trial、attempt 与 span 的责任层级

一次逻辑 trial 可能因 worker 失联产生多个 attempt；每个 attempt 又包含模型、工具、环境和 grader span。trial 回答“这道题最终怎样”，attempt 回答“哪些执行消耗了资源”，span 回答“时间与错误出在哪里”。P5 的 fencing可以拒绝旧 attempt 的迟到结果，却不能抹去它已经发生的模型费用。

worker 重试必须新建 attempt_id，跨进程传 trace 上下文。不同机器的单调时钟不可直接相减；父 span 的端到端耗时也不能靠并行子 span 简单求和。费用账本应关联实际请求与 attempt，区分 provider 返回用量、估算值和未知值，价格表独立保存日期/版本。超时但已被服务端接受的请求可能仍收费，“没有响应”不是零用量。

完整 prompt 可能携带知识助手读到的私有文档、修复器读到的仓库机密，评测平台还持有隐藏答案。日志默认记录元数据、哈希和经授权保存的脱敏片段；原始产物另设访问控制、保留期限与审计。哈希用于版本比对，不会自动匿名化原文。优化器可读的失败反馈与受限原始轨迹也应分开，见 P9。

成功率、费用与延迟的统计口径

下面是手算情景，不是本仓库实测：预定 10 个 trial，6 个成功、2 个业务失败、2 个基础设施失败；所有运行、失败、重试和必要判分合计消耗 120 个抽象成本单位。端到端完成率是 6/10=60%；只有预先约定排除这两次基础设施失败，才可另报模型条件成功率 6/8=75%，同时披露排除数。每成功任务成本为 120/6=20，而不是只累加那 6 次的费用。成功数为零时成本比未定义，不能写零。

再改变条件：新版成功请求都更快，但超时更多。成功请求的平均延迟不能代表整体用户体验；至少同时报告全量终态、排队、环境准备、模型/工具和验证耗时。超时若只是本地等待上限，应标记截断而非伪装成实际服务端完成时长。低样本 p95 要附样本量与原始分布，不用一个小数位制造稳定感。固定数据与模型后增加并发，吞吐上升也可能伴随单次尾延迟恶化。

故障注入与修复确认

一种诊断演练是冻结 baseline，再由独立操作者从旧索引、读工具返回空、grader 改严或 provider 错误增加中注入一项，暂不公开注入位置。诊断过程记录两个竞争假设及其预言，优先执行能区分二者的最小干预；证据不足时再扩大运行。发现、定位、修复和确认时间，以及被排除的判断，共同构成复盘记录。这是实验方案，不代表已发生的事故。

复盘记录的组织

一份可复核的复盘从异常数字链接到任务与 attempt，再指向决定性事件、干预结果和修复后的原条件确认。每个数字附来源、分母与版本；失败轨迹解释 dashboard 上的聚合，原条件复验区分诊断性恢复与可发布修复。若变化仅发生在 grader，保存输出的重评分应先于新的模型调用，避免引入无关随机性。

定位说明“为什么这次失败”；P7 继续检验“修复是否在相同预算下值得采用”。
