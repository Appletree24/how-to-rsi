递归自改：从解题器改进到改进器自应用

解析器通过率从 40% 提到 80%，可能来自更好的补丁，也可能只是多搜索了几轮。递归自改关注另一层变化：产生修改的策略本身被更新，并在后续改进中实际使用。本章以 " 3s " → 3000 的时长解析器为例，分别测量解题器与改进器，追踪自应用、成本和分布变化带来的退化。

解析器规格与有限补丁空间

本章的解析器接收非负时长：没有单位时按毫秒解释，允许 ms 和 s、首尾空白、大小写单位，以及换算后恰好为整数毫秒的小数。非法输入返回 None。因此 "10" → 10、" 3s " → 3000、"1.5s" → 1500，而 "-2s" 和 "0.1ms" 应被拒绝。这是本实验自己定义的接口，不是通用时长标准。

初始版本只识别数字串。我们准备四种人工编写的补丁：支持单位 units、单位转小写 case、去首尾空白 trim、支持小数 decimal。每个候选版本由启用了哪些补丁确定，最多有 2⁴ = 16 种。后面的“搜索”就在这 16 种真实可执行的解析器配置中进行。

初始行为与完整行为
Solver().parse("10")                              # 10
Solver().parse(" 3s ")                             # None
Solver(("units", "trim")).parse(" 3s ")             # 3000
Solver(("units", "case")).parse(" 3s ")             # None
Solver(("units", "decimal")).parse("1.5s")          # 1500

最后三个版本各有适用范围：去空白、大小写转换与小数解析解决的是不同输入条件。一个补丁修复某条输入后，整体收益仍取决于任务集的构成。

固定改进器产生的收益

将解析器称为解题器 S。改进器 I 接收 S，提出候选，再用测试得分决定是否保留。初始改进器 I₀ 的尝试顺序是 units → case → trim → decimal；每次只允许尝试两个补丁。分数相同就保留原版本，失败和无效尝试也消耗一次机会。

开发集有 10 条输入。初始 S₀ 只通过数字串那一条；启用 units 后，通过数字串及两条带小写单位的输入；随后加 case，又通过一条大写单位输入。分数依次为 1/10、3/10、4/10。这里 S 变了，I 的尝试顺序和接受规则都没有变。

固定改进器；伪代码中的评分都使用开发集
best = initial_solver
for patch in ("units", "case"):       # 顺序固定，预算为 2
    candidate = enable(best, patch)
    if score(candidate) > score(best):
        best = candidate

让 I₀ 连续运行两轮，S 也可能从 40% 涨到 80%。这种变化说明固定策略在更多预算下找到了更好的解，尚未涉及改进方法自身的变化。比较 I₀ 与新策略 I₁ 时，共同起点和相同应用预算因此是必要条件。普通超参数搜索、固定策略的程序修复都能产生上升曲线；如果新方法获得更多机会，曲线差异就混入了预算收益。

元效用：通过下游搜索评价改进器

改进器输出的是解析器，无法直接用它解析 "3s"。评价补丁顺序需要经过一次下游搜索：从同一个空补丁版本 S₀ 开始，让 I 用两个尝试机会找出 S，再测量这个 S 的得分。

元效用：评分对象是改进器，观测来自它产生的解题器
U(S) = 解析器在指定任务集上的通过比例
M(I) = U(从 S₀ 出发、由 I 用两个补丁机会得到的解析器)

I₀: units → case → trim → decimal    得到 units + case    M(I₀) = 0.4
I₁: trim → units → case → decimal    得到 trim + units    M(I₁) = 0.8

I₁ 的优势来自开发集的输入构成：五条输入带空白，其中两条同时带单位。先处理空白再处理单位，能在两个机会内覆盖更多情况。补丁组合与任务分布共同决定了结果；换一批输入，两个顺序的排名可能反过来。

U 衡量解析器的任务表现，M 衡量改进器在规定起点和预算下得到的解析器表现。若让 I₁ 接着已经有 units、case 的 S 继续改，收益就混入了 I₀ 留下的成果。真实系统还需要对多个起点、任务和完整搜索过程取平均，以覆盖随机性；把一个搜索过程的末代候选重复评十次，只测量该候选的波动，并未得到十次独立的元改进实验。

改进器自应用与后续接管

如果新顺序由人手工指定，只能说人设计了更好的改进器。配套代码做了一个受限的自应用：仍使用同一个 improve 过程，但把目标从 Solver 换成 Improver，并将评分函数从 U 换成 M。

同一个操作名有两种解释：对 Solver 使用 trim，表示启用去空白补丁；对 Improver 使用 trim，表示把 trim 移到尝试顺序的第一位。I₀ 按自己的顺序依次提出这四种修改，用 M 比较，最终保留 trim 优先的 I₁。下一次修复解析器时，实际执行的是 I₁ 的顺序。

调用结构；完整实现见 labs/improver_lab.py
def meta_utility(candidate_improver):
    solver = improve(candidate_improver, Solver(), U, budget=2)
    return U(solver)

I1 = improve(controller=I0, target=I0, utility=meta_utility, budget=4)
S1 = improve(controller=I1, target=Solver(), utility=U, budget=2)

上面省略了计账参数，实际程序会复用已取得的得分，避免重复评分。这一轮外层调用期间 controller 固定为 I₀；返回的 I₁ 只在后续调用中接管。否则，修改“下一项操作的顺序”可能让同一次循环跳项或重复运行，连预算都难以解释。

这个例子展示的是配置层面的改进器自应用。四种补丁、移动顺序的操作、接受规则和评分函数都由人写好，搜索没有发明新的补丁或算法。这个受限空间使反馈关系可以完整追踪，也限定了结论：它展示了自应用，尚不具备开放式 RSI 的能力。

运行实验：成本与分布外退化

仓库根目录 · Python 3.10+ 标准库
python labs/improver_lab.py
python labs/improver_lab.py --rounds 2 --output lab-output/improver/two-rounds.json

默认输出在 lab-output/improver/report.json。training.trace 同时记录内层解析器修改和外层顺序修改；查看 stage 以区分两者。最终每一条输入的期望值、实际值和通过状态都在 methods.*.results 中。

确认集只替换了数字，沿用了开发集的格式模板；它检查同类新输入，无法支持跨任务泛化结论。变化集则增加大写单位、减少空白。I₀ 在变化集上达到 8/10，I₁ 只达到 3/10：同一个自应用过程，产生了可复现的分布外退化。

再看成本：评一个改进器，需要运行一次基线解析器和两个候选，共 3 次整组评分。外层要评初始改进器和 4 个候选，所以训练为 5 × 3 = 15 次；随后用 I₁ 修复解析器还需 3 次，总计 18 次。穷举全部 16 种配置只需 16 次，而且得分更高。因此这次实验支持“学到的顺序在两个补丁机会内更适合这些模板”，不支持“从零开始比穷举更划算”。

所有方法最后还各执行 30 次单条输入检查，用于报告三个任务集。表里的成本单位是“对 10 条开发输入评分一次”，不是秒或 token；真实模型实验要另记调用、生成、验证和超时成本。重复自应用两轮还会发现：顺序不再变化，但外层搜索仍然付费。

训练成本还可以按后续使用次数摊销。若训练只付一次 15 次评分，随后 N 个独立实例都从 S₀ 开始、每个实例用 I₁ 花 3 次评分，总成本是 15 + 3N；每个实例重新穷举则是 16N。仅按调用数，15 + 3N < 16N 在整数 N≥2 时成立。不过穷举产物的质量更高，而且这个玩具的候选空间不变，最好的解析器本身也可以直接复用，未必需要每次重新搜索。摊销比较适用于新实例确实需要重新优化的情形，例如数据或工具变化使直接复用失效；比较双方还须达到同一质量门槛。

Agent 中的状态更新与策略更新

在上述例子中，关键是新产生的 I₁ 被拿来承担后续改进工作。它不是因为函数调用栈出现了递归语法才有这个关系；把程序改写为 while 循环，关系仍在。相反，反复调用一个从不改变的 I₀，不会因为运行一百轮就自动成为“改进器的改进”。

文献对 RSI 的范围没有完全统一的操作口径。STOP 让调用模型的改进程序自应用，同时明确其底层语言模型没有改变，因此不称为 full RSI。本文用三个条件描述具体实验：更新的部件、修改的生成者，以及更新后的部件是否承担后续改进。prompt 或 Python 文件都可能承载改进策略，文件类型本身不能确定反馈关系。

三个 Agent 改动可以说明这种区分。知识助手把 top_k=5 调成 10，若它只影响回答时的检索，是改 S；仓库修复器将“超时后先缩小检索目录”写入下轮候选提议提示，是改 I；评测平台把 passed=false 改成 true，则破坏了测量，不能算能力提升。同样是 prompt、JSON 或数据库行，作用取决于使用位置。记忆保存答案与保存“以后优先尝试哪些改法”，也处在不同位置。

Adam 更新动量、Agent 更新记忆，首先都可能只是固定规则的正常运行。若将可学习状态定义为改进策略的一部分，就可以研究状态学习对改进能力的影响：冻结初态，确认新状态改变了后续候选分布，再在新任务上比较完整搜索收益。状态变化本身不足以说明策略变强；反过来，源代码变化也可能只涉及日志格式，完全不影响 I。

人类审批和外部模型属于系统的依赖条件，应单独写清。审批存在，并不会抹去 I₀ 到 I₁ 的反馈；取消审批，也不会自动让 I₁ 更有效。能改评分器是另一个研究问题：如果连衡量成绩的规则也换了，新旧分数需要外部共同标准才能比较。

从局部改进到智能爆炸，还缺什么

Good 的原始论述从“设计机器本身也是一种智力活动”出发，设想更强机器继续设计更强机器。这给出了正反馈的动机，没有给出本章解析器会持续加速的证明。“不再使用新数据”和“不再经过人工批准”都不是由这个反馈关系推出的定义条件。

一个简化动力学模型可以说明反馈与加速之间的差别。设 q 是某个明确能力指标，每轮获得的平均有效增益为 g(q)，一轮所需时间为 c(q)。平均增长速度近似为 dq/dτ = g(q) / c(q)。模型假设指标、环境和成本函数在讨论区间内有意义；它不描述现实智能的测量定律。

  • 若 g/c 是常数 a，则 q(τ) = q₀ + aτ。系统可以持续改进，但没有加速。
  • 若指标上限为 1，且 g/c = a(1−q)，则 q(τ) = 1 − (1−q₀)e^(−aτ)。反馈仍存在，收益却逐渐耗尽。
  • 若假设 g/c = aq²，且 q₀>0，则 q(τ) = q₀ / (1−aq₀τ)，在理想模型中出现有限时间发散。真正需要论证的正是这个超线性假设，以及为何验证、数据、硬件与部署成本不会使它失效。

本实验最多只有 16 个解析器配置，得分上限是 1，无法无限增长。真实编码基准也会饱和。若要研究持续加速，需要换成能表达新增能力的任务分布和指标，记录完整资源投入，再检验增长机制；单条开发集涨分曲线做不到这些。

预算、搜索路径与实验记录

将内层预算从 2 改为 4

增加预算不一定消除补丁顺序的影响。某个暂时无收益的改动可能与后续补丁互补，但严格贪心会先丢掉它。运行所有顺序并记录被拒绝的中间候选，可以区分预算限制与搜索路径的影响。下一章的档案搜索会进一步讨论这种互补性。

从最终得分还原自应用过程

最终的 80% 没有记录 I₁ 是否承担后续改进、生成 I₁ 的预算，以及候选选择过程。report.json 中的 training.trace 区分 Solver 与 Improver 的修改，并记录后续任务使用的顺序；methods.*.results 则保留逐输入结果，包括变化集退化。只有最终 S 的得分，无法排除人为指定顺序或挑选最好一次结果。将这些关系保存为版本与运行记录的方法见 03。

将实验扩展到 RepoOps

S 可以对应工单 Agent 的提示词和检索配置，I 对应根据失败轨迹提出配置修改的程序。实验先固定 I 比较 S，再让当前 I 提议自身策略的候选。对每个 I 候选，从相同的 S₀ 重跑固定预算搜索；最终任务集只在选择结束后使用。P1–P7 提供数据、评分、计账和实验基础，候选生成与隔离执行则需要另外实现。
