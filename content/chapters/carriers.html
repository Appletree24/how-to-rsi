自修改的执行载体：配置、生命周期与权限边界

检索策略既可以通过重启加载配置，也可以由运行时插件热切换。本文将前者记为方案 A，后者记为方案 B。两者的差异不仅在切换速度，还包括配置何时生效、哪些状态延续，以及候选代码获得什么权限。本章用一个离线检索实验讨论这些取舍：候选只允许把 top_k 从 5 改成 10，每题预算 120 秒、最多 8 次工具调用，禁止读取确认答案。以下能力与检查条件构成选型设计，不表示仓库已经实现跨产品适配。

工作负载决定必要能力与隔离状态

知识助手、仓库修复和评测平台可能调用同一个模型，但任务要求的副作用不同，因此需要不同的权限范围。知识助手主要读取文档，仓库修复需要写临时工作区并执行程序，评测平台则持有候选不能接触的确认数据和结果存储。

工作负载与输入必要能力必须隔开的状态可修改对象与验收
知识助手：询问政策版本 v3 的退款期限读取固定文档快照，检索并给出处租户资料、索引版本、缓存与长期记忆；不需要生产写权限改检索配置或提示；检查引文是否支持答案、越权读取是否被拒绝
仓库修复：固定 base commit 上修 issue-042读写临时仓库、执行允许的构建与测试源码工作区、依赖缓存、子进程、网络与凭据；验证资料另存改补丁或修复策略；交付 diff、退出状态与独立回归结果
评测平台：比较 baseline 与 candidate调度独立运行、收集可信产物、计账与裁决确认题、评分器、结果库和发布指针不对候选开放平台协议由控制域管理；候选只能提交产物，不能自填最终分数

Shell 对知识助手未必有用，却额外赋予写文件与启动进程的能力；仓库修复若完全没有执行能力，又可能无法完成任务。载体比较因此需要等价的任务能力和权限约束，而非各自的出厂默认设置。某载体无法实现规定边界时，只能认定它在该约束下不适用；放宽权限后的成功率回答了另一个问题。

配置加载、生效路径与状态延续

独立离线任务可以冻结配置、启动新进程，并在完成后销毁。这种方式已能评估候选，也更容易将一次运行绑定到明确版本。同一长会话内的策略切换才需要热加载。重启和热加载都可以用于反馈闭环；递归自改要求新改进策略承担后续改进工作，启动方式本身不决定这一关系。

配置加载成功还需与实际执行对应。客户端可能只在启动时缓存旧值，检索器可能读取另一份配置，旧会话也可能保留旧服务引用。可信执行记录可以同时保存候选内容标识、实际生效配置和检索返回数量。返回数量小于 10 也可能只是语料不足，因此无法单凭结果数量反推配置版本。

状态延续会影响效果和成本。B 若沿用 A 已写入的记忆与暖缓存，增益便混入了历史；热切换后若旧监听器没有释放，一个事件可能触发两次检索，工具成本随之增加。两版从相同索引与记忆快照启动，可以控制历史差异；取消实验则检查旧请求是否仍写入新会话、旧子进程是否继续运行。配置版本与资源生命周期需要分别记录。

扩展文件、插件、harness 与通信协议

ACP 位于通信层，可以连接客户端与某个 runtime，不能单独与完整 runtime 作能力排名。一个可比较的 ACP 方案包括客户端版本、协议版本及能力、Agent 实现版本，并注明权限请求在哪一端执行。方法名、握手过程和支持的能力需要以两端具体版本为准。

工具入口与代码执行权限

假设工具列表不再显示 read_answers，但候选插件与评分器在同一进程、同一系统身份下，且确认答案位于可读目录。插件仍可能直接使用文件 API；在提示词里说“禁止读取”也不会改变访问权。工具白名单控制模型可请求的入口，进程/容器/虚拟机及资源策略控制代码实际可做的事，必须分别检查。只读挂载阻止篡改，却不阻止答案泄漏；摘要标识内容，却不证明分数由可信评分器生成。

候选、控制与发布三个执行域的职责
候选执行域：任务输入 + 允许工具 + 临时工作区 + 有上限的模型访问
+ 只输出产物和可核对事件；不可访问确认答案、评分器密钥、发布权限
控制域：固定任务快照 → 启动候选 → 收集终态 → 独立判分 → 保存裁决
发布域：核验裁决绑定的版本 → 激活；不得让候选直接改发布指针

隔离的失败路径同样影响实际权限。沙箱初始化失败后若自动转为宿主执行，这次操作便不再受预期边界约束；通用网络代理或宿主 socket 也可能绕过文件系统隔离。运行记录需要保存实际隔离模式与拒绝事件，无法建立规定边界时记为配置失败。否则，更宽权限带来的成功会被误计为搜索算法的收益。

公开实现的版本范围

DSH 提供了一个运行时扩展案例：其固定 commit 的 SAFETY.md 将它标为 developer preview，明确说明未经安全审计、不能视为安全或生产就绪，也不能作为不可信工作负载的唯一安全控制。插件框架的具体机制见 第 13 章；包索引见 第 17 章。

DSH 包与工具清单缺少生成时的 commit，因此只能作为导航，不能作为已验证的 API 快照。实际适配需要记录安装版本、commit、依赖锁、profile 与叠加配置；define/run/stop 的参数、异步终态和卸载范围均受具体版本约束。Git commit、镜像 digest 或内容寻址包都可标识候选，记录结构无需依赖某个固定字段名。

Claude Code 官方沙箱文档的 2026-09-20 页面介绍了 sandboxed Bash 的文件系统与网络隔离，并区分平台支持、权限模式与非沙箱重试。这说明产品提供内置沙箱能力，但不能推广为所有工具和扩展默认获得同样隔离。复现需要记录实际 CLI 版本与系统，并确定沙箱不可用时的行为、非沙箱重试权限与排除项。本节依据在线文档，不包含本机产品运行验证。

切换开销与固定预算下的比较

设一次候选生成耗时 G=20 秒、评估 E=100 秒，A 每次启动/切换 Lₐ=10 秒，B 为 Lᵦ=1 秒，总预算 T=1,000 秒；均为假设参数，串行且不重叠。若每个候选都支付这三项成本，A 能完整评估 floor(1000/130)=7 个，B 能评估 floor(1000/121)=8 个。按候选数固定时，两者都评 7 个，可比较搜索机制；按墙钟固定时，B 多一次机会，比较的是部署效率。两个问题都合理，但不能固定 A 的次数、放开 B 的时间，再把最优分差全算成递归增益。

改变约束后，优势可能消失：若批量离线任务可共用一次启动，L 不再每候选支付；若热切换需要等待旧请求排空，Lᵦ 不一定为 1 秒；若模型排队支配总时长，9 秒差异也可能不是主要瓶颈。完整计账应包含失败候选、冷启动、状态恢复、验证与模型费用，而不是只量成功切换的那一个 API。

载体方案的运行检查

版本检查从一次实际启动开始：候选摘要绑定加载的提示、代码、模型配置与环境，远程模型不可固定的部分另行记录。同一次运行还应有独立终态和完整成本，即使候选超时或崩溃也不例外。超过 120 秒或 8 次工具调用时，执行端按协议停止并记为失败，额外重试继续计账。

权限检查可以使用仅供验证器的哨兵文件，并尝试写成绩或修改发布指针。执行端应拒绝这些越权操作，留下独立证据；这组用例覆盖指定入口，不构成不存在其他绕过方式的证明。重放检查则从同一索引、仓库与记忆快照重新运行，并记录不可控的模型和网络随机性，不要求逐字确定。

恢复检查关注失败后的残留状态。候选先写入错误记忆再失败，回退后检查记忆、子进程与外部写入，可以区分直接恢复的状态、需要补偿的操作和不可逆的副作用。代码重新加载成功，只覆盖其中一部分。

对于开头的独立检索实验，满足约束的重启方案足以完成比较；只有研究运行中服务替换时，才需要引入热切换及其额外状态管理。完整实验再将载体运行记录接入 03 的版本账本 与 04 的发布协议。R6 现有实验 可以支持统计比较，执行隔离与具体适配器则由所选载体方案承担。
