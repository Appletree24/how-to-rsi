会话恢复：事件日志、未知结果与 Checkpoint

日志最后一条是“请求编辑文件”，没有工具结果。这个尾部可能来自几种完全不同的情况：日志写到一半，工具尚未执行，或文件早已修改但结果还没落盘。恢复协议需要分别处理物理完整性、逻辑完整性与外部副作用；仅凭缺失结果，无法决定是否可以重新编辑。

DSH 的会话与存储契约依据固定提交的 session 文档、persistence 文档。恢复决策表、工单示例与 checkpoint 身份字段属于通用协议设计，故障场景是实验方法，未提供 DSH 崩溃恢复实测。末节对照 RepoOps 的 trial 级持久化。

事件日志保存执行事实，消息是其中一个投影

聊天消息能保存用户和助手文字，却通常缺少失败尝试的预算、工具派发状态、内容压缩范围，以及当时的工具 schema。DSH 文档以追加式 SessionEvent 为事实源，deriveMessages() 从中导出模型历史。消息投影随事件变化，不单独维护另一份可任意修改的历史。

模型可见 ⇒ 日志可重建turn/*、request/header、assistant/attempt 等日志项用于恢复或审计，无需全部进入模型历史。插件修改模型所见内容时，必须通过记录与已声明的纯投影路径；离线读取方也需要同版本投影定义，才能由事件重建请求。

每条事件为 { type, seq, time, data }，seq 连续，data 要能无损表示为 JSON。四类表面事件——system/message、user/message、assistant/message、tool/result——带 surfaceOp 声明追加或替换范围；log-only 事件不带它。日志从不改旧事件，但投影可以通过新事件替换模型当前看到的表面，这两句话并不矛盾。

同一日志的模型历史与调用视图

事件含义示例，省略 payload，不是可导入日志

seq 1  step/start
seq 2  system/message     surface append：当前系统提示
seq 3  user/message       surface append：用户问题
seq 4  request/header     log-only：路由配置与工具 schema

可以把投影写成 state[n+1] = fold(state[n], event[n], projectionVersion)。增量投影避免每次从头扫描；冷读必须能用相同规则复算。若某个投影依赖当前网络结果或系统时间，重放会改变历史；纯投影应只依赖受控输入。快照是加速手段，不应成为第二份无法对账的真相源。

request/header 记录调用配置与工具，request/context 记录路由能力等元数据；系统提示通过 system/message 进入日志。完整 assistant message 内嵌已结算流及可用的 usage；attempt 保留未形成表面消息的已结算尝试。进程硬崩溃前尚未结算的实时流可能丢失，这些事件无法恢复从未记录的内容。

append 的可见性与 flush 的持久性

文档中的 SessionHandle.append 承诺批次已接受、排序，并对同后端实例后续读取可见；后端可以缓冲。已 resolve 的 flush 才承诺其覆盖的已确认写入具备崩溃持久性。该承诺依赖部署环境满足文件系统与存储硬件假设，覆盖范围也限于相应存储屏障。

固定提交中 flush 时点的文档差异persistence 的 checkpoint 段称循环在领取下一普通 turn 前用 flush 作为检查点；同提交 session 的 turn/end 注释却称 loop 不在回合边界等待 flush，由 checkpoint-policy 负责每请求屏障，whenIdle() 后读取存储的消费者需自己 flush。这两处描述不足以确定默认时点。handle 的显式 flush 契约是明确的；实际屏障由目标 profile、checkpoint 插件及调用路径决定。

每条事件都 fsync 可以缩小丢失窗口，但会增加 I/O 与尾延迟。批处理降低成本的同时，也拉长了接收成功与持久成功之间的间隔；两种确认需要分开，并向调用方暴露存储失败。若业务承诺用户收到完成通知就能恢复，通知之前就需要完成相应持久化屏障。

物理修复与逻辑恢复

文档中的 JSONL Provider 默认使用带校验和的拼接 Zstandard 帧，也可配置裸行。存储层只返回物理有效的连续前缀，处理撕裂尾巴，并在新 append 前完成必要的物理修复；它不应因为 turn 未结束而删掉整个回合。一个长回合可能已经持久化大量有效工作。

逻辑恢复由持有写 handle 的 resume 路径计算 interruptedTurnClosers：为缺失工具结果补中断错误、闭合开放 step，并追加 turn/end { reason: { kind: 'interrupted' } }。这些是新的普通事件，不伪造历史成功。只读观察者可在内存平衡视图，但不写回，以免与活体 writer 竞争。

失败窗口推演：恢复不是重新执行工具
T0 writer 获得会话所有权
T1 tool/call(c1) 进入有效日志前缀
T2 外部写入可能发生，也可能尚未发生
T3 进程崩溃，tool/result(c1) 未持久
T4 新 writer 获得所有权，读取连续前缀
T5 为未结算调用补中断结果，并闭合 step/turn
T6 对外部副作用做状态核对；只有明确策略才决定能否重试
# T5 解决日志可解释性，不证明 T2 的真实结果

追加日志本身无法保证外部动作恰好执行一次。远端支付、工单或仓库提交需要目标系统的幂等键、版本前置条件或查询接口；无法查证时保留未决状态并转人工处理。中断错误只能说明本地调用没有正常结算，将它写成“未执行”会诱导重复副作用。

从持久证据决定后续执行

日志重放只运行纯投影，不调用工具、不重新发模型请求。恢复执行是另一个受授权、预算和所有权约束的流程：先取得唯一恢复写者，阻止旧执行者继续提交，再检查连续有效前缀。会话日志的单写者只能约束日志；远端动作还需要目标系统可校验的 fencing、幂等协议或状态核对，取得会话锁无法让外部执行自动停止。以下状态表将这些情况分开处理。

恢复时的持久证据决策与后续动作明确禁止
请求快照已记录，模型尝试未结算标记尝试中断，保留可能已计费的预算占用；若继续，在同一冻结输入与剩余预算下显式创建新尝试伪造丢失流内容，或把未知费用清零
仅有工具意图，没有结果默认 pending tool / outcome unknown。只有协议保证“派发前持久屏障”且能够排除旧执行者继续派发，才能根据缺失派发标记认定未派发仅凭没有 started/result 就推断工具没运行
已派发，无结果；确认是纯只读工具记录旧尝试中断，可在新 callId 下重新读取并关联旧调用；保留新证据版本，重新计费把新读取伪装为崩溃前的结果，尤其数据已经变化时

checkpoint 缺失、损坏或与日志前缀不匹配丢弃这个加速快照，从可信日志前缀用支持的投影版本重建；依赖缺失则只读诊断并阻止执行用较新的快照覆盖日志空洞，或静默采用当前配置补齐历史

工单已创建，回执却丢失

派发前将 callId=c17、规范化参数摘要、主体、目标系统与稳定幂等键 K 记录并完成持久屏障；K 代表这次逻辑动作，不能每次重试生成新键。远端创建成功后、写本地结果前崩溃，恢复者首先查询 K 对应的工单。查询确认成功，就追加带操作 ID 的核对记录，再让用户知道工单已经存在；远端仍在处理中则有界等待，而不是再创建一张。

查询返回“未找到”也未必是未执行：需要确认查询是否强一致、旧请求是否仍在途以及幂等键是否还在保留期内。仅当目标协议保证同一 K 与相同参数再次提交不会重复动作，且当前权限与预算允许时，才能带 K 重试；参数冲突或键已过期都应停下。若服务既无幂等键又无可靠查询，保留 outcome unknown 并提示人工查证。根据标题搜索到一张相似工单只能作为线索，不足以自动认领为本次结果。

不同目标系统提供不同的核对条件。本地文件可以通过“期望旧摘要 → 原子替换 → 校验新摘要”降低歧义，但新摘要相同只证明目标状态满足，未必证明由本次调用完成。受控数据库可以把业务变更与执行账本放进同一事务。通用 outbox 保存待投递意图，投递仍可能重复，因此消费者必须去重。缺少这些条件的跨系统动作需要保留未知状态；补偿同样是新的副作用，必须独立授权。

工单协议的故障实验有三个关键切点：意图 flush 后尚未派发、远端提交后尚未收到回执、结果 flush 后尚未写入 turn/end。每次终止执行者后，记录有效日志、目标系统操作数量和恢复决策；连续恢复两次，应重用已有核对事实而不创建第二个工单。查询暂时未找到时仍保持未知，旧执行者恢复连通后也不能绕过所有权继续提交。目标系统若无法约束旧执行者，重复动作风险就仍然存在。

单写者所有权与恢复竞争

每会话 SessionHandle 把读取、追加、flush 和 close 放在同一个所有权边界。写式 open 原子获取单写者，活跃 owner 存在时第二个写 open 拒绝；只读 handle 不取得所有权且禁止变更。close() 按文档幂等、异步且不可取消，负责最后排空与释放；调用方仍要等待它，不应在释放过程中强行丢弃依赖。

存储 seam 的契约摘要，不是完整类型定义
ctx.sessionPersistence: create / open / stat / list / flush
SessionHandle:          read / append / flush / close
write ownership:        第二个活动写者被拒绝；只读 handle 不得变更
seq:                    新批次必须连续接在已有逻辑末尾
append:                 best-effort durability；已接受与可见
flush:                  显式持久化屏障
close:                  最后排空并释放所有权；幂等、不可取消

分布式存储中的单写者需要存储端可验证的所有权或版本条件。本进程 mutex 无法覆盖网络分区，租约到期也未必阻止旧 owner 继续提交。这是更换存储后端时新增的设计责任，不能由本地 JSONL 文件的所有权规则直接推出。

日志代际与格式迁移

固定提交文档讨论 v0–v3 的已发布格式；实际版本由 packages/core/session/src/types.ts 的 SESSION_FORMAT_VERSION 定义。迁移保留前代，在旁边发布后继，每个包只拥有一步 vN → vN+1。

session.jsonlv0 已发布代际
── v0→v1 ─▶
session.v1.jsonl保留原代际
── v1→v2 ─▶
session.v2.jsonl保留原代际
── v2→v3 ─▶
session.v3.jsonl本图示意目标
  • 选择最高规范代际：即使旧代能读，最高代是未来版本也拒绝。否则旧程序继续写旧代，会形成两个互不承认的分叉。
  • 读与写不同：读式 open 在内存组合迁移，不发布后继；写式 open 持有所有权，编码、验证并独占发布新代。不能用“打开看看”偷偷修改用户数据。
  • 旧代保持不变：已提交代际不改名、不替换、不删除，作为审计材料保留；自动降级需要另外的兼容协议。
  • 未知事件默认拒绝：当前格式中，只有丢失也不影响重建的纯信息事件可标 ignorable: true。历史 v0/v1/v2 迁移对未知事件更严格，即使有该标记也拒绝，不能泛化宽松规则。

stat/list 读取头和不透明 revision，适合冷读缓存判断；revision 不是递增业务序号、租约 token 或恢复游标。SessionHeader 保存版本、cwd、来源及 preset 等元数据，fork 的精确继承切点 inheritedEventCount 与正文配对保存。恢复正确文本却恢复了另一套工具权限，也不是正确会话恢复。

Checkpoint 绑定日志前缀与执行身份

在通用恢复协议中，可恢复 checkpoint 绑定日志流/代际身份、已持久连续前缀的末尾 seq 与摘要、投影版本、工作区基线、未决 callId 和预算账本。实际系统提示与工具 schema、模型路由、Provider/插件版本、最终组合配置身份、授权快照与上下文编译版本，则确定这段状态来自哪一次执行；它们与 第 14 章的请求编译产物对应。摘要用于核对身份，可读取的不可变内容仍须保留。凭据通过受控引用获取，并在恢复时重新授权，不随 checkpoint 明文保存。

发布顺序应是：先让对应日志前缀与引用对象持久化，再生成并原子发布指向该前缀的 checkpoint。期间崩溃最多留下较旧快照，恢复从其 seq 之后继续 fold；快照绝不能声称覆盖尚未 flush 的事件。并发追加时快照必须来自固定前缀的状态，不能拿“当前内存状态”配上较早 seq。它不包含可直接复活的网络连接、进程句柄或正在执行的工具栈；这些资源要按恢复协议重建或核对。

例子：旧任务按策略 P7、工具 schema S3 在基线 B 上准备 patch，重启时宿主已经部署 P8 并撤销写权限。可以用 P7/S3 的受控历史定义重建当时模型看见的请求，但不能凭旧快照恢复写权；新执行受当前撤权约束，应追加恢复拒绝或重新准入记录。如果允许切换新模型或新摘要器，记录配置转换并重新编译，不能把新输入记成旧 attempt 的原样重试。恢复后的剩余预算也沿用已消耗与未对账占用；墙钟截止时间不能靠进程重启延长，跨进程应使用可信时间基准，无法判断剩余时间时停止新派发而不是重置计时。

全量扫描日志容易保持单一事实源，但恢复耗时随会话增长；快照降低冷启动成本，同时增加格式兼容、原子发布与依赖保留义务。旧配置用于解释历史，当前安全政策约束后续执行。旧投影版本不可用时，重建应停止并报告缺失依赖，静默换用新版本可能生成与原执行不同的历史。即使旧请求被完整重建，模型输出也仍可能变化，请求恢复只保证输入身份。

快照实验可以截断 checkpoint 写入、替换前缀摘要，或在日志 flush 与快照发布之间终止进程，检查能否退回可信前缀；再用 P8 撤权后的配置恢复 P7 任务，观察历史是否可读、写动作是否被拒。全量 fold 与 checkpoint 加尾部重放的比较应覆盖模型投影、未决集合和预算余额。旧配置被清理会破坏重建依赖，未计费尝试则仍需保留占用，直到对账或按保守上界结算，与 第 15 章的取消与预算约束保持一致。

附件的 persist-before-event 顺序

固定提交的 附件文档 要求 persist-before-event：先发布持久不可变对象，再追加引用它的消息。先记引用再写对象，崩溃后可能留下完整日志和缺失图片；先写对象则可能留下孤儿对象，后者可以通过保守回收处理。

AttachmentId 是不透明标识，本地后端的 sha256:<digest> 表示不授权消费者自行拼路径。对象位于独立存储，权威读取重新核对摘要、媒体与尺寸；readImageRequest() 再按路由生成请求版本。固定提交文档的本地图片准入上限为每消息 20 张、源编码合计 200 MiB，单源 20 MiB / 6400 万像素 / 单边 8192 px；默认归一化长边 2048 px、编码 4 MiB。它们是该版本后端约束，不是所有存储或模型的通用容量。

fork/resume 可能共享附件，删除某会话不能直接删除其所有对象。该文档明确服务 retention-neutral、引用感知 GC 延后，因此会话删除与对象回收需要分别处理。改为远程 Provider 时，还要核对对象权限，以及当前工具执行环境能否读取宿主路径。

RepoOps 的 trial 级恢复

runner.py 用 (run_id, task_id, repeat) 唯一键跳过已提交 trial；结果和完整轨迹在一次 SQLite 事务中可见。run_agent 的动作与观察在内存中累积，结束后才交给 runner。进程在 trial 中途退出，未提交 trial 会整体重跑，无法从最后一个工具事件继续。当前只读 search/read/finish 降低了重跑风险；迁移到修复工具后，还需要处理重复写入和未知结果。

会话级恢复的实验需要更细的终止切点：append 前、append 后 flush 前、flush 后，以及外部副作用后结果提交前。比较重启后的有效日志、模型投影与实际外部状态，再加入双恢复者竞争、旧 reader 读取未来代际和共享附件删除场景，才能分别判断物理可读、逻辑可恢复、副作用可核对与对象可回收四类性质。
