RepoOps / P0 · 项目介绍

三个项目，一条可检查的改进链

知识助手、仓库修复器与评测平台处理不同的结果：有依据的建议、可验证且可回滚的补丁，以及经历失败、重试与取消后仍可信的实验比较。它们可以共享实验记录，但成功条件各不相同。本系列从一张只读工单出发，沿数据、执行、检索、评分和持久化追踪结果的形成过程，再讨论隔离执行与自动改进。

三类项目的结果与约束

P1–P5 以仓库已有的只读知识助手代码为起点；仓库修复与评测平台用于讨论需求变化后的架构。P8–P10 进一步讨论隔离执行、候选搜索与修改器更新。这三类项目的结果和约束如下。

项目 / 用户需求结果关键约束验证方式的差异
知识助手：值班人员判断当前故障如何处理动作建议、适用条件、可回到原文的证据；证据不足时拒答版本正确、请求者有权读、建议不自动变成生产操作答对文本不意味着执行成功；不需要先引入 shell 或多 Agent
仓库修复：维护者得到可审查的补丁固定基线上的 diff、独立验证结果与执行轨迹任务环境隔离、验证器不可被修改、不得把测试删除当修复引用齐全不能证明程序行为正确；需要环境与行为验证
评测平台：研究者比较候选是否真的变好冻结规格、完整 trial/attempt、失败与费用账本、可重放报告不能挑最好一次伪装 pass@1；取消与重试不擦除成本吞吐高不代表评分可靠；平台不替模型定义答案语义

少量只读任务的主要风险在于评分是否可靠，串行循环与 SQLite 已能保留一次失败的完整上下文。任务变成长时间构建、多个研究者并发运行且需要取消后，执行所有权和故障恢复才成为调度的核心问题，P5 的租约、资源预算与独立 attempt 由此引入。消息队列可以提高调度效率，但无法解决错误答案被判对的问题。

一张工单的数据路径

tasks.json 中的 checkout-0 包含 error=POOL_EXHAUSTED 和建议 rollback_release；旧手册也支持回滚，但 revision 2 已将处置改为 resize_pool。这张公开合成教学工单用版本冲突构造了一个可追踪的错误来源，并非生产事故记录。

  1. 需求与数据：用户需要建议，不执行操作。prompt 与 documents 进入 Agent，expected_answer 与 required_citations 只由评分器消费；P1 区分参数分离和安全隔离。
  2. 最小执行：evidence 策略先 read 故障，再 search 当前手册、read 手册，最后 finish。P2 分析这些步骤产生的可信事实，以及预算耗尽后的终态。
  3. 证据选择：当前适用手册决定处置，工单建议仍需核实。P3 的独立实验区分候选召回、排序、上下文裁剪与读取策略。
  4. 评分：finish 返回 resize_pool 并引用 checkout-incident-0 与 checkout-runbook，两份材料还须实际 read 过。P4 分析读取记录与语义支持之间的差距。
  5. 持久化：结果与轨迹在一个 trial 事务内保存。P5 讨论外部调用成功、本地提交前崩溃时的重复计算与费用归属。

删除 read 但猜对答案，会被证据规则拒绝；把未知错误强行映射到旧动作，会错失应当拒答的边界；允许 Agent 修改评分器，则高分失去可信依据。这些反例分别定位取证、决策和评测边界，成功轨迹本身无法区分它们。

实现范围

仓库包含 12 张公开教学工单、Python 只读 Agent 循环、SQLite 结果存储、规则策略和可选的本机 Ollama 适配器。代码入口见 RepoOps README。两个独立故障实验与后续设计的范围如下。

模块实现与实验范围限制
单机只读 starter任务文件、run_agent、grade、run manifest、SQLite trial 与报告不是权限服务、隔离沙箱、自动运维或生产知识助手
可选 Ollama 适配器本机 /api/chat、严格 JSON 动作、usage 与终态记录仓库不自带权重；本文未提供真实模型质量测量
P3 检索故障 lab独立可下载脚本；Recall 0.5→1 而上下文覆盖仍为 0.5 的合成单例没有 embedding、学习式重排或 LLM，不代表生产效果
P5 租约故障 lab独立 SQLite 实验；20 条时序观测、两次合成记账共 14 单位单进程逻辑时刻，不是多 worker 服务或真实支付测试
后续扩展混合检索、Go 控制面、Harbor、GEPA、修改器更新的设计与实验方案这些模块尚未接入 starter

运行规则策略对照

仓库根目录使用 Python 3.10+，无需依赖或 API key。测试命令用于检查 starter 行为，不测 LLM 能力。

运行两种规则策略
python -m projects.repoops.runner demo
python -m unittest discover -s tests -v

结果写入 lab-output/repoops/summary.json 和两份策略报告。开发集有 6 张工单，来自 3 个服务家族；naive 直接采用工单建议，evidence 读取当前手册，示例预期严格通过率分别为 0 和 1。这个人为构造的规则对照用于验证流程；complete、任务清单、终态和引用共同说明 aggregate 的来源。6 个相关样本不足以估计总体优势，也没有测量学习能力。

共用实验外壳，不统一内部语义

三个项目可以共享不可变实验规格、任务标识、预算、轨迹与 artifact 引用，但知识助手的证据支持、修复器的行为测试、平台的接受结果事务应各自实现。把它们都压成一个 success=true 会丢掉失败原因。保留分项结果，明确谁有权产生每一个字段，再由预先声明的发布规则决定是否接受。

P9 搜索候选策略，P10 更新生成候选的修改器。这两层改进都依赖同预算、冻结数据与可信评分下的净收益比较。若开发集分数反复上涨而独立确认没有改善，现有证据只能支持选择过拟合或证据不足，无法支持递归改进成功。

章节之间的依赖

P1 确定数据边界与独立拆分，P2 保存执行终态，P3 定位证据在检索链路中的丢失位置，P4 检查评分反例，P5 区分结果接受与费用发生。P6–P7 在此基础上讨论观测和冻结实验；P8–P10 才增加隔离执行与改进研究。岗位与项目材料的讨论集中在 P11。
