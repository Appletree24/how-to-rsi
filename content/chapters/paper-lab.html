STOP、DGM 与 HGM：自改进的控制流程

自改进系统既要生成修改，也要决定修改由谁提出、以哪个版本为起点，以及预算用于生成新候选还是测量已有候选。STOP、DGM 与 HGM 将这些决定放在不同位置：STOP 让改进程序以自身为输入，DGM 从历史档案中选择自修改的父代，HGM 则把展开与补测纳入同一搜索过程。本章沿控制流程比较三者，并用可手算的例子说明这些机制如何影响搜索与测量。

STOP：自应用与两层评分

设 I 是一段改进程序的代码，s 是待改程序，u 是程序的任务得分，L 是固定语言模型。普通调用让 I 改进 s；STOP 则把 s 换成 I 自己。此时评分也要换一层：候选改进器的价值，取决于它在下游任务上能改出什么程序，而不是它自己的代码长什么样。这是 v3 §3–4、Algorithm 1 与式 (2) 的自应用关系。

控制流程的简化记法
I(u, s, L) → 候选程序        # 改进器调用固定语言模型 L
M(I) = 下游任务上 u(I(u, s, L)) 的平均
I_next = I(M, I, L)          # 当前 I 以自身为待改程序

下一轮使用 I_next，重新生成程序或改进器候选。

内层的 u 衡量程序做题的结果，外层的 M 衡量“改程序的程序”。因此，评价一次候选 I 往往包含多次下游改进与测试，成本不等于一次普通任务调用。固定 L 意味着这里改变的是调用模型的程序，而不是模型权重。

直接按候选改进器的代码质量评分，测量的是可读性或静态性质，无法确定它能否改好下游程序。用一次下游结果代替 M 的约定任务平均，也会让搜索随机性混入能力判断。两层评分对应两种输出：S 产生答案，I 产生以后用于回答任务的程序。外层评价沿这段因果链衡量 I，所有内层生成和失败测试也随之成为外层成本。

第一章的本地实验把这个关系缩到四种补丁：units 处理单位，case 转换大小写，trim 去除首尾空白，decimal 支持小数。labs/improver_lab.py 中的 edit 对 Solver 启用补丁，对 Improver 则把该补丁移到提议顺序的最前面；train_improver 用候选 Improver 从空 Solver 出发、做两次提议后的开发集得分作为 M。内外两层都只接受严格涨分的候选。按初始顺序 units, case, trim, decimal 做一次外层搜索，可以逐项推得下表：

开发集共十项。初始空解析器只通过 "10"；先启用 units 后，还能通过 "2s" 和 "5ms"，再启用 case 才能通过 "4S"，得到 0.4。若把 case 提前，它在没有单位处理时并不增加通过项，于是被拒绝；第二次启用 units 后就停在 0.3。反过来，trim 单独就能处理三个带空白的纯数字，接上 units 又能处理带空白的单位字符串，最后通过八项。顺序的作用来自补丁依赖、严格接受规则和两次提议的预算共同限制。

外层接受 trim 后，当前保留顺序变成 trim, units, case, decimal；下一项 decimal 是移到这个版本前面，而不是重新从初始顺序构造候选。不过，本次外层调用的控制器仍是初始版本，直到下一次调用才由新版本接手。这个有限配置实验展示了自应用怎样改变后续搜索，没有复现 STOP 的语言模型候选生成。真实任务上的提升还可能来自更多调用、对训练任务的适配，或恰好选中了表现好的运行；冻结模型并没有排除这些解释。R1 的同预算完整搜索对照用于区分它们。

配置实验的执行时序：控制器在单次调用内固定
controller = I₀                 # 本次外层调用使用的控制程序
incumbent = I₀                  # 已保留的待改对象
best_score = M(incumbent)        # 初始评价计入成本，之后复用这个值
for patch in controller.order:
    proposal = move_to_front(incumbent, patch)
    score = M(proposal)          # 从空 Solver 出发，按 proposal 提议两次
    if score > best_score:
        incumbent, best_score = proposal, score
return incumbent                # 下一次调用才把返回值作为控制器

case 在 units 之前被拒，是因为它当下不带来收益，大小写处理的价值要等单位处理生效后才显现。接受中性中间状态、一次提议组合补丁，或增加提议预算，都可能解除这个局部限制。因此 trim 优先的优势依赖补丁库、严格接受规则与两次提议预算的共同作用。分别改变其中一个条件，才能区分顺序策略的作用与接受规则、搜索空间或预算变化的作用。

DGM：父代既是修改对象，也是修改者

DGM 保留一个代理档案，从中选出父代，再让父代产生自身代码的修改。变化的是代理代码，外部档案管理与父代选择保持固定。v3 §3、§4.3 与附录 C.2–C.4 描述了这个流程；其中 C.3 还把诊断与实现分开：独立诊断模型给出改进建议，再由编码代理动手。因此，自修改发生在系统的特定组件内，其余组件仍在控制搜索。

突出修改者的差别；省略诊断与执行细节
parent = select(archive)

自修改条件：child = modify(modifier=parent, target=parent)
冻结修改者：child = modify(modifier=initial_agent, target=parent)

候选通过有效性检查后入档；任务分数影响后续选择。
外部 select 不因 child 的代码变化而自动更新。

这解释了一个容易漏掉的对照：冻结修改者不等于永远只改初始代码。它仍可以针对已经改进的 parent 工作，只是负责动手的 modifier 保持初始版本。如果两组的 target 也不同，就同时改变了两个变量。

这一机制可以用 modifier_id 和 target_id 分别记录修改者与目标版本，并据此设计对照。在同一组目标版本上比较旧、新修改者，可以看出修改能力的局部差别；让冻结组与更新组各自跑完整段搜索，则比较它们在累计预算下找到的结果。这两个结果可能不同：即使新修改者在固定目标上更好，它带来的后代也会改变之后的搜索路径，未必使整段搜索更有效。

档案保留了从其他实现结构继续探索的机会。当前任务能力与产生有用后代的能力是不同的量，最高分节点未必总是最有价值的起点。档案也会增加存储、评估与选择费用，并可能积累噪声高分。比较修改者时，固定这些外围机制有助于归因；比较整套系统时，其费用则属于总成本的一部分。

父代抽样：表现与展开次数的权衡

附录 C.2 对可选父代的得分要求是小于 1。对其中每个父代，先计算权重 w = sigmoid(10(α−0.5)) / (1+n)，再除以所有可选父代的权重之和，得到抽样概率。这里 sigmoid(x)=1/(1+exp(−x))，α 是表现，n 计仍有代码编辑能力的子代数。分子偏向当前表现较好的节点，分母降低已反复展开节点的权重，两者在同一次选择中起作用。

假设只有两个可选父代。A 得分 0.8、已有 9 个这样的子代；B 得分 0.5、没有子代。A 的未归一化权重约为 0.9526/10 = 0.0953，B 为 0.5/1 = 0.5。归一化后 A 约 16%，B 约 84%。较高当前分数并不意味着这一次更可能被选中。

这个结果来自明确的探索偏好：A 虽然当前更强，却已经有较多可继续工作的子代，B 因而获得更多展开机会。它并不保证 B 能产生更好的后代。任务子集决定 α，子代是否仍能编辑代码决定 n；改变任一口径，即使公式不变，也会改变搜索分布。

档案选择与修改者更新是两种不同的机制，对照也不同。论文的“无开放探索”消融继续使用最新有效后代；它不等于始终保留历史最高分的严格爬坡，因为“有效”不要求比父代得分更高。附录 E.1 的历史费用估算又给出另一层差别：SWE-bench 完整方法一次运行约 22,000 美元，对照约 10,000 美元。这些是原文特定设置的估算，不是今天复现的报价，但说明同样迭代数可能消耗不同资源。同轮数表现与同费用表现回答的是不同问题。

HGM：在展开与补测之间分配预算

给新代理生成一个后代，和给已有代理再测一道题，都会占用搜索资源，却带来不同信息。前者扩大候选集合，后者让某个候选的表现估计更稳定。HGM v3 §2–3.3 将选择、展开与评估区分开，树策略既可以产生新代理，也可以增加已有代理的任务评估。评估次数因而不再是每个节点相同的固定配额，而是搜索决策的一部分。

例如，两个代理分别测得 1/1 和 60/100。前者的观测通过率更高，但仅有一次试验，尚不足以确定它更好；若一律把所有代理测到 100 次，又可能把预算耗在明显较差的候选上。调度器既要估计哪里可能产生好后代，也要判断哪里值得再测一次。只记录最终树结构，会漏掉测量所消耗的预算。

直接淘汰 60/100 会把点估计当成确定排名；给 1/1 永久最高优先级，则会让早期幸运结果吸走后续资源。固定均分测试预算便于比较，却可能浪费在不值得继续的支系上。HGM 把这种机会成本交给树策略处理，但自适应调度仍会影响最终统计：测试分配、回传任务与停止时机都是分析所需的运行信息。搜索期的自适应分配与最终冻结后的确认承担不同作用。

CMP 的理论目标与可观测统计量

HGM 用 CMP 描述一个支系在继续投入搜索资源后可能带来的价值，不过论文中有三种相关而不同的量。

  • 理论目标（§3.2）：给定未来策略与预算，在该支系中最终选出代理的期望效用。它关心继续搜索后的终选结果，不只是现有节点的分数。
  • 在线机制（§3.3）：利用支系的成功/失败统计引导采样。搜索时尚不知道未来结果，只能根据已获得的观测分配下一份资源。
  • 回顾性实证目标（附录 D）：搜索结束后查看最佳后代的经验均值，并排除根节点。这衡量已经找到的后代，而不是当时可直接观测的未来期望。

假设 A 支系的两个后代分别为 9/10 和 1/10；B 为 6/10 和 6/10。合并通过率为 A=50%、B=60%；当前最佳后代则为 A=90%、B=60%。指标一换，排序就反过来。未来还有多少预算、是否能再生成更好后代，这些信息尚未包含在这四个分数中，因此两种统计量都不等于理论 CMP。

再给 A 的强后代测十次，假设又通过九次。A 的合并通过率变成 (9+1+9)/(10+10+10) = 63.3%，现在超过 B。但没有产生新后代，已有强后代的通过率也仍是 90%。变化来自采样权重，而不是代理能力的变化。这也是自适应评估记录中每个节点的测试次数很重要的原因：只剩支系总分时，就无法区分能力差别和测量资源偏向。

理论分析的 Assumption 1 还包含只关心最终代理、可重复的任务试验、不消耗预算的证明以及单位成本自改等条件。实际部署中，一次修改的耗时可能相差几个数量级，任务分布也可能漂移。此时按“动作次数”分配的相同预算未必对应相同成本，理想条件下的最优性结论也不能直接说明实际估计器的表现。

这种差异也影响统计接口的设计。单一 cmp_score 字段如果不注明定义与观测截止点，就可能混淆在线支系统计、当前最佳后代和理论未来期望。节点测试次数与最佳后代的选择规则需要同时保留：上一段从 50% 到 63.3% 的变化完全来自补测，若只展示一个“能力分”，就无法从记录中辨认变化来源。

分离修改者、起点选择与测量调度的贡献

要验证的改变最小机制差别不能省略的反事实与代价
改进器自应用把 I 作为输入，用下游元效用评价候选 I，再让新 I 接管后续调用冻结 I 同预算搜索；计入外层评价嵌套的全部内层成本
代理自修改与档案探索分别标识 modifier、target 与档案选择器，允许从历史节点展开冻结 modifier 但不冻结 target；另对照档案与顺序搜索，计入无收益展开
展开与补测联合调度同一预算中区分生成后代和增加已有节点的测量记录每个节点的采样量及动作成本，不能拿支系汇总分直接当能力增益

这三种机制可以在同一实验框架下分离。以 RepoOps 为对象的一种对照设计是：固定模型、候选字段与初始规则改进器，比较固定改进器的顺序搜索、允许更新改进器、同预算随机搜索、带档案但固定改进器的搜索。更新组与固定组的差别指向修改者；档案组与顺序组的差别指向起点选择；随机组则比较复杂控制与相同资源下普通尝试的效果。

各组从同一批起点开始，用开发数据搜索，在预设预算内按事先确定的规则终选，之后再运行确认。完整轨迹同时保留失败、零收益候选和成本，才能解释这样的结果：更新组按轮数领先，对齐总成本后却不再领先；或者档案带来收益，更新修改者没有额外收益。前者说明轮数没有反映资源差别，后者支持搜索组织方式的价值，却没有提供修改能力变强的证据。

历史最优后代分数按定义不会下降，因此一条随迭代上升的曲线只能描述搜索曾找到哪些候选。要判断改进来源，还需要同预算固定修改者与随机搜索曲线、全部成本和独立搜索重复。按已看到的后代反选“最强祖先”又引入了事后选择，其优势需要新数据或新运行确认。只有把这些对照与控制流程对应起来，最终得分才有助于解释搜索为何有效。
